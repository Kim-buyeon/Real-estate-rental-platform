## 1. 인프라 기능 (INF)

서비스가 성립하기 위해 인프라가 무엇을 제공해야 하는지를 정의한다. **인프라 구간의 목적은 웹 서비스를 배포하고 안정적으로 구동하는 것이다**(2026-09-19 결정). 배포 대상은 AWS EC2이며, 먼저 EC2에 배포한 뒤 Rocky Linux로 옮긴다 — 노드와 OS는 시스템 구성서가 정한다.

구현은 INF-01 → INF-02 → INF-03 · 04 순서로 진행한다. 슬롯이 둘 이상이어야 순차 교체가 성립한다.

**INF-07 ~ 09는 현재 구성(INF-01 ~ 04) 위에 얹는 서버 운영 기반이다** — 네트워크 격리 · 백업 저장소 · 계정 · 정기 작업 · OS 보안. 설계는 서버 운영 기반 설계서(`docs/infra/platform.md`)가 갖는다.

원래는 **Rocky Linux로 옮긴 뒤** 더하기로 했었다(2026-09-19 사용자 결정). **그 전제를 뗀다**(2026-09-23) — 이전에 새 노드가 필요해 지금 할 수 없는데, 셋 중 일부는 이전을 기다리지 않고 지금 노드에서 확인된다. **무엇이 지금 확인되고 무엇이 이전에 매여 있는지는 아래 「환경 제약」 표가 가른다.**

**INF-05(관측)는 범위로 돌아왔다**(2026-09-23 사용자 결정). 2026-09-19에 차기 범위로 뺐던 것을 되살린다. 다만 **노드를 늘릴 수 없어 자체 호스팅을 할 자리가 없다** — 수집기만 이 노드에 두고 지표 · 로그는 밖으로 보낸다. 근거는 인프라 기술 스택 4장.

**INF-06(시험 환경)은 여전히 차기 범위다.** 행은 정의를 보존하려고 남기며 번호를 재사용하지 않는다. 부하 생성기를 둘 노드가 없다.

### 환경 제약 — 노드를 늘릴 수 없다

> **2026-09-25 갱신 — 제약이 풀렸다.** 사용자 본인 계정에 **3노드(APP-01 · DB-01 · DB-02, Rocky 9.8)**를 세우고 서비스를 옮겼다(#233 · #235). 아래 표는 옛 계정 기준의 기록이다. 지금은 — INF-03 **노드 분리 복제가 성립**(DB-01 → DB-02, 다른 AZ, TLS), INF-07 **성립**(사설 서브넷 · APP-01 NAT 겸임 · 보안 그룹 · firewalld · 루프백 게시), INF-08 **NAS를 두지 않는다**(3노드 결정 — 백업 오프사이트는 S3, 자기 NFS 설정 검증은 옛 노드에서 끝났다), INF-09 **세 노드에 같은 기준**(파일시스템 · 계정 UID · SELinux · firewalld · 보안 갱신). 옛 노드는 점검 모드로 남아 있다. INF-04는 **DB 노드 정기 백업 + 논리 백업 S3 사본 · 새 primary의 PITR 리허설까지**(#237). **노드 간 페일오버 · 페일백 리허설도 밟았다**(#239 — DB-01 노드째 정지, 승격 7.3초 · 서비스 복귀 94.4초, 유실 없음). WAL · 물리 백업의 S3 전송은 후속

**공유 계정의 인스턴스 쿼터가 소진돼 새 인스턴스를 만들 수 없고, 쿼터는 풀 수 없다**(2026-09-23 확인). 설계는 다섯 노드를 전제하는데 실제로는 **APP-01 한 대**다.

그래서 아래 표의 여러 항목이 **설계대로는 성립하지 않는다.** 설계를 지우지 않는다 — 노드가 생기면 그대로 쓴다. 대신 **지금 환경에서 어디까지 확인되는지**를 갈라 적는다.

| INF-01 | 요청 분산 · 인스턴스 이중화 | 동일 애플리케이션을 두 프로세스로 구동하고 Nginx가 요청을 분산한다. 한 프로세스가 정지해도 남은 프로세스가 전량을 처리한다. 두 프로세스가 모두 상시 트래픽을 받는 액티브-액티브를 채택한다. 한쪽을 유휴로 두면 그쪽을 정지시켜도 이중화가 동작함을 보일 수 없고, 정작 서빙 중인 쪽이 죽으면 서비스가 중단된다. 애플리케이션이 무상태여야 성립하므로 세션·토큰·캐시를 프로세스 메모리에 두지 않으며, 이 제약은 USER-02(토큰)·NOTI-03(실시간 수신)·RISK-08(배치)의 구현 방식을 직접 규정한다. 사용자에게 노출되는 모든 조회 경로가 의존하며, 특히 메인(서비스 진입점)과 지도 탐색(PROP-02)은 사용자가 가장 먼저 닿는 경로라 중단이 곧 서비스 중단이다. 없으면 프로세스 하나가 죽는 순간 서비스 전체가 정지하고, 배포할 때마다 계획된 중단이 발생한다.<br>검증: 시나리오 1(앱 1대 정지), 2(앱 전체 정지)<br>관련: APP-01, Nginx, Redis | 핵심 |
| INF-02 | 무중단 배포 | 배포 중에도 요청이 끊기지 않으며, 새 버전 기동에 실패해도 서비스 공백이 발생하지 않는다. 두 슬롯을 하나씩 순차 교체하는 롤링 방식이다. 교체 도중 신·구 버전이 같은 데이터베이스를 동시에 보므로 스키마 마이그레이션은 하위 호환이어야 하며, 컬럼 삭제·이름 변경·NOT NULL 추가는 단계를 나눈다. 개발 기간 내내 배포가 반복되므로 매 배포마다 중단이 발생하면 가용성 목표를 달성할 수 없다. 없으면 배포마다 계획된 중단이 발생하고, 서버가 유지하던 연결이 전 사용자에게서 동시에 끊긴다.<br>검증: 시나리오 5(배포 중 요청 유실)<br>관련: Nginx upstream, APP-01 | 핵심 |
| INF-03 | 데이터베이스 복제 | 원본과 같은 내용을 따라 적는 데이터베이스를 하나 더 두고, 원본이 정지하면 승격해 그 자리를 대신한다. **지금 환경에서는 같은 노드 안에서 절차만 검증한다**(위 표). standby는 트래픽을 받지 않고 복제만 수신하며 대기하는 액티브-스탠바이다. 복제는 RTO 수단이지 RPO 수단이 아니다. 비동기이므로 복제 지연만큼의 커밋이 유실될 수 있으며, 손실 허용량은 INF-04가 담당한다. 1등급 기능의 RTO 30분은 복제 없이 달성할 수 없다. 없으면 백업으로부터 복원해야 하므로 복구에 수 시간이 걸린다.<br>검증: 시나리오 3(primary 정지 · 페일백), 8(복제 슬롯 적체)<br>관련: DB-01, DB-02 | 핵심 |
| INF-04 | 백업 및 시점 복구 | 데이터 유실과 논리적 손상으로부터 복원한다. 복구 수단은 실패 유형에 따라 다르며, 특히 논리적 손상은 복제로 복구되지 않는다. 잘못된 UPDATE가 standby에도 동일하게 복제되기 때문이다. 재계산이 가능한 데이터는 복원보다 재생성이 빠르므로 수단을 데이터 성격에 따라 구분한다. USER-03의 자격 정보와 RISK_ANALYSIS의 판정 이력은 외부에서 다시 받아올 수 없다. 없으면 잘못된 UPDATE나 배치 오적재를 되돌릴 방법이 없다.<br>검증: 시나리오 7(논리적 손상 · PITR), 복구 시험 주기<br>관련: DB-01, 오브젝트 스토리지 | 필수 |
| INF-05 | 관측 기반 제공 | 지표와 로그를 수집·저장하고, 시각화하고, 임계값 초과 시 알림을 전달하는 기반을 제공한다. 감시를 두 겹으로 둔다. 지표는 애플리케이션과 서버가 스스로 내보내는 값이므로 정지하면 산출되지 않고, 지표만 보면 오류가 0으로 보인다. 그래서 앱 밖에서 경로를 호출하는 계층을 두되, 그 계층도 관측 스택과 같은 노드에 있어 노드가 통째로 정지하면 감시자와 알림 발송 주체가 함께 사라진다. 노드 밖에 한 겹을 더 두어 관측 스택이 침묵하는 경우를 담당하게 하며, 바깥 계층은 알림을 자체 경로로 보내 내부 알림 체계를 거치지 않는다. 전 서비스 기능과 다른 모든 INF 항목이 이 기능에 의존한다. 없으면 다른 인프라 기능을 만들어도 동작 여부를 확인할 수 없다.<br>검증: 전 시나리오. 관측이 없으면 어떤 시험도 판정할 수 없다.<br>관련: APP-01, DB-01, DB-02 | 핵심 |
| INF-07 | 네트워크 격리 · 접근 통제 | 인터넷에서 닿는 노드를 APP-01 하나로 줄인다. DB · NAS는 공인 주소가 없는 사설 서브넷에 두고, 밖으로 나가는 길은 NAT 인스턴스 하나로 모은다. 접근 통제는 보안 그룹 · 호스트 방화벽 · 컨테이너 포트의 루프백 바인딩 세 겹이다. 운영자는 APP-01을 경유해 SSH 공개키로만 들어간다. 네트워크 이중화는 NIC 티밍이 아니라 가용 영역 분산과 Elastic IP 재지정으로 한다(본인 계정 3노드는 Elastic IP를 쓰지 않는다 — 사용자 결정 2026-09-25, 서버 운영 기반 설계서 3.5) — EC2는 NIC를 묶어 대역폭 · 링크를 이중화할 수 없다. 없으면 보안 그룹 설정 실수 하나가 곧 데이터 저장소 노출이 된다.<br>관련: VPC, 보안 그룹, firewalld, NAT-01 | 핵심 |
| INF-08 | 백업 저장소(NAS) | 백업을 한곳에 모으는 NFS 서버를 둔다. DB 논리 백업(일 1회)과 운영 설정 사본이 여기에 쌓이고, 주 1회 오프사이트(S3)로 사본을 보낸다. 물리 백업 + WAL(INF-04)은 시점 복구용, NAS의 논리 백업은 테이블 단위 복원 · 이전용이라 서로를 대체하지 않는다. 없으면 백업이 각 노드 디스크에 흩어져, 그 노드가 사라질 때 백업도 함께 사라진다.<br>관련: NAS-01, NFS, INF-04 | 핵심 |
| INF-09 | 서버 운영 기반 | 파일시스템(데이터 볼륨 분리) · 계정(개인 계정 · 역할 계정 · UID 고정) · 정기 작업(systemd timer) · OS 보안(SELinux · 보안 갱신 · 시간 동기화)을 전 노드에 같은 기준으로 둔다. 정기 작업의 성공 · 실패는 저널에 남긴다. **저널을 관측으로 거두는 경로는 미확정이다** — 정해진 로그 원천에 저널이 없다. 관측 착수(로드맵 6주차)에 정한다. 없으면 노드마다 설정이 달라지고, 디스크가 차거나 백업이 조용히 멈춰도 알 수 없다.<br>관련: 전 노드 | 핵심 |
| INF-06 | 시험 환경 제공 (시험) | 부하를 생성할 별도 노드와, 장애를 주입할 수 있는 대상 환경을 제공한다. 부하 생성기는 측정 대상 밖에 있어야 한다. 같은 노드에 두면 생성기가 쓰는 자원만큼 한계가 과소 측정되고, 포화 구간에서는 생성기도 자원을 받지 못해 목표 부하를 인가하지 못한다. 검증에만 필요하며 서비스 동작에는 관여하지 않는 유일한 항목이다. 없으면 측정값이 시스템의 성능이 아니게 된다.<br>검증: 해당 없음. 검증 수단 자체다.<br>관련: APP-02 | 핵심 → **차기 범위** |
