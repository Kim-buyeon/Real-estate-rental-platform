## 1. 테스트 전략

리뷰어가 없는 1인 개발에서는 테스트가 품질을 확인하는 유일한 수단이다. 또한 AI 코딩 에이전트를 활용해 개발하므로, 생성된 코드가 의도대로 동작하는지 기계적으로 판별할 기준이 반드시 필요하다. 테스트는 부가 작업이 아니라 개발 절차의 일부로 둔다.

### 1.1 계층별 테스트

| 구분 | 도구 | 대상 및 방침 |
| --- | --- | --- |
| 단위 테스트 | JUnit 5 + AssertJ | 위험 등급 판정, 깡통전세 계산, 보증보험 3사 가입 판정, LTV·DSR·Stress DSR 한도 산출을 검증한다. 외부 의존이 없는 순수 계산 로직이므로 데이터베이스 없이 수행한다.<br>판정 로직은 구현 전에 기대값 표를 먼저 작성하고 그에 맞춰 테스트를 정의한다. |
| 매퍼 테스트 | JUnit 5 + Testcontainers | MyBatis 매퍼는 컴파일 시점 검증이 없으므로, 실제 데이터베이스에 질의해 컬럼명과 문법 오류를 차단한다. 매퍼 메서드 추가와 동일 단위로 작성한다. |
| 통합 테스트 | Spring Boot Test<br>+ Testcontainers | 실제 PostgreSQL 컨테이너를 기동해 Flyway 마이그레이션부터 조회까지 전 경로를 검증한다. H2를 사용하면 방언 차이로 통과와 실패가 어긋날 수 있어 사용하지 않는다. |
| 외부 연동 테스트 | Mock · Fault 구현체 | 외부 API 클라이언트는 인터페이스로 분리되어 있으므로 구현체로 대체한다. Mock은 항상 동일한 정상 응답을 반환해 네트워크 상태와 무관한 결과를 보장하고, Fault는 지연·오류·타임아웃을 반환해 서킷 차단과 대체 응답 경로를 검증한다. |
| 다중 인스턴스 테스트 | Spring Boot Test<br>+ Testcontainers | 애플리케이션을 두 개 기동한 상태에서만 드러나는 결함을 검증한다. 토큰 회전(USER-02), SSE 이벤트 팬아웃(NOTI-03), 배치 분산 락(RISK-08)이 대상이다. 단일 인스턴스에서는 모두 통과하므로 이중화 이후에 발견하면 세 기능을 다시 작성해야 한다. |
| 부하 테스트 | k6 | 포화점 실측과 성능 개선 조치의 전후 비교에 사용한다. 상세 방침은 성능 및 확장성 문서를 따른다. |
| 배포 검증 | k6 + 배포 스크립트 | 슬롯 순차 교체 중 요청 손실이 0건인지 확인한다. 정상 부하를 유지한 상태에서 배포를 실행한다. 부하 없이 배포하면 무중단 여부를 셀 수 없다. |
| 장애 주입 시험 | 주입 스크립트 + Prometheus | 앱·데이터베이스·Redis 정지, 디스크 임계, 복제 슬롯 적체 등 시나리오 9종을 실행하고 기대 동작과 실제 동작을 대조한다. 목적은 통과가 아니라 설계와 현실의 차이를 찾는 것이다. |
| 복구 시험 | 백업 복원 · WAL 재생 | 시점 복구(PITR)와 승격 절차가 실제로 동작하는지 확인한다. 복구는 문서로 보장되지 않으므로 주기적으로 실행한다. |

### 1.2 운영 규칙

- Testcontainers는 개발 환경에 이미 Docker가 전제되므로 추가 설치 비용이 없다. 통합 테스트의 기본 실행 환경으로 삼는다.
- 판정 로직과 한도 계산은 경계값을 포함한 케이스 표를 근거로 검증한다. 임의의 예시 하나로 통과 여부를 판단하지 않는다.
- 매퍼 메서드와 그 테스트는 같은 변경 단위에 포함한다. 테스트 없는 매퍼는 검증되지 않은 코드로 간주한다.
- 빌드와 테스트는 지속적 통합에서 자동 실행하며, 실패한 상태를 기본 브랜치에 남기지 않는다.
- 장애 주입과 배포 검증은 배경 부하 위에서 실행한다. 부하가 없으면 정지시켜도 아무 일이 일어나지 않아 시험이 성립하지 않는다.
- 부하 생성기는 측정 대상과 같은 노드에 두지 않는다. 자원을 나눠 쓰면 측정값이 시스템의 성능이 아니게 된다.
- 시험 중 발견한 문제를 그 자리에서 고치지 않는다. 코드를 고치면 이후 결과가 앞선 결과와 비교 불가능해진다. 기록하고 별도 작업으로 분리한다.
