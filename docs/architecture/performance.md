## 1. 성능 및 확장성 설계

트래픽 증가 상황을 가정하고 병목 지점을 사전에 식별한다. 본 서비스의 부하는 두 축에서 발생한다. 하나는 매물 검색·목록 조회의 데이터베이스 부하이고, 다른 하나는 위험도 분석 시 발생하는 외부 API 호출 지연이다. 후자가 응답 시간에 미치는 영향이 더 크다.

### 1.1 병목별 대응 방안

| 병목 | 대응 |
| --- | --- |
| 외부 API 응답 지연 | 가상 스레드 기반 병렬 호출로 등기·대장·시세 조회를 동시에 수행한다. 조회 결과는 Redis에 캐싱하여 동일 매물 재조회 시 외부 호출을 발생시키지 않는다. 원본 데이터의 갱신 주기가 길어 캐시 유효 기간을 넉넉히 설정할 수 있다. |
| 매물 목록 조회 | 자치구·계약유형·보증금 범위에 대응하는 복합 인덱스를 설계하고 실행 계획으로 검증한다. 목록에 필요한 컬럼만 조회하여 불필요한 데이터 전송을 줄인다. |
| 깊은 페이지네이션 | OFFSET 방식은 뒤쪽 페이지에서 비용이 선형 증가하므로, 마지막 조회 지점을 기준으로 하는 커서 방식을 적용한다. |
| 연관 엔티티 반복 조회 | 조회 경로를 MyBatis로 단일화하여 목록 조회에서 N+1 문제가 구조적으로 발생하지 않도록 한다. JPA 사용 구간에는 페치 조인과 배치 크기를 설정한다. |
| 통계 실시간 집계 | REGION_STATS를 사전 집계 테이블로 운용한다. 요청 시점에 원본 데이터를 집계하지 않고 배치가 산출한 결과를 조회한다. 설계 단계에서 이미 반영된 구조다. |
| 알림 발송 지연 | 판정 결과 확정과 알림 발송을 분리한다. 애플리케이션 이벤트로 발행하고 비동기로 처리하여 주 트랜잭션의 응답 시간에 포함되지 않도록 한다. |
| 동시 요청 중복 처리 | 위험도 재분석 등 동일 자원에 대한 중복 실행은 분산 락으로 차단한다. |
| 커넥션 고갈 | 커넥션 풀 크기와 타임아웃을 명시적으로 설정한다. 조회 전용 트랜잭션에는 읽기 전용 속성을 지정한다. 풀 대기 상한을 넘거나 질의가 시간 제한으로 취소되면 500 이 아니라 503 `SERVICE_BUSY` 로 응답해 버그(500)와 구분하고 클라이언트가 다시 시도하게 한다. 앞단은 503 을 다른 슬롯으로 넘기지 않는다 — 503 을 슬롯 실패로 세면 공용 DB 가 바쁠 때 슬롯 넷이 함께 빠진다(#402). 시간 제한의 값과 근거는 1.4. |
| 암호화 비용 | HTTPS 핸드셰이크 · 비밀번호 해싱 · JWT 검증 · 컬럼 암 · 복호화가 노드마다 CPU를 쓴다. 알고리즘 · 파라미터는 보안 하한 위에서 비용이 가장 작은 것을 측정으로 고른다 — 보안 · 암호화 설계서, 시험 계획서 9장 |
| 로그인 몰림(비밀번호 해싱) | 해싱 비용은 보안 하한이 막아 낮추지 않고, **슬롯마다 해시 · 대조의 동시 실행 수를 묶어** 넘치면 짧게 기다린 뒤 503 `SERVICE_BUSY` 로 돌려보낸다 — 로그인이 몰려도 같은 슬롯의 다른 요청이 CPU를 다 뺏기지 않게 한다(#390 R05 — 로그인 몰림 p95 3.6 s · 앱 CPU 95 %, #408). 앞단은 로그인 경로에 IP별 상한을 따로 둔다. 방식은 보안 · 암호화 설계서 4.2, 값은 설정 파일(앱 `auth.password-hashing` · 앞단 서버 블록) |

### 1.2 검증 방법

성능 개선은 수치로 확인한다. 개선 조치를 적용하기 전에 부하 테스트로 기준값을 먼저 측정하고, 적용 후 동일 조건에서 재측정하여 비교한다.

| 도구 | 용도 |
| --- | --- |
| k6 | 매물 검색·위험도 조회 시나리오의 처리량과 응답 시간 분포를 측정한다 |
| Spring Boot Actuator<br>+ Micrometer | 메서드 실행 시간, 캐시 적중률, 커넥션 풀 사용량을 지표로 노출한다 |
| 실행 계획 분석 | 느린 쿼리를 식별하고 인덱스 적용 전후의 비용을 비교한다 |
| p6spy 또는 쿼리 로깅 | 개발 단계에서 실제 발생 쿼리 수와 내용을 확인한다 |

측정 대상 지표는 응답 시간 95백분위수, 초당 처리량, 요청당 쿼리 수, 캐시 적중률로 한다. 개선 항목별로 적용 전후 수치를 기록하여 근거를 남긴다.

### 1.3 범위 한정

**애플리케이션은 두 인스턴스로 운용한다**(INF-01). 세션을 서버에 보관하지 않고 캐시와 락을 외부 저장소에 두는 것은 선택이 아니라 그 전제다 — 두 인스턴스가 같은 상태를 보아야 한다. 데이터베이스 샤딩과 메시지 브로커 도입은 현재 요구 수준을 넘어서므로 적용하지 않는다. 데이터베이스 복제는 인프라 구간(INF-03)이 다루고, **standby 읽기 분산**은 앱이 데이터 소스를 둘(primary · 읽기용) 두고 표시(`@ReplicaRead`)한 지도 · 목록 · 구별 집계 조회만 읽기용으로 보낸다(기본 끔, #343) — 근거는 운영 측정 #342(지도 쿼리가 동시 2 부터 DB-01 CPU 100% · 약 13 TPS 에서 멈추고, 반반 나누면 처리량 2배 · 지연 절반). 구조는 영속성 설계서 1.1.

**예외 — 판정 기준표는 슬롯 메모리에 둔다(#399).** 위험도 판정 기준(보증 기준 · HF · SGI · 보증료율 · 보증 상품 · 위험 등급 기준)과 대출 한도 기준(최신 대출 규제 · 매물 유형별 대표 대출 상품)을 슬롯마다 한 벌씩 든다. 캐시는 둘(위험도 기준 · 대출 기준)이고 버전 키 하나를 함께 쓴다 — 어느 쪽이 바뀌어도 키를 올리고, 키가 바뀌면 둘 다 다시 읽는다. 이 표들은 관리자 수정과 월 1회 금리 갱신으로만 바뀌는데 위험도 · 대출 요청마다 읽혔다 — 2026-10-04 부하 시험(#390)에서 요청당 SQL 이 위험도 17 · 대출 22 였다(저장된 판정 반환과 함께 줄이는 대상). Redis 에 통째로 두면 요청마다 Redis 왕복이 남아 이 전제를 따르지 않는다.

전제가 지키려는 것은 「두 인스턴스가 같은 상태를 본다」이므로, 슬롯 로컬 캐시에는 변경을 전 슬롯에 알리는 무효화 경로가 있어야 한다([Distributed Cache Invalidation Patterns](https://foojay.io/today/distributed-cache-invalidation-patterns/), [Solving the Distributed Cache Invalidation Problem with Redis and HybridCache](https://www.milanjovanovic.tech/blog/solving-the-distributed-cache-invalidation-problem-with-redis-and-hybridcache)). 여기서는 이렇게 둔다.

| 부분 | 방식 | 이유 |
| --- | --- | --- |
| 변경 알림 | 기준을 바꾼 쪽이 **커밋 뒤** Redis 버전 키(`criteria:version`)를 올리고 자기 슬롯을 비운다 | 커밋 전에 알리면 다른 슬롯이 옛 값을 다시 읽어 든다 |
| 변경 감지 | 각 슬롯의 반복 작업이 짧은 간격으로 버전 키를 읽어 바뀌었으면 다시 읽는다 | 요청마다 확인하면 Redis 가 느릴 때 모든 위험도 요청이 기다린다. 발행 · 구독은 끊긴 동안 온 메시지를 잃는다 — 버전 키는 이어진 뒤 다음 확인에서 잡는다 |
| 안전망 | 버전 키와 무관하게 긴 간격마다 다시 읽는다 | Redis 장애로 버전 키를 못 올린 변경도 이 간격 안에 따라온다. 이 간격이 슬롯 사이에 기준이 어긋날 수 있는 상한이다 |
| 요청 경로 | Redis 를 부르지 않는다. 비어 있으면 DB 에서 읽는다. 예외 하나 — 저장된 판정의 기준 지문이 지금 캐시의 지문과 다르면 다시 판정하기 전에 버전 키를 한 번 확인한다(슬롯당 확인 간격에 한 번, 다른 확인이 진행 중이면 건너뜀, Redis 실패면 그대로 진행) | 다른 슬롯이 새 기준으로 적은 판정을 옛 기준을 든 슬롯이 다시 판정해 덮는 왕복을 변경 감지 간격만큼 줄인다 |

간격 값과 그 근거는 설정 파일(`risk.criteria-cache`)이 갖는다. 이 예외는 판정 기준표에만 해당한다. 다른 캐시와 락 · 세션은 전제대로 외부 저장소에 둔다.

### 1.4 세션 시간 제한

앱이 쓰는 데이터베이스 커넥션(쓰기 노드 풀 · 읽기용 풀)에만 건다(#402). 값과 근거는 이 절이 정하고, 설정 파일(`spring.datasource.hikari.data-source-properties`)이 그 값을 적용한다. 넘어 취소된 질의는 503 `SERVICE_BUSY`다(API 공통 명세 2장).

| 설정 | 값 | 근거 |
| --- | --- | --- |
| `statement_timeout` | 30초 | 앞단이 응답을 기다리는 상한(`proxy_read_timeout` 30초, 운영 절차서 4.2)과 같다 — 그 뒤의 응답은 받을 쪽이 없으므로 DB 에서도 끊어 커넥션과 CPU 를 돌려받는다. 실측 최장은 한참 아래다: 사용자 질의 975 ms(2026-10-04 부하 시험 R04, `pg_stat_statements`), 배치 질의 약 0.55초(#334 · #338). 더 짧게(예: 5초) 두지 않은 것은 그 값을 받칠 측정이 없어서다 |
| `idle_in_transaction_session_timeout` | 60초 | 트랜잭션을 연 채 문장 없이 머문 세션을 서버가 끊는다. 유휴 구간은 잰 적이 없다(#334 보류 사유) — 쓰기 트랜잭션 안의 자바 처리(GC · 과부하에서 수 초)보다 한 자리 크게 둔다. 외부 호출은 트랜잭션 밖에서 하므로 정상 경로에 오래 머물 자리가 없다 |

| 어디에 걸지 않는가 | 이유 |
| --- | --- |
| 서버 전역(`-c`) · 계정(`ALTER ROLE`) | 같은 계정의 운영자 수작업(`CREATE INDEX CONCURRENTLY` 등) · `pg_basebackup` 에도 걸린다 |
| 마이그레이션(Flyway) | 큰 표의 인덱스 · 열 변경은 30초를 넘을 수 있고, 넘으면 기동이 실패한다. Flyway 는 앱 풀 밖의 자기 커넥션으로 돌고 세션 값을 0 으로 연다(실측 최장 V19 916 ms). 앱 풀을 빌린 채 0 으로 SET 하면 그 커넥션이 풀로 돌아가 앱 요청이 시간 제한 없는 세션을 받는다 |
