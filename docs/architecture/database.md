# 전월세 부동산 금융 플랫폼 — 데이터베이스 설계서

> 엔티티 · 속성 · 관계 정의 (PostgreSQL 기준)
> 총 30개 테이블
> 매물 조회 · 위험도 분석 · 대출 추천 · AI 상담 · 실시간 알림
> 작성 기준일 : 2026년 8월

---

## 1. 설계 개요

본 데이터베이스는 서울시 전월세 실수요자를 위한 부동산 금융 플랫폼을 지원한다. 매물 탐색부터 전세 위험도 분석, 맞춤형 대출 추천 및 계획 수립, AI 상담, 실시간 알림까지 5가지 핵심 기능을 총 30개의 테이블로 구성한다. 모든 PK는 IDENTITY 컬럼(BIGINT GENERATED BY DEFAULT AS IDENTITY)으로 채번하며, 계산·판정 로직은 애플리케이션에서 수행하고 DB에는 결과만 저장한다.

- 코드성 엔티티 — PROPERTY_CODE — 계약 유형·매물 유형·매물 상태를 공통 코드로 관리
- 이력성 엔티티 — OWNERSHIP_HISTORY(갑구)·MORTGAGE_HISTORY(을구)·RISK_ANALYSIS·INTEREST_RATE_HISTORY — 변경 이력 누적
- 슈퍼타입-서브타입 — GUARANTEE_CRITERIA + HUG/HF/SGI_CRITERIA(보증보험), NOTIFICATION + 4개 하위(알림) — 배타적 1:0..1
- 보증료율 분리 — GUARANTEE_PREMIUM_RATE — 주택유형·부채비율 구간별 요율을 별도 관리
- 위험 판정 중심 — RISK_ANALYSIS — 보증보험 가입 가능 여부(3사)로 안전 판정, 대출 추천의 전제

## 2. 엔티티 관계 요약

전체 40개 관계의 카디널리티·필수 여부·식별 유형을 정의한다. DA# 관계 편집 시 '필수' 체크박스 입력에 대조하여 사용한다.

필수: ● 필수(자식이 부모 없이 존재 불가) / ○ 선택(FK NULL 허용).  식별: 식별(부모 PK가 자식 PK 일부) / 비식별(일반 FK).  1:0..1은 배타적 서브타입.

## 4. 식별자 설계 원칙

본 설계는 각 엔터티의 식별자를 결정할 때, 먼저 업무적 본질 식별자(자연 식별자)를 분석한 뒤 물리 설계 단계에서 인조 식별자(IDENTITY)로 전환하는 정통 절차를 따랐다. 자연 식별자를 PK 자리에서 배제하는 것이 아니라, UNIQUE 제약으로 보존하여 고유성은 그대로 보장한다.

### 4.1 식별자 결정 절차

- 1단계 — 자연 식별자 분석 — 각 엔터티가 업무적으로 무엇으로 식별되는지(본질 식별자)를 먼저 도출한다.
- 2단계 — 인조 식별자 전환 — 자연 식별자가 복합키이거나 변경 가능성이 있는 경우, 물리 설계에서 IDENTITY 기반 단일 인조키로 전환한다.
- 3단계 — 자연 식별자 보존 — 전환 후에도 자연 식별자는 UNIQUE 제약으로 명시하여 데이터 고유성을 DB가 강제하도록 한다.

### 4.2 인조 식별자 전환의 근거

- 변경 불변성: 인조키는 업무적 의미가 없어 영구 불변이다. 자연키(provider 코드, 행정구역 등)는 제도 변화로 바뀔 수 있으며, PK 변경은 이를 참조하는 모든 FK의 연쇄 수정을 유발한다.
- FK 단순화: 복합 자연키를 PK로 두면 이를 참조하는 모든 자식 테이블이 복합 FK를 가져야 하고 조인 조건도 복잡해진다. 단일 인조키는 FK와 조인을 단순하게 유지한다.
- 일관성: 모든 엔터티가 단일 IDENTITY PK로 통일되어 ORM 매핑·쿼리·유지보수가 예측 가능해진다.

### 4.3 자연 식별자 보유 엔터티

전체 30개 엔터티 중 명확한 자연 식별자를 가진 4개 엔터티는 아래와 같다. 이들은 인조키(PK)와 자연키(UNIQUE)를 함께 보유한다. 나머지 26개 엔터티는 업무적 고유 식별자가 없어 인조키만 사용한다.

| 엔터티 | 인조 식별자 (PK) | 자연 식별자 (UNIQUE) |
|---|---|---|
| GUARANTEE_CRITERIA | guarantee_id | provider (HUG/HF/SGI 기관명) |
| PROPERTY_CODE | code_id | code_group + code_value |
| REGION_STATS | stat_id | district + contract_type + stat_date |
| USER_AUTH | auth_id | auth_type + provider_id |

※ 예: GUARANTEE_CRITERIA는 provider가 본질 식별자이나, 이를 참조하는 RISK_ANALYSIS·서브타입의 FK 단순화를 위해 guarantee_id(IDENTITY)를 PK로 두고 provider는 UNIQUE로 고유성을 보장한다.

## 5. 키 표기 안내

- PK : 기본 키 (Primary Key) — IDENTITY 컬럼으로 채번
- FK : 외래 키 (Foreign Key)
- UQ : 고유 제약 (Unique)

## 6. PostgreSQL 적용 규약

본 설계서의 데이터타입은 PostgreSQL을 기준으로 표기한다. 물리 구현 시 아래 규약을 따른다.

- 식별자 채번 — 모든 PK는 BIGINT GENERATED BY DEFAULT AS IDENTITY로 정의한다. 별도 시퀀스 객체를 수동으로 생성하지 않는다.
- 문자열 — VARCHAR(n)은 표기된 길이를 그대로 적용한다. 길이 제한이 불필요한 장문 항목은 TEXT를 사용한다.
- 수치 — 금액은 BIGINT, 비율·좌표 등 소수 자릿수가 필요한 항목은 NUMERIC(정밀도, 소수점)을 사용한다. 금액·이율 연산에 부동소수점 타입을 사용하지 않는다.
- 일시 — TIMESTAMP를 사용하며 기본값은 now()로 지정한다. 애플리케이션과 데이터베이스의 시간대를 Asia/Seoul로 일치시킨다.
- 논리값 — BOOLEAN을 사용한다. 별도의 문자·숫자 대체 표기를 두지 않는다.
- 열거형 — 권한, 상태, 등급 등 고정된 값 집합은 VARCHAR로 저장하고 애플리케이션에서 열거 타입으로 다룬다. 데이터베이스 고유 열거 타입을 사용하지 않으며, 저장 값은 열거 상수명과 동일하게 유지한다.
- 식별자 표기 — 테이블명과 컬럼명은 소문자 스네이크 표기로 생성한다. 본 문서의 대문자 표기는 가독성을 위한 것이다.
- 스키마 형상 관리 — 모든 DDL은 마이그레이션 스크립트로 관리하며 데이터베이스에 직접 실행하지 않는다.
