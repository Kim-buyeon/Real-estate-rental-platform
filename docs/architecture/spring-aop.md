## 1. 횡단 관심사 설계 (AOP)

로깅·성능 측정·캐싱·동시성 제어처럼 여러 도메인에 공통으로 걸리는 처리는 비즈니스 코드에 섞지 않고 관점(Aspect)으로 분리한다. 판정 로직이 프로젝트의 핵심인 만큼, 서비스 계층에 부가 관심사가 침투하지 않도록 유지하는 것이 목표다.
Spring이 이미 트랜잭션·보안·캐시를 프록시 기반 AOP로 처리하고 있으므로, 본 프로젝트는 그 위에 도메인 특성에 맞는 관점을 추가로 정의한다.

### 1.1 정의할 관점

| 관점 | 적용 대상 | 역할 및 도입 사유 |
| --- | --- | --- |
| 실행 시간 측정 | 서비스·매퍼 계층 | 판정·집계 메서드의 수행 시간을 지표로 수집한다. 성능 개선의 전후 비교 근거를 코드 수정 없이 확보하기 위함이다. |
| 외부 API 호출 로깅 | 외부 연동 클라이언트 | 요청·응답·소요 시간·실패 사유를 일괄 기록한다. 연동 대상이 여럿이므로 클라이언트마다 로깅 코드를 반복하지 않는다. |
| 호출량 제어 | 외부 연동 클라이언트 | 일일 호출 한도가 있는 공공 API의 사용량을 집계하고 임계치 초과 시 캐시 응답으로 대체한다. |
| 분산 락 | 위험도 재분석,<br>알림 생성 | 동일 매물에 대한 재분석이 배치와 사용자 요청에서 동시에 발생하면 중복 이력과 중복 알림이 생성된다. Redis 기반 락으로 단일 실행을 보장한다. |
| 조회 이력 기록 | 매물·위험도 조회 | SEARCH_HISTORY 적재를 서비스 로직에서 분리한다. 부가 기능이 주 로직의 트랜잭션에 영향을 주지 않도록 한다. |
| 예외 변환 | 컨트롤러 진입점 | 도메인 예외를 API 응답 규격으로 일관되게 변환한다. |

### 1.2 적용 원칙

- 관점은 부가 관심사에만 적용한다. 위험 등급 판정, 대출 한도 계산 등 도메인 규칙은 관점으로 옮기지 않는다. 흐름이 코드에서 보이지 않게 되면 검증과 디버깅이 어려워진다.
- 프록시 기반 AOP의 제약을 전제한다. 같은 클래스 내부 호출과 private 메서드에는 적용되지 않으므로, 관점을 적용할 지점은 별도 빈으로 분리한다.
- 포인트컷은 패키지 표현식이 아닌 애노테이션 기준으로 정의한다. 적용 범위가 코드에 명시되어 의도가 드러난다.
- 관점 내부에서 발생한 예외가 주 로직에 전파되지 않도록 격리한다. 이력 적재 실패가 매물 조회 실패로 이어져서는 안 된다.
