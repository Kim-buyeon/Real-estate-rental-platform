## 1. 개발 환경 및 구현 리스크

### 1.1 로컬 개발 환경 구성

데이터베이스와 캐시는 호스트에 설치하지 않고 컨테이너로만 운용한다. 개발 시작 절차를 명령 한 줄로 고정해, 환경 차이에서 오는 문제를 원천 차단한다.

| 구성 요소 | 이미지 | 용도 및 비고 |
| --- | --- | --- |
| PostgreSQL | postgres:17-alpine | 명명 볼륨에 데이터 보존. 헬스체크 설정으로 기동 완료 여부 확인 |
| Redis | redis:7-alpine | 캐시 및 토큰 저장 |
| DB 클라이언트 | 호스트에 설치 | DBeaver 등으로 컨테이너에 접속. 컨테이너 내부에 별도 관리 도구를 두지 않는다 |

운용 규칙
- 로컬 호스트에 PostgreSQL·Redis를 직접 설치하지 않는다. 포트 충돌과 버전 혼선의 주된 원인이다.
- 스키마 생성과 변경은 Flyway 마이그레이션으로만 수행한다. 클라이언트 도구에서 DDL을 직접 실행하지 않는다.
- 스키마를 초기 상태로 되돌릴 때는 볼륨까지 삭제 후 재기동한다. 초기 개발 단계에서는 이 절차가 가장 빠르고 안전하다.
- 접속 정보는 환경 변수로 주입한다. 배포 환경 전환 시 애플리케이션 코드 변경이 발생하지 않도록 한다.
- docker-compose.yml은 저장소 루트에 두고 형상 관리한다.

### 1.2 구현 리스크와 대응

| 리스크 | 대응 |
| --- | --- |
| Spring Boot 4 계열은 공개된 예제·문서가 3.x 대비 적어, AI 코딩 에이전트가 3.x 문법을 생성할 가능성이 높다 | 프로젝트 규칙 파일에 사용 금지 문법을 명시하고, 컴파일과 테스트를 매 작업 후 실행하는 검증 루프를 강제한다 |
| MyBatis는 컴파일 시점 검증이 없어 컬럼명 오타가 런타임까지 전달된다 | 매퍼 단위 테스트를 필수로 하고, 엔티티와 스키마 정합성은 ddl-auto validate로 기동 시점에 차단한다 |
| JPA와 MyBatis 병행 시 동일 트랜잭션 안에서 변경 사항이 조회에 반영되지 않을 수 있다 | MyBatis 매퍼를 조회 전용으로 제한하고, 필요한 경우 조회 직전 flush를 수행하거나 읽기·쓰기 트랜잭션을 분리한다 |
| 등기부등본 실데이터 확보 불가 | 인터페이스 분리 + Mock 구현. 판정 로직 검증은 고정 테스트 케이스로 수행한다 |
| 시세(market_price) 출처 신뢰도 | 실거래가 평균 또는 공시가격으로 대체하고, price_type·price_date 컬럼에 산출 근거를 기록해 화면에 노출한다 |
| 보증보험 기준·대출 규제 수치의 잦은 변경 | 코드 하드코딩 없이 GUARANTEE_CRITERIA·LOAN_REGULATION 테이블로 관리한다. 초기에는 시드 데이터로 적재하고, 기준 데이터 관리 기능이 구현되면 그 경로로 갱신한다 |
| 외부 API 호출 한도 초과 | Redis 캐시와 배치 수집으로 실시간 호출을 최소화한다 |
| 알림 발송 실패나 지연이 판정 결과 저장 또는 사용자 요청 처리에 영향을 줄 수 있다 | 알림 생성과 발송을 분리하고, 발송은 트랜잭션 커밋 이후 비동기로 처리한다. 이력 저장 성공을 기준으로 판단한다 |
| 실시간 연결이 끊긴 사용자가 알림을 받지 못할 수 있다 | 알림 목록은 조회 API로도 완전하게 제공하고, 실시간 연결은 즉시성을 높이는 보조 수단으로만 사용한다 |
| 배치와 사용자 요청에서 동일 알림이 중복 생성될 수 있다 | 캐시 기반 중복 방지 키와 분산 락을 함께 적용한다 |
| 관점을 과도하게 적용하면 실행 흐름이 코드에서 드러나지 않아 디버깅이 어려워진다 | 부가 관심사로 적용 범위를 한정하고, 애노테이션 기준 포인트컷으로 적용 지점을 코드에 명시한다 |
| TanStack Query는 공개된 예제에 v4 문법이 다수 남아 있어 v5와 혼용될 수 있다 | 프로젝트 규칙 파일에 v4에서 변경된 항목을 명시하고, 타입 검사로 기동 전에 차단한다 |
| 성능 개선 조치가 실제 효과가 있었는지 확인되지 않을 수 있다 | 조치 전 기준값을 부하 테스트로 먼저 측정하고, 동일 조건에서 재측정하여 항목별로 수치를 기록한다 |
