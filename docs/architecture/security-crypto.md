# 전월세 부동산 금융 플랫폼 — 아키텍처 설계서 — 보안 · 암호화

> 무엇을 왜 암호화하고, 알고리즘을 무엇으로 고르는가 — **보안 하한 · CPU 비용 · 가용성 위협**을 함께 본다
> 입구(HTTPS) · 앱(비밀번호 해싱 · JWT 서명) · DB(컬럼 암호화) · 인프라(키 · 인증서)
>
> ※ 시험 방법 · 판정 기준은 시험 계획서 9장, 부하 시험 결과는 용량 산정 리포트, 노드 구성은 시스템 구성서 · 서버 운영 기반 설계서를 따른다.
> 작성 기준일 : 2026년 9월 27일 · **구현 전 설계다 — 알고리즘 · 파라미터는 모두 후보이고 측정으로 확정한다(8장)**

## 1. 원칙

- **선택 순서는 보안 하한 → 비용이다.** 법령 · 표준이 정한 하한(3장 · 각 절의 「보안 하한」)을 넘는 후보만 남기고, 그중 **CPU · 메모리 비용과 가용성 위협이 가장 작은 것**을 실측으로 고른다. 하한 아래는 비용이 작아도 고르지 않는다.
- **네 계층을 함께 본다.** 암호화는 CPU를 쓰므로 그 자체로 처리 한계(포화점 — 용량 산정 리포트)를 낮춘다. 각 계층에서 어떤 노드의 CPU가 늘고 무엇이 가용성을 위협하는지를 5장에 적는다.
- **대칭 암호 알고리즘끼리의 차이는 작다고 가정하고 확인한다.** AES는 하드웨어 명령(AES-NI)으로 처리되어 수십 바이트 필드의 암 · 복호화는 질의 한 번(수 ~ 수십 ms)에 비해 무시할 만하다는 것이 가설이다. **CPU를 크게 가르는 것은 알고리즘보다 설계**(무엇을 암호화하는가 · 어디서 푸는가 · 인덱스를 잃는가)와 **의도적으로 느린 연산**(비밀번호 해싱 · TLS 핸드셰이크 서명)이다. 가설은 벤치마크로 확인한다(시험 계획서 9장).
- **확정 전 값은 미확정으로 둔다.** 이 문서의 「후보」는 측정 뒤 「확정」으로 바꾸고 근거(측정 회차)를 함께 적는다.
- 운영 결정(2026-09-27 사용자) — 이 작업은 기능 코드 동결의 **예외**다(로드맵 5장 판정 지점 표). 키는 **노드 `.env`**, HTTPS 인증서는 **Let's Encrypt IP 인증서**(무료). 비용이 드는 대안은 7장.

## 4. 영역별 방침

### 4.1 HTTPS — 입구(APP-01 앞단 Nginx)

| 항목 | 후보 | 보안 하한 | 비용 가설 |
|---|---|---|---|
| 인증서 키 | **확정 — ECDSA P-256**(RSA 2048 대비) | [Mozilla TLS 권장 v6.0](https://ssl-config.mozilla.org/guidelines/latest.json) intermediate — ECDSA(prime256v1 · secp384r1) 또는 RSA 2048 | **가설 확인** — 서명 단위 40,410 대 1,488회/초(27배, APP-01 OpenSSL 3.5.8 · 1코어). 서비스에서는 새 연결 400/초에 APP-01 CPU 48.7 % 대 65.9 %(HTTP 28.1 %) — 핸드셰이크 한 번의 추가 CPU 약 1.0 대 1.9 ms(키 교환 등 서명 밖 비용이 섞여 차이가 27배보다 작다). RSA 는 400/초에서 p95 10.3 ms(ECDSA 2.3 ms). 근거: 용량 산정 리포트 C-2 |
| TLS 버전 | **확정 — 1.2 + 1.3(intermediate)** | 같은 문서 | 요즘 클라이언트는 1.3 으로 협상한다(밖에서 `openssl s_client` 기본 — TLSv1.3 · h2, `-tls1_2` 강제도 협상된다 — 용량 산정 리포트 C-2). 1.3만으로 좁혀 얻는 비용 이득이 측정되지 않고 오래된 클라이언트만 잃는다 |
| 암호군 | 위 문서의 목록 그대로 | AEAD만(GCM · ChaCha20-Poly1305) | 대칭 구간 비용은 작다(1장 가설) |
| 세션 재사용 | **확정 — 연결 재사용(keep-alive 65초 · HTTP/2) + 세션 캐시 켬 · 티켓 끔** | 티켓 끔은 Mozilla 권장(티켓 키가 교체되지 않으면 전방 보안이 약해진다) | **가설 확인 — 새 연결 비율이 CPU를 가른다.** 연결을 재사용하면 HTTPS 는 HTTP 와 같다(400 RPS 에 25.9 % 대 25.5 %). TLS 1.2 세션 캐시 재사용은 새 연결 대비 약 18배 빠르다(`s_time`). TLS 1.3 재사용은 측정 도구 한계로 **미측정**(s_time 이 핸드셰이크 뒤 오는 티켓을 읽지 않는다) |

- **인증서 발급** — [Let's Encrypt IP 주소 인증서](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability)(2026-01 정식, `shortlived` 프로필 · **유효 160시간**). APP-01의 공인 IP는 켤 때마다 바뀌므로(서버 운영 기반 설계서 — 본인 계정 켜고 끄기) **켤 때마다 발급**하고 6일 안에 갱신한다. 발급 · 갱신 자동화와 만료 감시가 이 방식의 전제다(5장 — 인증서 만료는 전면 장애).
- **이 절이 대체한 결정** — 시스템 구성서의 「접속은 공인 IP + HTTP, 도메인 · TLS는 두지 않는다(2026-09-19 결정)」와 운영 절차서 4.2 의 `listen 80` 서버 블록. HTTPS 구현(2026-09-28 · #288)에서 두 문서를 함께 고쳤다.
- HTTP(80)는 ACME 확인과 HTTPS 넘기기(301)만 남긴다. 앞단 요청 상한 · 점검 모드는 443 서버 블록으로 옮긴다(운영 절차서 4.2).
- **확정(2026-09-28 · #288 — C-2)** — 인증서 키 ECDSA P-256, TLS 1.2 + 1.3, 세션 캐시 10 MB · 1일 · 티켓 끔. 판정(시험 계획서 9.3): **채택** — 보안 하한(Mozilla intermediate)을 지키고, 입구 CPU 비용은 최악(모든 요청이 새 연결) 400/초에서도 APP-01 2코어의 약 20 %p 로 병목(DB-01 CPU — 용량 산정 리포트)이 아니다. API 전체 포화점을 HTTPS 로 다시 재지는 않았다(**미측정** — 연결 재사용 시 입구 비용이 HTTP 와 같아 영향이 작을 것으로 본다).
- **발급 · 갱신은 `infra/tls/`**(`issue-cert.sh` · `rental-tls.timer` — 부팅 20초 뒤 · 12시간마다, IP 변경 · 자체 서명 · 만료가 가까우면 발급 — 기준 시간은 스크립트 머리 주석이 갖는다). 켤 때 새 IP 인증서까지 **약 32초**(부팅 → 새 인증서, 2026-09-28 실측) — 그동안은 옛 IP 인증서라 브라우저가 경고한다. 절차는 운영 절차서 4.3.
- **카카오맵 사이트 도메인** — 페이지 출처가 `https://<IP>` 로 바뀐다. 등록 주소에 `https://` 를 넣어야 하는지는 **미확인**이다(켤 때마다 IP 도 바뀌어 옛 등록으로는 어차피 지도가 뜨지 않아 이번에 가를 수 없었다) — 다음에 켜서 등록할 때 `https://<IP>` 로 넣고 확인한다(운영 절차서 9.1).

### 4.2 비밀번호 해싱 — 앱(슬롯 넷)

| 후보 | 파라미터(보안 하한) | 비용 가설 |
|---|---|---|
| BCrypt | 비용 **10 이상**(지금 값은 라이브러리 기본값 — 설치본 소스로 확인) · 입력 72바이트 제한 | 비용 1 증가마다 약 2배. CPU만 쓴다 |
| **Argon2id** | [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) 최소 조합 중 하나 — m=19 MiB · t=2 · p=1(동등: 46 MiB · t=1, 12 MiB · t=3, 9 MiB · t=4, 7 MiB · t=5) | CPU와 **메모리**를 쓴다. 메모리를 줄이고 반복을 늘리는 조합이 슬롯 메모리 상한(운영 Compose)에 유리하다 |
| PBKDF2-HMAC-SHA256 | 반복 600,000 | CPU만. 메모리 방어 없음 — 후보 중 우선순위 낮음 |

- **하한 해석** — OWASP는 해시 한 번이 1초 미만이어야 하고, 과한 강도는 **로그인 요청만으로 CPU를 고갈시키는 서비스 거부 경로**가 된다고 경고한다. 강도는 「세게」가 아니라 **하한 이상에서 로그인 몰림을 버티는 값**이다.
- **Spring 기본값을 그대로 쓰지 않는다** — `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`은 메모리 `1 << 14`(16 MiB) · 반복 2로 **OWASP 최소(19 MiB · t=2)보다 낮다**([Spring Security API](https://docs.spring.io/spring-security/reference/api/java/org/springframework/security/crypto/argon2/Argon2PasswordEncoder.html)). 메모리 단위(KiB)와 필요한 의존성은 구현 때 설치본 소스로 확인한다.
- **메모리 상한과의 관계** — Argon2id는 해시 하나가 m 만큼 메모리를 잡는다. **동시 해싱 수 × m** 이 슬롯 컨테이너 메모리 상한(운영 Compose)을 넘을 수 있다 — 동시 해싱 수의 상한은 요청 스레드 수(`application.yml`, 잠정)다. 넘으면 동시 해싱 수를 제한(세마포어 등)하거나 메모리가 작은 조합을 고른다 — 측정으로 정한다.
- **이행** — 기존 BCrypt 해시는 풀 수 없으므로 **로그인 성공 때 새 알고리즘으로 다시 해시**한다(`DelegatingPasswordEncoder` 계열 — 구현 때 확인). 새 알고리즘으로 바꾸면 72바이트 제한이 사라지므로 가입 정책(`PasswordPolicy`)의 바이트 검사도 함께 본다.
- 미확정 — 알고리즘 · 파라미터 · 동시 해싱 제한. **측정(시험 계획서 9장 C-1) 뒤 확정한다.**

### 4.3 JWT 서명 — 앱(슬롯 넷)

| 후보 | 보안 하한 | 비용 가설 |
|---|---|---|
| **HS256 유지** | 키 256비트 이상([RFC 7518](https://www.rfc-editor.org/rfc/rfc7518) 3.2 — 지금 코드가 검사한다) | 가장 가볍다 |
| ES256(P-256) | RFC 7518 3.4 | 서명 · 검증 모두 HS256보다 무겁다 |
| RS256(2048) | RFC 7518 3.3 | 검증은 가볍고 서명은 무겁다 |

- **검증은 모든 API 요청에 붙는다** — 요청당 비용이라 포화점을 직접 움직인다. 서명은 로그인 · 재발급 때만이다.
- **비대칭의 이점은 검증자가 서명 키를 갖지 않는 것**이다. 지금은 토큰을 발급하고 검증하는 주체가 같은 서비스(슬롯 넷)라 그 이점이 작다. 비용 차이가 크면 **HS256 유지가 합리적인 결론일 수 있다** — 측정 뒤 판단하고, 유지하면 그 근거를 여기에 적는다.
- 미확정 — 알고리즘. **측정(시험 계획서 9장 C-3) 뒤 확정한다.**

### 4.4 컬럼 암호화 — DB

**대상 후보**(우선순위 순)

| 컬럼 | 쓰임 | 암호화하면 |
|---|---|---|
| `users.annual_income` · `credit_score` · `existing_loan` · `existing_loan_annual_payment` · `own_fund` | 대출 한도 계산 · 내 정보 | 앱에서 풀어 계산한다 — **DB 안에서 연산 · 비교에 쓰는 질의가 있으면 옮겨야 한다**(질의 목록은 구현 때 확인) |
| `user_auth.provider_id`(= 이메일) | **로그인 조회 키** · 중복 가입 검사 — `UNIQUE(auth_type, provider_id)` | 인덱스 · UNIQUE 로 못 찾는다 — **검색용 해시 컬럼**(아래)으로 조회 · 제약을 옮긴다 |
| `users.email` · `users.phone` · `users.name` | 표시 · 내 정보(`users.email` 에는 인덱스 · UNIQUE 가 없다) | 표시할 때만 푼다 — 로그인과 무관하다 |
| `property.landlord_name` | 매물 상세 · 등기 소유자 대조 | 대조 로직이 평문 비교를 쓰면 앱으로 옮긴다 |

| 항목 | 후보 | 보안 하한 | 비용 가설 |
|---|---|---|---|
| 알고리즘 | **AES-256-GCM** · ChaCha20-Poly1305 · AES-256-CBC + HMAC-SHA256 | **인증 암호화(AEAD 또는 암호화 후 MAC)**, [KISA 권고](https://seed.kisa.or.kr/kisa/reference/EgovGuide.do) 블록 암호(AES · ARIA · SEED 등) · 128비트 이상 | 셋 다 필드 하나에 마이크로초 이하 — **차이가 측정되지 않을 것**이라는 가설(1장). ChaCha20은 AES-NI가 없는 CPU용이다 |
| IV(GCM) | 96비트 무작위 · 필드마다 새로 | NIST SP 800-38D — **무작위 IV는 키 하나당 약 2^32회까지** | 이 규모(사용자 수만)에서 한도에 닿지 않는다. 키 교체 주기의 근거로 둔다 |
| 풀어 쓰는 자리 | **앱**(JPA 변환기 · MyBatis 타입 핸들러) · DB(`pgcrypto`) | — | **지금 병목은 DB-01 CPU**(용량 산정 리포트) — 앱에서 풀면 CPU가 슬롯 넷으로 흩어진다는 가설. DB에서 풀면 키가 질의로 DB에 건너간다(로그 · 통계에 남을 위험) |
| 검색용 해시 | HMAC-SHA256(암호화 키와 **다른 키**) — 정규화(소문자 · 공백 제거) 뒤 | — | 동등 검색만 된다. 부분 검색 · 정렬은 불가 |

- **키 보관** — 노드 `.env`(사용자 결정). 키는 **앱 노드에만** 두고 DB 노드에는 두지 않는다 — DB 노드가 털려도 암호문뿐이다. 암호문 앞에 **키 식별자**를 붙여 키 교체 때 옛 키로 풀고 새 키로 다시 쓴다.
- **기존 데이터** — **SQL 마이그레이션으로는 암호화하지 않는다** — 키는 앱 노드에만 있고 DB 에는 없다. 스키마(암호문 · 해시 컬럼 추가, 나중에 평문 삭제)만 Flyway 가 하고, **값 채우기는 앱의 일회성 이행 작업**이 한다. 이행 동안은 두 컬럼을 함께 읽는다(순서는 컬럼 암호화 절차 스킬).
- 미확정 — 대상 컬럼 · 알고리즘 · 풀어 쓰는 자리 · 키 교체 주기. **측정(시험 계획서 9장 C-4) 뒤 확정한다.**

### 4.5 키 · 인증서 — 인프라

| 자산 | 자리 | 잃으면 | 대비 |
|---|---|---|---|
| 컬럼 암호화 키 · 검색용 해시 키 | 앱 노드 `.env` | **암호화한 데이터를 영구히 못 읽는다** | 백업 키(gpg)와 **다른 자리**에 사본 — 백업 사본과 같은 곳에 두면 둘이 함께 샌다. 복원 리허설에 키 포함 |
| JWT 서명 키 | 앱 노드 `.env`(지금) | 발급된 토큰 전부 무효 — 재로그인 | 교체 절차(새 키로 서명 · 옛 키로도 검증하는 기간) |
| TLS 인증서 · 개인키 | APP-01 | 만료 · 분실 = 입구 전면 장애 | 자동 발급 · 갱신, 만료 전 경보 |

**키 관리 절차**(3장 ⑥항) — 생성(난수원 · 길이) · 이용(주입 경로) · 보관(자리 · 사본) · 배포(노드에 넣는 방법) · 파기(교체 뒤 옛 키를 언제 지우는가)를 운영 절차서에 둔다 — 컬럼 암호화 구현 때 쓴다(8장).

| 계층 | 보안 작업 | 가용성을 위협하는 것 | 볼 지표 |
|---|---|---|---|
| 입구(APP-01) | HTTPS | 핸드셰이크 CPU가 **입구 노드에 몰린다**(APP-01은 메모리 여유도 가장 적다) · **인증서 만료 = 전면 장애** · 새 연결 폭주 | APP-01 CPU, 초당 새 연결 · 세션 재사용률, 인증서 남은 유효 시간 |

| 인프라 | 키 · 인증서 | **키 분실 = 데이터 영구 손실** · 갱신 실패 | 키 사본 존재 확인(정기 점검), 발급 · 갱신 작업 결과 |

## 6. 질의 특징 분석 — 무엇이 DB CPU를 쓰는가

부하 시험(용량 산정 리포트 T2-⑥ · ⑦)에서 DB 실행 시간 상위 질의는 다음 **특징**을 가졌다 — 암호화 전후 비교의 기준으로 쓴다.

| 특징 | 예 | 대응(적용 여부) |
|---|---|---|
| 넓은 범위를 조인한 뒤 집계 | 지도 묶음 조회 — 위험 분석 2.2만 행 해시 조인 · 칸별 집계 | 캐시 · 읽기 분산(보류 — 리포트) |
| 인덱스 없는 조건 → 전체 스캔 · 정렬 | 목록(자치구) · 등기 이력(등기 ID) | 인덱스(적용 — V15) |
| 행마다 도는 하위 질의 | 마커의 선순위 채무 EXISTS | 인덱스(적용 — V15) |
| **(암호화 뒤 예상)** 평문 조건이 사라진 조회 | 로그인 조회(`user_auth.provider_id`) | 검색용 해시 컬럼 |
| **(암호화 뒤 예상)** 많은 행을 풀어 돌려주는 조회 | 목록에 암호화 컬럼이 끼는 경우 | 목록에서 빼고 상세에서만 푼다 |
