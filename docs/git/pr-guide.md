# PR 가이드

**PR을 만드는 이유는 승인이 아니라 CI 실행과 변경 이력 정리다.** 1인 개발이라 리뷰어가 없고 승인 인원도 두지 않는다. 리뷰어 역할은 CI와 `code-reviewer` 에이전트가 대신한다.

작업 순서에서 PR이 어디에 오는지는 `docs/workflow.md` 2장, merge 방식과 브랜치 삭제는 `docs/git/branch-strategy.md`가 정한다. 본 문서는 **PR 자체의 대상·제목·본문**만 정한다.

---

## 대상 브랜치

| 출발 | 대상 | 언제 |
| --- | --- | --- |
| `feature/*` · `fix/*` · `chore/*` · `docs/*` | `develop` | 평시 작업 전부 |
| `develop` | `main` | 배포 시점 |
| `hotfix/*` | `main`, 그리고 `develop`에도 별도로 | 배포 후 긴급 수정 |

hotfix를 `develop`에 반영하는 PR을 빠뜨리면 다음 배포에서 같은 버그가 되살아난다.

---

## 제목

**squash 커밋 제목과 같게 둔다.** 형식은 `docs/git/commit-convention.md`를 따른다.

```
chore(be,infra): JWT 인증 필터체인·PasswordEncoder 설정 추가
```

squash merge 시 이 제목이 그대로 `develop` 이력에 남으므로, PR 제목과 squash 제목이 다르면 나중에 PR을 찾을 수 없다.

---

## 본문

**본문 구성은 `.github/pull_request_template.md`가 정본이다.** PR을 열면 그 템플릿이 자동으로 채워진다. 절 구성을 여기에 옮겨 적지 않는다 — 두 곳에 적으면 템플릿을 따르는 사람과 이 문서를 따르는 사람이 다른 PR을 쓰게 된다.

본 문서가 정하는 것은 **템플릿을 쓰는 방식** 셋뿐이다.

- **템플릿을 지우지 않는다.** 본문을 파일이나 문자열로 직접 넘기면 템플릿이 덮인다. `gh pr create`를 쓸 때도 템플릿의 절을 채운 본문을 넘긴다.
- **해당 없는 절은 비우지 말고 뺀다.** 빈 표와 빈 목록이 남으면 채우지 않은 것과 해당 없는 것이 구분되지 않는다.
- **`closes #이슈번호`를 빠뜨리지 않는다.** merge 시 이슈가 자동으로 닫힌다. 빠뜨리면 이슈가 열린 채 남고, 한 번에 하나만 연다는 규칙이 깨진다.

템플릿의 절을 늘리거나 줄일 일이 생기면 템플릿을 고친다. 이 문서를 고치지 않는다.

---

## 하지 않는 것

| 하지 않는 것 | 이유 |
| --- | --- |
| 승인 인원 지정 | 리뷰어가 없다. 승인 규칙을 걸면 아무것도 merge할 수 없다 |
| 리뷰어 지정 | 같은 이유 |
| CI 실패 상태로 merge | CI가 유일한 게이트다 |
| 본문에 규칙 전재 | 커밋 형식·머지 방식·순서는 각 문서가 갖는다. 참조만 한다 |

---

## merge 이후

merge 방식과 브랜치 삭제는 `docs/git/branch-strategy.md`가 정한다. 절차를 여기에 옮겨 적지 않는다.

**뒷정리를 미루지 않는다.** 남은 브랜치가 쌓이면 어느 것이 진행 중인 작업인지 구분되지 않는다.
