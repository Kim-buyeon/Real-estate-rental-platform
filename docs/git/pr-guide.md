# PR 가이드

## 생성 규칙

- 이슈와 연결한다. 본문에 `closes #이슈번호`
- 하나의 PR은 하나의 기능 또는 수정이다. 여러 기능을 몰아넣지 않는다
- 작업 중 상태를 남겨두려면 Draft PR로 올린다. merge 버튼이 비활성화되어 실수로 병합되지 않는다

---

## 제목

`docs/git/commit.md`와 동일한 형식이며, scope는 브랜치의 scope와 같다.

```
feat(be): 보증보험 3사 가입 판정 로직 추가 (RISK-05)
feat(infra): 슬롯 순차 교체 배포 스크립트 추가 (INF-02)
docs: 인프라 API 명세서 추가
```

Squash merge 시 이 제목이 `develop`의 커밋 메시지가 되므로, 이력에 그대로 남을 문장으로 쓴다.

---

## 본문

`.github/PULL_REQUEST_TEMPLATE.md`를 따른다. 다음 항목을 포함한다.

| 항목 | 내용 |
| --- | --- |
| 변경 요약 | 무엇을 왜 바꿨는지 |
| 관련 기능ID | `docs/features/`의 `USER-01`~ · `docs/features/infra.md`의 `INF-01`~ · `docs/infra/traffic.md`의 `T1`~ |
| 검증 결과 | 실행한 명령과 통과 여부. 인프라 변경은 `docs/git/commit.md`의 확인 명령 결과를 적는다 |
| 문서 변경 | 명세를 함께 고쳤다면 어느 문서인지 |

## Merge 조건

- CI 통과 필수. 빌드·테스트·마이그레이션 검증이 모두 성공해야 한다
- 충돌은 PR 작성자가 해결한다
- merge 방식은 대상 브랜치에 따른다. 상세는 `docs/git/branch.md`을 따른다
- merge 후 브랜치를 원격·로컬 모두 삭제한다
  - 원격: GitHub의 Delete branch
  - 로컬: `git branch -d <브랜치명>`

## 검토

1인 개발이므로 승인 규칙을 두지 않는다. 리뷰어의 역할은 다음이 대신한다.

| 수단 | 역할 | 시점 |
| --- | --- | --- |
| 훅 | 자격 증명 커밋, 적용된 마이그레이션 수정, 금지 의존성 추가 차단 | 커밋 시점 |
| `git-check` 스킬 | 커밋 메시지 규약, 커밋 단위, 함께 커밋해야 하는 짝 | 커밋·push 전 |
| code-reviewer 에이전트 | 코드 규칙, 계층 경계, 연동 지점 정합, 슬라이스 범위 검토 | **PR 생성 전** |
| CI | 빌드·테스트·마이그레이션 검증. **merge 차단 권한을 갖는다** | PR 생성 시 |

- **PR을 만들기 전에 code-reviewer를 실행하고 지적 사항을 처리한다.** 열어둔 PR에 수정 커밋을 쌓지 않는다. 검토를 건너뛰면 CI를 통과하는 잘못된 코드를 걸러낼 수단이 없다
- 검토 항목은 code-reviewer 정의를 따른다. PR마다 별도 확인 목록을 두지 않는다
- **PR을 만드는 이유는 승인이 아니라 CI 실행과 변경 이력 정리다**
