# PR 가이드

**PR을 만드는 이유는 승인이 아니라 CI 실행과 변경 이력 정리다.** 1인 개발이라 리뷰어가 없고 승인 인원도 두지 않는다. 리뷰어 역할은 CI와 `code-reviewer` 에이전트가 대신한다.

작업 순서에서 PR이 어디에 오는지는 `docs/workflow.md` 2장, merge 방식과 브랜치 삭제는 `docs/git/branch-strategy.md`가 정한다. 본 문서는 **PR 자체의 대상·제목·본문**만 정한다.

---

## 대상 브랜치

| 출발 | 대상 | 언제 |
| --- | --- | --- |
| `feature/*` · `fix/*` · `chore/*` · `docs/*` | `develop` | 평시 작업 전부 |
| `develop` | `main` | 배포 시점 |
| `hotfix/*` | `main`, 그리고 `develop`에도 별도로 | 배포 후 긴급 수정 |

**`main`과 `develop`에 직접 push하지 않는다.** hotfix를 `develop`에 반영하는 PR을 빠뜨리면 다음 배포에서 같은 버그가 되살아난다.

---

## 제목

**squash 커밋 제목과 같게 둔다.** 형식은 `docs/git/commit-convention.md`를 따른다.

```
chore(be,infra): JWT 인증 필터체인·PasswordEncoder 설정 추가
```

squash merge 시 이 제목이 그대로 `develop` 이력에 남으므로, PR 제목과 squash 제목이 다르면 나중에 PR을 찾을 수 없다.

---

## 본문

다섯 절을 쓴다. 해당 없으면 절을 비우지 말고 뺀다.

### 무엇

이 PR이 무엇을 하는가. 그리고 **무엇을 하지 않는가.** 슬라이스의 어느 조각이고 나머지는 어느 기능ID가 갖는지 적는다. 범위를 적어 두지 않으면 나중에 이 PR이 왜 이만큼만 했는지 알 수 없다.

### 판단한 것

규칙이 재량을 허용하는 지점에서 고른 것을 표로 적는다. **사유를 함께 적는다.** 승인받은 계획의 「정한 것」·「정해야 할 것」이 그대로 여기 온다.

| 지점 | 선택 | 사유 |
| --- | --- | --- |

### 검증

**무엇으로 확인했는지 적는다.** 통과했다는 말만 적지 않는다.

| 방법 | 결과 |
| --- | --- |

인프라 변경은 컴파일도 테스트도 되지 않으므로 확인 명령과 그 결과를 반드시 적는다. 어떤 명령을 쓰는지는 `docs/git/commit-convention.md`.

### 후속 작업에서 걸릴 것

**이 PR에서 고치지 않았고 나중에 문제가 되는 것을 적는다.** 어느 작업에 착수할 때 걸리는지까지 적는다.

기반 작업은 최소 규칙만 두고 세부를 각 기능 슬라이스로 미루는 경우가 많다. 미룬 것을 적어 두지 않으면 그 슬라이스에서 조용히 터진다. 지적을 받고 고치지 않기로 결정한 것도 여기에 남긴다.

### closes

```
closes #이슈번호
```

merge 시 이슈가 자동으로 닫힌다. **빠뜨리면 이슈가 열린 채 남고, 한 번에 하나만 연다는 규칙이 깨진다.**

---

## 하지 않는 것

| 하지 않는 것 | 이유 |
| --- | --- |
| 승인 인원 지정 | 리뷰어가 없다. 승인 규칙을 걸면 아무것도 merge할 수 없다 |
| 리뷰어 지정 | 같은 이유 |
| CI 실패 상태로 merge | CI가 유일한 게이트다 |
| 본문에 규칙 전재 | 커밋 형식·머지 방식·순서는 각 문서가 갖는다. 참조만 한다 |

---

## merge 이후

`docs/git/branch-strategy.md`의 merge 방식을 따르고, **원격과 로컬 브랜치를 모두 지운다.**

저장소 안에서 `gh pr merge --delete-branch`로 merge하면 원격과 로컬이 함께 지워진다. **GitHub 웹에서 merge하면 로컬 브랜치가 남는다.** 그때는 직접 지운다.

```bash
git switch develop
git pull origin develop
git fetch --prune
git branch -d <작업 브랜치>
```

`-d`는 브랜치의 커밋이 전부 현재 브랜치 이력에 있을 때만 지운다. **squash merge는 내용만 합쳐 해시가 다른 새 커밋 하나를 만들므로 원래 커밋이 `develop` 이력에 없고, `-d`가 거부된다.** 그때는 `git log develop..<브랜치>`가 비었는지로 반영 여부를 확인한 뒤 `-D`로 지운다. 비어 있지 않으면 아직 반영되지 않은 커밋이 있다는 뜻이므로 지우지 않는다.

**merge 후 뒷정리를 미루지 않는다.** 남은 브랜치가 쌓이면 어느 것이 진행 중인 작업인지 구분되지 않는다.
