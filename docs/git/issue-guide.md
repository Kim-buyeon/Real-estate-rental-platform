# 이슈 가이드

모든 작업은 이슈에서 시작한다. 이슈 → 브랜치 → PR 순서다.

혼자 작업하더라도 이슈를 남기는 이유는 두 가지다. 작업을 시작하기 전에 범위를 글로 적으면 슬라이스 밖으로 새는 것을 막을 수 있고, 나중에 "이 코드를 왜 이렇게 만들었나"를 되짚을 근거가 남는다.

---

## 생성 규칙

- 작업 시작 전에 만든다. 이슈 없이 브랜치를 파지 않는다
- 하나의 이슈는 하나의 기능 또는 하나의 수정이다
- 본문은 `.github/ISSUE_TEMPLATE/`의 템플릿을 따른다
- 관련 문서를 본문에 링크한다. 기능 정의와 API 명세의 어느 항목인지 적어두면 작업 중 다시 찾지 않는다

---

## 제목 형식

### 기능 관련

```
[분야] [분류] 기능ID - 작업 내용
```

- `[분야]` — `[BE]` · `[FE]` · `[INFRA]`
- `[분류]` — `[기능]` · `[버그]` · `[리팩터링]` · `[시험]`
- 기능ID — `docs/features/`의 `USER-01`~ 또는 `docs/features/infra.md`의 `INF-01`~

예시

- `[BE] [기능] RISK-05 - 보증보험 3사 가입 판정 구현`
- `[FE] [기능] PROP-02 - 지도 드릴다운 탐색 구현`
- `[INFRA] [기능] INF-02 - 슬롯 순차 교체 배포 스크립트 작성`
- `[FE] [버그] PROP-02 - 자치구 복귀 시 필터 초기화되는 오류`
- `[INFRA] [버그] INF-01 - 헬스체크가 DB 순단에 DOWN 반환하는 오류`
- `[BE] [리팩터링] LOAN-01 - 한도 계산 로직 분리`

**`[시험]`은 인프라 전용이다.** 부하 시험과 장애 주입 시험은 구현이 아니라 실행이고, 산출물이 코드가 아니라 결과서다.

- `[INFRA] [시험] INF-06 - 부하 시험`
- `[INFRA] [시험] INF-06 - 복구 시험`
- `[INFRA] [시험] INF-06 - 장애 주입 시험 9종`

**시험 구간마다 이슈 하나를 만들고 본문에 항목을 체크리스트로 둔다.** 항목을 모두 마치면 닫는다.

시험별 기록은 이슈가 아니라 결과서가 갖는다. 실행 시각, 구간별 지표, 기대와의 차이가 모두 결과서 양식에 있으므로 이슈를 시험 수만큼 쪼개면 같은 내용을 두 곳에서 관리하게 된다.

### 비기능 작업

```
[분야] [분류] 작업 내용
```

- `[분야]` — `[BE]` · `[FE]` · `[INFRA]` · `[공통]`
- `[분류]` — `[문서]` · `[환경]` · `[리팩터링]`

예시

- `[공통] [문서] API 명세 갱신`
- `[BE] [환경] Testcontainers 공용 지원 클래스 작성`
- `[INFRA] [환경] Docker Compose 기본 구성 작성`
- `[INFRA] [환경] 관측 스택 기동 (Prometheus·Loki·Grafana)`
- `[FE] [리팩터링] API 모듈 폴더 구조 정리`

### 비기능이지만 특정 기능과 관련된 경우

기능ID를 포함해 연관성을 표시한다.

- `[BE] [환경] RISK-05 - 보증 기준 시드 데이터 적재`
- `[공통] [문서] PROP-08 - 자치구 집계 응답 명세 보완`
- `[INFRA] [문서] INF-04 - 백업·복구 절차서 보완`

## 라벨

| 라벨 | 용도 |
| --- | --- |
| `enhancement` | 기능 추가·개선 |
| `bug` | 버그 |
| `documentation` | 문서 |
| `environment` | 개발 환경, 빌드, 배포 |
| `refactoring` | 리팩터링 |
| `test` | 부하 시험·장애 주입 시험 실행 |
| `urgent` | 우선 처리 |

- 제목의 분류에 맞는 라벨을 쓴다
- 필요하면 조합한다. 급한 버그는 `bug` + `urgent`

분야(`BE` · `FE` · `INFRA`)는 제목에 이미 있으므로 별도 라벨을 두지 않는다.

---

## 슬라이스와의 관계

슬라이스는 여러 기능을 묶으므로 이슈는 기능 단위로 만든다.

**한 번에 하나만 연다.** 기능 하나를 완료하고 이슈를 닫은 뒤 다음 이슈를 만든다. 슬라이스의 기능들을 미리 등록하지 않는다.

- 열린 이슈가 여럿이면 다음 작업이 흐려진다. 한 번에 한 작업만 진행한다는 규칙과 어긋난다
- 앞선 기능을 구현하다 보면 뒤 기능의 범위가 바뀐다. 미리 써둔 이슈는 그 시점에 이미 낡은 내용이다
- 이슈를 쓰는 시점이 범위를 확정하는 시점이다. 몰아서 쓰면 각각을 대충 쓰게 된다
- 스키마 작업처럼 기능ID가 없는 항목은 `[BE] [환경]`, 인프라 구성은 `[INFRA] [환경]`으로 만든다
- 슬라이스가 끝나면 그 슬라이스의 이슈가 모두 닫혀 있어야 한다

**시험 이슈는 대상 구현 이슈가 닫힌 뒤에 연다.** 이중화가 완성되기 전에 앱 정지 시험을 열면 무엇을 확인하는 시험인지 정의되지 않는다.

---

## 닫는 시점

- PR 본문에 `closes #이슈번호`를 적으면 merge 시 자동으로 닫힌다
- 작업을 중단하거나 범위를 바꿨다면 사유를 코멘트로 남기고 닫는다. 열어둔 채 방치하지 않는다

**시험 이슈는 결과서를 커밋하는 PR로 닫는다.** 결과서는 산출물이므로 저장소에 남긴다. `docs:` 커밋으로 올리고 PR 본문에 `closes #이슈번호`를 적는다. 기대와 다른 결과가 나왔다면 결과서에 적고, 조치가 필요하면 별도 이슈를 만든다.
