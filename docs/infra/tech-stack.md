> 인프라 기술 선정 결과 및 선정 사유
> Docker Compose · Nginx · PostgreSQL 복제 · AWS EC2 · Rocky Linux
> ※ 본 문서는 인프라 기술의 선정 결과만을 다룬다. 구성과 절차는 `docs/infra/system.md`·`docs/infra/runbook.md`를 따른다.
> 작성 기준일 : 2026년 8월

## 1. 문서 목적 및 선정 원칙

본 문서는 서비스를 배포하고 운영하는 데 사용할 기술을 계층별로 확정하고, 각 항목의 선정 사유와 고정 버전을 기록한다. `docs/tech-stack.md`가 애플리케이션 기술을 다루는 것과 같은 형식으로, 인프라 기술을 같은 수준으로 확정한다.

### 1.1 선정 원칙

**운영 인력 1인 전제** — 상시 감시를 전제하는 기술은 채택하지 않는다. 자동 감지와 절차서로 대체한다.

**서비스 요구가 없는 기술은 도입하지 않는다** — 각 기술은 `docs/features/infra.md`의 INF 항목 하나 이상을 근거로 갖는다. 근거를 댈 수 없으면 도입하지 않는다.

**동작을 시험으로 증명할 수 있어야 한다** — 도입한 기술이 실제로 동작하는지 확인할 수단이 함께 있어야 한다. 확인할 수 없는 구성은 채택하지 않는다.

**관리형 서비스에 의존하지 않는다** — 모든 구성 요소를 직접 기동한다. 서비스 구성 요소는 컨테이너로, OS 기능(NFS 서버 · NAT · 방화벽 · 정기 작업)은 OS 표준 패키지로 둔다 — 설계 대상은 Rocky이고 현재 노드는 Amazon Linux 2023이다(2.1절). 클라우드 사업자의 관리형 데이터베이스·로드밸런서·모니터링에 의존하지 않으므로 온프레미스나 프라이빗 클라우드로 그대로 이식할 수 있다.

> **예외 하나 — 관측의 저장 · 시각화 · 알림**(2026-09-23). 노드를 늘릴 수 없어(시스템 구성서 2.2절) 관측 스택을 둘 자리가 없다. **수집기만 노드에 두고 지표 · 로그를 밖으로 보낸다.**
>
> 원칙의 목적인 **이식성은 유지된다** — 수집기가 Prometheus 표준이라 수집 대상만 바꾸면 자체 호스팅으로 되돌아간다. 노드에 남는 것은 표준 exporter뿐이고 잠금이 생기지 않는다.
>
> 그리고 이 환경에서는 **밖에 두는 쪽이 오히려 설계 의도에 맞다.** 4장이 노드 밖 감시를 둔 이유가 「노드가 통째로 정지하면 감시자와 알림 발송 주체가 함께 사라진다」인데, 노드가 하나뿐이면 자체 호스팅은 자기 자신을 감시하는 구조가 된다.

**비용 상한 우선** — 월 고정 비용의 상한을 먼저 정하고 그 범위에서 최대 가용성을 설계한다.

### 1.2 스택 요약

| 계층 | 채택 기술 | 핵심 근거 |
|---|---|---|
| 서버 | AWS EC2 — Amazon Linux 2023 → Rocky Linux 9 | 먼저 EC2 기본 OS에 배포하고 Rocky Linux로 옮긴다. 시스템 구성서 2.1절 |
| 네트워크 격리 | VPC 공개/사설 서브넷 · NAT 인스턴스 · S3 게이트웨이 엔드포인트 | DB · NAS를 인터넷에서 닿지 않게. 관리형 NAT Gateway 대신 인스턴스(비용) — 서버 운영 기반 설계서 3장 |
| NAS(백업 모음) | NFS 서버(`nfs-utils`, NFSv4) on EC2 + EBS | 논리 백업 · 설정 사본을 한곳에 모은다. EFS 대신 자체 서버(비용 · 이식성) — 같은 설계서 5장 |
| 정기 작업 | systemd timer | 꺼져 있던 시각의 작업을 부팅 뒤 실행, 결과가 저널에 남는다 — 같은 설계서 7장 |
| OS 보안 | SELinux(enforcing) · firewalld · `dnf-automatic` · chrony | Rocky 기본을 끄지 않고 쓴다. 단 EC2 공식 AMI에는 firewalld · `dnf-automatic`이 없어 노드 준비에서 설치한다 — 같은 설계서 3.3 · 8장 |
| 컨테이너 실행 | Docker · Docker Compose | 노드 다섯 개(앱 · DB 둘 · NAS · NAT) 규모에서 오케스트레이터 도입은 과잉 |
| 리버스 프록시 | Nginx | TLS 종단, 요청 분산, 무중단 배포의 실행 주체 |
| CI | GitHub Actions | 푸시 시 빌드·테스트·이미지 생성 |
| 이미지 저장소 | GitHub Container Registry | CI와 같은 곳이라 인증이 추가로 필요 없다 |
| 이미지 검사 | Trivy | 배포 전 CRITICAL 취약점 차단 |
| DB 복제 | PostgreSQL 17 스트리밍 복제 | 내장 기능. 외부 클러스터 관리 도구 불필요 |
| 백업 | `pg_basebackup` + WAL 연속 아카이빙 | RPO 5분. 논리적 손상은 PITR로 복구 |
| 백업 저장소 | S3 호환 오브젝트 스토리지 | 온프레미스에서는 MinIO로 대체 |
| 공유 저장소 | Redis 7 | 두 인스턴스가 같은 상태를 보게 한다 |

## 2. 실행 및 배포 계층

| 기술 | 버전 | 선정 사유 |
|---|---|---|
| Docker | 최신 안정 | 서비스 구성 요소를 컨테이너로 통일한다(OS 기능은 Rocky 표준 패키지 — 1.1). 로컬과 운영의 구성 차이를 없애 "내 환경에서는 되는데"를 제거한다 |
| Docker Compose | v2 | 노드가 다섯 개이고 배포 단위가 하나다. Kubernetes는 학습과 구성에만 수 주가 필요하고 상시 감시를 전제한다 |
| Nginx | 1.26 이상 | TLS 종단, upstream 기반 요청 분산, `proxy_next_upstream` 재시도. 무중단 배포의 실행 주체이며 `down` 플래그 토글과 `reload`가 이 기능의 실질이다. **컨테이너로 구동하며** 설정과 인증서는 호스트 볼륨으로 마운트한다 |
| GitHub Actions | — | 푸시 시 빌드·테스트·이미지 빌드. 1인 개발에서 회귀 검출 수단이 CI뿐이다. 이미지 빌드·푸시까지 담당한다 |
| Trivy | 최신 안정 | 컨테이너 이미지의 OS 패키지와 Java 의존성 취약점을 한 번에 검사한다. CRITICAL은 배포 중단, HIGH는 기록만 남긴다 |
| GitHub Container Registry | — | 이미지 저장소. CI가 GitHub Actions이므로 `GITHUB_TOKEN`으로 인증이 끝나 별도 계정·시크릿이 필요 없다. 소스와 이미지가 같은 곳에 있어 커밋 해시 태그가 소스 이력과 1:1로 대응하며, **공개 저장소는 용량·전송 제한이 없다** |
| Let's Encrypt | — | TLS 인증서. **지금은 쓰지 않는다** — 공인 IP + HTTP로 접속한다(시스템 구성서 2.1절). 도메인을 붙일 때 되살린다 |

**Docker Hub를 쓰지 않는 이유는 pull 한도다.** 무료 계정은 6시간당 200회로 제한되고 비공개 저장소는 1개만 허용된다. 배포 1회에 슬롯 2개를 당기고 롤백까지 겹치면 한도를 의식해야 하는 구조가 된다. AWS ECR은 비공개 이미지가 GB당 과금이라 월 비용 상한에 항목이 하나 늘어난다.

**공개 저장소가 전제다.** 비공개로 두면 GitHub Free 플랜의 저장 500 MB·전송 월 1 GB 안에서 운용해야 하는데, Spring Boot 이미지 하나가 그 저장 한도에 근접한다. 포트폴리오 프로젝트이므로 공개로 둔다.

배포 절차와 이미지 태그 정책은 `docs/infra/runbook.md` 3장을, 네트워크·접근 통제 방침은 `docs/infra/system.md` 4장을 따른다.

### 2.1 서버 · OS 계층

현재 구성 위에 더하는 서버 운영 기반(INF-07 ~ 09)의 기술이다. **아래 선정은 Rocky Linux를 전제한다** — 이전이 불가해 지금 성립하지 않는 행이 있다. 어느 것이 이 노드에서 확인되는지는 서버 운영 기반 설계서 1장이 가른다. **설계와 근거는 서버 운영 기반 설계서(`docs/infra/platform.md`)가 갖는다** — 여기에는 선정 결과만 둔다.

| 기술 | 버전 | 선정 사유 |
|---|---|---|
| Rocky Linux | 9.8(2026-09-25 확정) | RHEL 9 계열. 공식 AMI(Rocky 소유 계정의 AMI는 Marketplace 구독 없이 뜬다 — 시스템 구성서 2.1). Docker 공식 저장소가 RHEL 9 계열을 지원한다 |
| Docker CE | Docker 공식 RHEL 저장소 | Rocky 기본 Podman 대신 — Compose · 배포 스크립트를 그대로 쓴다 |
| XFS · EBS(데이터 볼륨 분리) | — | Rocky 기본 파일시스템. LVM 없이 EBS 확장 + `xfs_growfs` |
| NFS(`nfs-utils`) | NFSv4 | NAS(백업 모음) |
| firewalld · SELinux | Rocky 패키지(firewalld는 EC2 AMI에 없어 설치) | 호스트 방화벽과 강제 접근 통제를 끄지 않는다 |
| systemd timer · `dnf-automatic` | Rocky 기본 | 정기 작업과 보안 갱신 |
| chrony + Amazon Time Sync Service | Rocky 기본 · 169.254.169.123 | 사설 서브넷에서도 인터넷 없이 시각을 맞춘다 |
| NAT 인스턴스(Rocky 9) | — | 사설 서브넷의 인터넷 출구 — 관리형 NAT Gateway 대신 |

## 3. 데이터 계층 운영

| 기술 | 버전 | 선정 사유 |
|---|---|---|
| PostgreSQL 스트리밍 복제 | 17 | Primary 장애 시 승격할 대상을 상시 준비한다. **비동기**를 채택해 standby 지연이 primary 커밋 지연으로 전이되지 않게 한다 |
| 물리 복제 슬롯 | — | standby 중단 시 WAL이 조기 삭제되는 것을 막는다. 다만 슬롯 자체가 primary 디스크를 고갈시킬 수 있어 `max_slot_wal_keep_size`를 2 GB로 제한한다 |
| `pg_basebackup` | — | 주 1회 전체 백업. 4주 보존 |
| WAL 연속 아카이빙 | — | `archive_command`로 노드 로컬 아카이브에 적재하고(3노드는 매분 암호화해 S3로 — 아래) 4분 강제 스위치를 건다(2026-09-25 300초 → 240초). **RPO 5분을 보장하는 것은 복제가 아니라 이 설정이다.** 3노드 전송은 #241 — 노드 소실 시 RPO 최대 약 5분(시스템 구성서 5장). 옛 단일 노드는 로컬만 |
| PITR | — | 잘못된 UPDATE·배치 오적재는 복제로 복구되지 않는다. standby에도 동일하게 복제되기 때문이다 |
| `pg_rewind` | — | 페일백 시 구 primary를 빠르게 standby로 되돌린다. **`wal_log_hints`를 초기 구성 시점에 켜두어야 하며, 장애 발생 후에는 선택할 수 없다** |
| S3 호환 오브젝트 스토리지 | — | WAL 아카이브와 백업 파일 저장. 인터페이스가 표준이라 온프레미스에서는 MinIO로 대체 가능하다 |
| Redis | 7 | 두 애플리케이션 인스턴스가 같은 상태를 보게 한다. 복제도 백업도 두지 않으며, 재생성 가능한 데이터만 보관한다 |

**백업 파일은 전송 전 암호화하고 복호화 키를 분리 보관한다.** USER 테이블에 민감 자격 정보가 포함되기 때문이다.

### 3.1 데이터 암호화 — 층별 적용 범위

위 한 줄이 백업만 다루고 있었다. **같은 데이터가 원본 · 전송 구간에도 있으므로 층마다 적용 여부와 사유를 적는다.** 적용하지 않기로 한 것도 적는다 — 판단한 적이 없는 것과 판단해서 안 하는 것은 다르다.

무엇을 지키려는지가 먼저다. `USERS`에 연소득 · 신용점수 · 기존 대출 · 보유 자금이 이름 · 이메일 · 전화번호와 같은 행에 있다. 금액과 신용 정보가 연락처와 묶여 있는 조합이라 한 행이 새면 그 사람을 특정할 수 있다. `PROPERTY`의 임대인 이름은 **정보주체의 동의 없이 수집되는 제3자 개인정보**다.

| 층 | 적용 | 사유 |
|---|---|---|
| 비밀번호 | **한다** — 단방향 해시 | 되돌릴 필요가 없는 값이다. 대조만 하면 된다 |
| 컬럼 단위 | **하지 않는다** | 신용점수 · 연소득은 대출 한도 계산의 **입력**이다. 암호화하면 조회마다 복호화해야 하고 범위 조건 · 정렬 · 집계가 깨진다. 키를 애플리케이션과 같은 노드에 두면 방어 효과도 반감된다. 기능 코드 동결(로드맵 5장) 이후 허용 범위인 성능 · 복원력 수정에도 해당하지 않는다 |
| 저장 시(블록 볼륨) | **한다** | 비용이 없고 성능 영향이 사실상 없다. **다만 실행 중인 볼륨을 제자리에서 켤 수 없다** — 스냅샷 · 재생성을 거쳐야 하므로 노드 재생성이 가장 싼 기회인데, **이전이 불가해 루트 볼륨은 그 기회가 없다**(서버 운영 기반 설계서 4.2). 데이터 볼륨은 분리할 때 켠다. 확인과 적용은 운영 절차서 9.1 |
| 전송 중(앱 ↔ DB, 복제) | **TLS**(2026-09-25 사용자 결정) | 3노드로 분리해 금전 정보가 사설망(AZ 사이 포함)을 건넌다. 노드별 자체 서명 인증서 · VPC 대역 평문 거절 — 서버 운영 기반 설계서 3.6 |
| 전송 중(사용자 ↔ 서버) | **하지 않는다** | 접속 방식은 시스템 구성서 2.1절이 정한다. **이 구간이 열려 있으면 다른 층의 암호화가 순서상 뒤가 된다** — 로그인 비밀번호와 토큰이 평문으로 인터넷을 건넌다 |
| 백업 | **한다** — 전송 전 암호화, 키 분리 | 위 문단 |
| 로그 | **가린다** | 위 값들은 의도적으로 기록하지 않아도 객체 출력이나 예외 메시지에 실려 로그로 샌다 |

**컬럼 단위를 하지 않기로 한 만큼 접근 경로를 좁히는 쪽에 기댄다** — 데이터베이스를 인터넷에서 닿지 않게 두고(서버 운영 기반 설계서 3장), 백업본과 그 사본을 암호화하고, 로그에 값이 남지 않게 한다. 이 셋 중 하나라도 빠지면 컬럼 암호화를 다시 판단해야 한다.

> **다만 수집 아래 계층을 노드에 두지 않는다.** 인스턴스를 늘릴 수 없어(공유 계정 쿼터 소진) 관측 스택을 얹을 자리가 없고, APP-01은 t3.small 고정이라 여유도 없다. **지표 · 로그를 밖으로 보내 저장 · 시각화 · 알림을 그쪽에서 한다.** 1.1의 예외로 적었다.

### 4.1 노드 쪽 수집 — 지금 구성

**노드에는 exporter와 수집기 둘만 둔다. 저장 · 시각화 · 알림은 Grafana Cloud(무료 티어)가 맡는다**(2026-09-23 결정, #192에서 구성). 값 · 이미지 태그 · 메모리 상한은 운영 Compose가 갖는다.

| 역할 | 채택 | 선정 사유 | 배제한 것 |
|---|---|---|---|
| 지표 수집 · 전송 | **Prometheus agent 모드**(`--agent`) | 스크레이프 · `remote_write`만 하고 로컬 저장 · 질의 · 규칙 평가를 끈다 — 그 일은 밖에서 한다. exporter 설정이 Prometheus 표준 그대로라 자체 호스팅으로 되돌릴 때 수집 설정을 다시 쓰지 않는다(1.1 예외의 이식성 논거). 노드 실측 27 ~ 47 MiB(2026-09-23 ~ 24) | Prometheus 서버 모드 — 로컬 TSDB가 노드 메모리 · 디스크를 쓰는데 볼 곳이 밖이다 |
| 로그 수집 · 전송 | **Vector** | Docker 로그를 컨테이너 · Compose 서비스 라벨과 함께 Loki 형식으로 보낸다. 노드 실측 10 ~ 14.5 MiB | **Promtail** — 2025-02-13 LTS 진입, **2026-03-02 EOL**([Grafana 공지](https://community.grafana.com/t/promtail-end-of-life-eol-march-2026-how-to-migrate-to-grafana-alloy-for-existing-loki-server-deployments/159636)). **Grafana Alloy** — Promtail의 후계이고 지표 · 로그를 하나로 모으지만 노드 여유(`free -m` available 359 MiB — 2026-09-24 15:04 실측, 임시 수집기가 돌던 상태)에 비해 무겁다는 보고가 있다. **실측하지 않았다** — 실측으로 들어간다고 확인된 조합을 고른 것이고, Alloy가 들어가지 않는다고 확인한 것은 아니다 |
| 지표 원천 | 앱 두 슬롯(`/actuator/prometheus`) · node · nginx · postgres · redis exporter | 위 표와 같다. nginx exporter는 루프백 전용 `stub_status` 서버 블록을 읽는다. 앱 지표 경로는 인증 없이 열고 노출 범위로 막는다(인프라 API 명세 1장). Blackbox exporter는 아직 없다. **Grafana Cloud 무료 티어는 활성 시계열 10k가 하드 한도다**([사용 한도](https://grafana.com/docs/grafana-cloud/cost-management-and-billing/manage-invoices/understand-your-invoice/usage-limits/)) — exporter 넷이 약 3,080개(2026-09-24 21:40 노드 실측, `/metrics`의 주석 아닌 줄 수)라 앱 응답 시간은 전체 히스토그램 대신 SLO 구간만 낸다 | 앱 응답 시간 `percentiles-histogram` — 구간 수십 개 × uri · status 조합 |

**exporter는 루프백에만 게시하고 agent는 호스트 네트워크에서 `127.0.0.1`로 긁는다.** 컨테이너 IP로 긁으면 재생성마다 대상이 바뀐다. 루프백 게시는 접근 통제의 셋째 겹과 같은 방식이다(시스템 구성서 4장).

**전송 자격 증명은 `infra/.env`에 둔다.** 저장소에는 자리표시자가 든 설정만 있다. Prometheus는 설정 파일에서 환경 변수를 풀지 못해 기동할 때 채운 사본을 컨테이너 안에만 만든다.

**Vector는 Docker 소켓을 읽기 전용으로 마운트한다 — 그래도 Docker API 전체를 쥔다.** 소켓 권한은 root 동급이고 `:ro`는 파일 쓰기만 막을 뿐 API 호출을 막지 않는다. 받아들이는 근거는 Vector가 **들어오는 포트가 없다**(API 끔)는 것 — 밖에서 그 권한에 닿는 길이 수집기 자신의 결함뿐이다. 로그 파일을 직접 읽으면 소켓이 필요 없지만 컨테이너 이름 · 서비스 라벨을 잃는다.

**PostgreSQL exporter는 전용 역할(`pg_monitor` 멤버)로 붙는다.** 논리 백업과 같은 이유다 — 수집기가 쓰기 권한과 최고 권한 비밀번호를 쥐지 않는다.
