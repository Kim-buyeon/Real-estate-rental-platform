> 무엇을 관측하는가 — 지표 · 대시보드 · 알림 규칙 · 트랜잭션 추적 · 스냅샷 점검
> INF-05
> ※ 수집기 · 전송 · 저장의 기술 선택은 `docs/infra/tech-stack.md` 4장을, 노출 지점과 지표 이름은 `docs/api/infra.md` 1장을, 손으로 하는 확인 · 경보가 울렸을 때의 조치는 `docs/infra/runbook.md` 2장을 따른다.
> 작성 기준일 : 2026년 10월

## 1. 문서 목적

**무엇을 보고, 그것을 어떤 수단으로 보는지를 정한다.** 어떤 도구로 거두는지는 인프라 기술 스택이, 화면을 열고 경보에 대응하는 손 절차는 운영 절차서가 갖는다.

항목마다 **지금 상태**를 적는다 — 「구현」은 지금 Grafana Cloud에 들어오는 것, 「미구현」은 이 문서가 정했지만 아직 거두지 않는 것이다(#353 이후 묶음 작업). 근거의 실측은 따로 적지 않으면 **2026-10-02 네 노드에서 직접 조회한 값**이고, 조회 방법과 값은 #353 「실측 기록」 코멘트에 있다.

### 3.3 데이터베이스 — DB-01 · DB-02

**DB-02에는 DB 지표 수집기가 없다.** postgres exporter는 APP-01에 하나만 있고 `DB_HOST`(primary)만 본다(운영 Compose). 그런데 2026-10-01부터 DB-02가 지도 · 목록 · 구별 집계 읽기를 받는다(#343) — 아래 표의 DB-02 열이 모두 「미구현」이던 이유다.

**수집기를 DB 노드마다 하나로 옮겼다**(#357 — 「구현 — 반영 대기」는 저장소에 있고 노드에 아직 반영하지 않은 것이다). 그 노드의 DB를 역할과 무관하게 보고 그 노드의 수집기가 긁는다. 내장 수집기로 안 되는 D2 · D5 · D6 · D12와 S1은 exporter의 사용자 질의 파일(`infra/prometheus/postgres-queries.yaml`)이 낸다. 지표 이름은 인프라 API 명세 1장 「DB 사용자 질의 지표」가 갖는다.

## 5. 알림 규칙

**무엇에 알림을 거는지는 이 장이 정한다.** 경보가 울렸을 때 무엇부터 볼지는 운영 절차서 2장 「경보별 조치」가, 노드를 끄기 전 무음을 거는 절차도 그 장이 갖는다.

### 5.1 Grafana 규칙 — 지금 일곱

**알림은 아래 일곱 규칙뿐이다 — 나머지 점검은 사람이 확인하는 것이다.** 백업 · WAL 전송 · 수집 끊김 · 입구 인증서는 메일로 오지만 디스크 · 메모리 · 컨테이너 상태에는 규칙이 없다. 외부 경로 감시는 아직 없다(3.5).

**Grafana Cloud(`rental` 폴더 · `rental-backup` 그룹)에 걸려 있다**(2026-09-26, #253). 평가 1분 · 대기(`for`) 5분 · 연락처 `bu2000kim`(메일). 정의 파일은 `infra/grafana/`이고, 올리고 고치는 법은 운영 절차서 2장이 갖는다. 지표 이름은 인프라 API 명세 1장.

| 규칙 | 식(PromQL) | 이유 |
|---|---|---|
| WAL 전송 멈춤 | `time() - rental_job_last_success_timestamp_seconds{task="wal_ship"} > 300` | 매분 도는데 5분 넘게 성공이 없으면 노드 소실 RPO가 늘고 있다(시스템 구성서 5.1) |
| WAL 전송 밀림 | `rental_wal_ship_pending_files > 3` | 보내지 못한 세그먼트가 쌓인다 |
| 논리 백업 누락 | `time() - max(rental_job_last_success_timestamp_seconds{task="logical_backup"}) > 26*3600` | 매일 02:00 — 두 DB 노드 중 primary만 쓰므로 `max` |
| 물리 백업 누락 | `time() - max(rental_job_last_success_timestamp_seconds{task="physical_backup"}) > 8*86400` | 매주 일 01:30 |
| 수집 끊김 | `up < 1` 또는 노드별 `absent(up{node="app-01", job="node"}) * 0`(app-02 · db-01 · db-02도 같은 모양 — 노드 넷) — 임계 `< 1`, 데이터 없음 → OK | 노드 · 수집기가 멈추면 위 규칙도 침묵한다 |
| 인증서 만료 임박 | A = `rental_tls_cert_expiry_timestamp_seconds - time() unless on(node) rental_tls_cert_self_signed == 1`, 임계 A < 48\*3600(critical) | 72시간 전부터 갱신하므로 48시간이면 하루 넘게 실패한 것 — 만료는 입구 전면 장애(운영 절차서 4.3, 2026-09-28 · #288). 식 안에서 비교하지 않고 임계로 둔다 — 이미 만료된(음수) 경우도 울리게. 자체 서명은 뺀다(임시 인증서는 처음부터 2일이라 바로 울린다 — 아래 규칙이 맡는다) |
| 자체 서명 인증서 사용 중 | `rental_tls_cert_self_signed > 0`, 대기 30분(critical) | 발급이 계속 실패해 임시 자체 서명으로 받는 중 — 브라우저가 경고하므로 사실상 입구 장애다 |

**`up == 0` 하나로는 울리지 않는다.** 결과 값이 0이라 임계를 `> 0`으로 두면 늘 거짓이다. 식이 `up`이어도 노드가 통째로 꺼지면 그 노드의 시계열이 사라질 뿐 0이 되지 않고, Grafana는 사라진 시계열의 알림을 해소로 처리한다(2026-09-26 14:47 규칙 이력의 `Normal (MissingSeries)`로 관찰). 그래서 노드 이름을 박은 `absent`를 더한다(2026-09-26 DB-02 node exporter를 14:54:04에 멈춰 15:00:00 Firing · 메일 발송을 확인, #253). 노드를 늘리면 이 식에 한 줄을 더한다 — **APP-02의 `app-02` 줄을 더했다**(2026-09-26 · #255). 그 노드의 `up{node="app-02"}`가 `job="app"` 둘 · `job="node"` 하나로 들어오는 것은 확인했다. APP-02 인스턴스를 멈춘 리허설(운영 절차서 9.1 APP-02)에서 app-02 줄은 **Pending까지 갔고 Firing · 메일은 확인하지 못했다** — 다시 켜서 Normal로 돌아갔다.

**알림까지 걸리는 시간은 끊긴 방식에 따라 다르다**(2026-09-26 · #253 · #255 실측, 표본 1회씩).

| 끊긴 방식 | 알림까지 | 실측 |
|---|---|---|
| 수집 대상 정지 — 시계열이 남아 `up = 0` | 약 5 ~ 6분(대기 5분) | DB-02 node exporter 14:54:04 정지 → 15:00:00 Firing |
| 노드 통째 정지 — 시계열이 사라져 `absent` | **약 10분** — 사라졌다고 판정되기까지 약 5분 + 대기 5분 | APP-02 인스턴스 15:45:56 정지 → `absent(up{node="app-02", job="node"})` **15:51:00 Pending** → (15:56 Firing 예정) 15:54:30 다시 켬 → 15:57:00 Normal |

사라짐 판정의 약 5분은 **질의의 기본 조회 구간(lookback) 5분 때문으로 보인다 — 추정이다.** 줄일 수단(대기 단축 등)은 정하지 않았다 — 후속으로 남긴다.

**일곱 규칙 모두 데이터 없음을 OK로 둔다.** 정상일 때 이 식들은 결과가 비어 있다 — 데이터 없음을 Alerting으로 두면 정상 상태에서 울린다(2026-09-26 14:38 · 14:51 수집 끊김에서 겪었다). 노드가 꺼져 수집 끊김 말고 여섯 규칙(백업 · WAL 넷과 입구 인증서 둘)이 침묵하는 공백은 수집 끊김의 `absent`가 알린다.

### 5.2 EC2 경보 — 노드 자동 복구

Grafana 밖에서 AWS CloudWatch가 거는 경보다. **무엇을 거는지만 여기 적고, 조건 · 기준 근거는 각 스크립트(머리 주석 · `--alarm-description`)가, 동작 실측 · 울렸을 때의 확인은 운영 절차서 2장이 갖는다.**

| 경보 | 무엇을 잡는가 | 동작 | 정의 |
|---|---|---|---|
| `rental-<노드>-instance-check-reboot` | OS가 응답하지 않는다 — 인스턴스 상태 검사 실패 | 재부팅 | `infra/aws/status-check-alarms.sh`(#258) |
| `rental-<노드>-system-check-recover` | AWS 호스트 쪽 장애 — 시스템 상태 검사 실패 | recover | 같다 |
| `rental-APP-01-stall-reboot` | 상태 검사는 정상인데 APP-01 송신이 끊긴 멈춤 | 재부팅 | `infra/aws/stall-alarm.sh`(#266) |

### 5.3 후보 — 기준값 미확정

3장에서 「알림 후보」로 둔 항목이다. **기준값을 경험치로 채우지 않는다.** 정하는 곳은 이 절 하나이고, 근거는 둘이다 — 정하면 5.1 표로 옮긴다.

| 근거 | 무엇을 정하나 | 어디서 오나 |
|---|---|---|
| 평소 범위 | 이보다 낮으면 오탐이 잦다 — 기준값의 아래 끝 | 화면에 올린 뒤 1주 관찰 |
| 포화 시점 | 이보다 높으면 사용자가 먼저 겪는다 — 기준값의 위 끝 | 부하 시험 용량 산정 리포트의 「알림 임계 근거」(시험 계획서 2.4) |

**응답 p95 · 5xx(W1)는 배포 판정보다 엄격하게 두지 않는다** — `infra/smoke.sh`의 판정 기준(운영 절차서 3.3)보다 엄격하면 배포는 통과했는데 직후에 알림이 울린다. 둘은 커밋 규약 「함께 커밋해야 하는 것 — 인프라」의 짝이다.

| 항목 | 기준 |
|---|---|
| 응답 p95 · 5xx 비율(W1) | 미확정. 운영 요약의 색 경계(p95 빨강 500ms · 5xx 빨강 1%)는 화면 색이지 알림 기준이 아니다 |
| 커넥션 풀 대기 · 타임아웃(W3) | 미확정 |
| CPU(O1) · 가용 메모리(O4) | 미확정 |
| OOM 강제 종료(O5) | 미확정 — 1 이상이 후보 |
| 디스크 사용률 · inode · 예측(O6 · O7) | 미확정 |
| conntrack(O11) · 시간 동기(O12) · systemd 실패 유닛(O14) | 미확정 |
| DB 연결 수(D2) · 오래 열린 트랜잭션(D3) · 복제 지연 시간(D10) | 미확정 |

## 6. 트랜잭션 추적 — 구현 · 반영 대기

**OpenTelemetry 자바 에이전트로 요청 하나의 구간을 거두어 Grafana Cloud Traces(Tempo)로 보낸다.** 기술 선택의 근거는 인프라 기술 스택 4장. 에이전트는 앱 이미지 안에 있고(#364), 무엇을 남기고 어디로 보내는지는 `infra/otel/agent.yaml`이, 켜는 스위치 · 슬롯 메모리 상한은 운영 Compose(`x-app`)가 갖는다(#363). **노드에는 아직 켜지 않았다** — 켜는 것과 Tempo 수신 확인은 반영 묶음이다.

| 항목 | 정한 것 | 근거 |
|---|---|---|
| 잡히는 구간 | 서버 요청(경로 이름 `http.route` 포함) · 그 아래 JDBC 질의(SQL 문장 · 대상 DB) · 트랜잭션 커밋 | **#352 실측** — 운영 이미지 27be1cd(Spring Boot 4.1 · spring-webmvc 7.0.9 · Tomcat 11.0.26 · Java 21) + 에이전트 2.31.1, 업무 경로 셋(구별 집계 · 목록 · 지도 묶음)이 SQL과 같은 추적으로 묶였다 |
| **잡히지 않는 구간** | **Redis** — 캐시 적중으로 Redis만 탄 요청에 Redis 구간이 없었다. 컨트롤러 메서드 구간도 나오지 않았다 | #352 실측. 원인은 확인하지 않았다(Lettuce 7.5.2를 계측하지 않는 것으로 보인다). Redis 지연은 W9가 대신한다 |
| **남기는 추적** | **업무 요청만.** 요청 밖에서 시작한 구간(갱신 배치 · 스케줄의 JDBC · 외부 API 호출)과 `/actuator`(지표 긁기 · 헬스체크) 서버 구간은 버린다 | 거르지 않으면 갱신 배치 한 번이 구간 수만 개를 낸다 — #363 첫 로컬 실측에서 배치(mock) 구간이 쏟아져 로컬 디스크를 채웠다. 수집기가 슬롯마다 15초마다 `/actuator/prometheus`를 긁으므로 그것만으로 슬롯당 하루 5,760개 추적이 된다 |
| 샘플링 | 업무 요청은 **비율 1.0(100%)으로 시작**, 그 아래 구간은 부모를 따른다 | 실사용 요청이 적다 — 2026-09-29 ~ 10-02 APP-01 Nginx의 API 요청 81,101건은 대부분 부하 생성기 LOAD-01이었다. 10%면 보고 싶은 느린 요청이 남지 않는다. 비율은 아래 「도입 뒤 확인」으로 다시 정한다(미확정) |
| **설정 방식** | **선언형 설정 파일**(`-Dotel.config.file`)의 규칙 기반 샘플러 | 위 걸러내기를 **환경 변수로는 할 수 없다** — 부모 없는 JDBC 구간 · `/actuator` 서버 구간을 끄는 키가 없다(에이전트 2.31.1 소스, #363). 규칙 기반 샘플러는 에이전트 안에 있어 jar를 더하지 않는다. **대가 — 공식 문서상 「experimental」이고 샘플러 키에도 `/development`가 붙어 있다**([선언형 설정](https://opentelemetry.io/docs/zero-code/java/agent/declarative-configuration/)). 에이전트를 올릴 때 이 파일이 그대로 읽히고 같은 걸러내기가 되는지 다시 본다. **파일을 쓰면 다른 `OTEL_*` 환경 변수는 읽히지 않는다** — 값은 파일 안 `${env:…}` 치환으로만 들어온다. 예외는 에이전트 기동 전에 읽는 `OTEL_JAVAAGENT_ENABLED`(스위치) |

| 전송 | OTLP/HTTP, gzip 압축 | 추적 하나 평균 1.7 KB → 0.2 KB(#363 로컬 실측, 아래) |

| 로그와 추적 잇기 | 앱 로그 줄에 요청 ID와 함께 에이전트의 `trace_id` · `trace_flags`를 찍는다(#364) — `[요청 ID] [trace_id=<trace_id> flags=<trace_flags>]`(`trace_id=` 글자는 아래 기본 파생 필드에 걸리게 하려는 것, #373) | 요청 ID(Nginx 접근 로그의 `rid`)로 접근 로그와 앱 로그를 잇고, 그 줄의 `trace_id`로 Tempo의 추적을 연다. **샘플러가 버린 요청 · 배치의 줄에도 `trace_id`가 찍힌다** — `trace_flags`의 끝자리가 홀수면 Tempo에 남은 것, 짝수면 버려진 것이다. 로컬 실측에서 남은 구간은 `03`, 버려진 `/actuator` 요청의 로그 줄은 `02`였다 |

**켜는 법**(반영 묶음) — 앱 노드(APP-01 · APP-02)의 `infra/.env`에 세 키를 넣고 슬롯을 다시 만든다. 키 이름과 값의 형식은 `.env.example`의 「추적」.

### 6.1 측정 모드 — 부하 시험 동안만

**부하 시험 결과 보고서의 칸(함수별 시간 · Redis 시간 · 배치 구간)을 채우려고 시험 동안만 추적을 넓힌다**(INF-06, #378). 평시 설정은 위 그대로다. 노드 `infra/.env`의 `OTEL_AGENT_PROFILE=agent-measure`가 운영 Compose에서 `infra/otel/agent-measure.yaml`을 붙이고, 켜고 끄는 절차는 `chaos-harness/measure/README.md`가 갖는다. **켜는 것 자체가 측정 조건이다** — 회차 기록에 남긴다.

| 항목 | 평시(`agent.yaml`) | 측정 모드(`agent-measure.yaml`) | 근거 |
|---|---|---|---|
| 메서드 구간 | 없다 | controller · service · calculator · store · external 패키지와 Redis를 직접 쓰는 클래스, 요청마다 지나는 필터 둘(`JwtAuthenticationFilter` · `RequestIdFilter`)의 메서드. 목록은 `chaos-harness/measure/tools/gen-methods.py`가 소스에서 만든다 | 위 「잡히지 않는 구간」 — 컨트롤러 · 서비스 구간이 없어 「어느 함수가」를 못 본다. 에이전트 2.31.1의 구조형 설정(`instrumentation/development.java.methods.include` — `class` · `methods[].name`, 소스 `MethodConfiguration`)을 로컬에서 확인했다 |
| Redis 시간 | 없다(W9가 대신) | **Redis를 쓰는 클래스의 메서드 구간이 Redis 왕복을 감싼다** — store 패키지 + 그 밖의 다섯(분산 락 · 스트림 티켓 · SSE 발송 · 건축HUB 일일 한도 · 초당 한도). 집계는 이 구간을 Redis 시간으로 센다 | Redis 구간이 잡히지 않는다(위). Redis를 쓰는 클래스(`RedisTemplate` · 락)를 저장소 전체에서 찾아 목록에 넣었다. 안쪽 클래스(락 갱신 `Renewal`)는 `Outer$Inner` 이름으로 적어야 잡힌다(#378 일회용 JVM 실측) |
| BCrypt 대조 · 해싱 | 없다 | `BCryptPasswordEncoder` 의 `matchesNonNull` · `encodeNonNullPassword` 구간 — 우리 소스 밖이라 생성기의 `THIRD_PARTY` 로 넣는다 | 로그인 시간의 대부분이 BCrypt 일 수 있다(#390). 에이전트는 적은 클래스가 **선언한** 메서드에만 구간을 붙이는데 `matches` · `encode` 는 상위 `AbstractValidatingPasswordEncoder` 의 final 이라, 실제 계산을 하는 두 메서드를 적었다(spring-security-crypto 7.1.1 소스 jar) |
| Controller 밖 시간 | — | 요청을 감싸는 필터 구간의 **자기 시간**이 Controller 밖에서 쓰인 시간(Spring MVC 처리 · 응답 JSON 변환 · 보안 필터 체인)이다 — 집계가 그 이름으로 적는다. JSON 변환기(spring-web 의 Jackson 변환기)는 목록에 넣어도 구간이 생기지 않는다 | #390 로컬: Controller · 필터를 넣기 전 빠른 조회(상세 · 알림 · 구별 집계)의 「설명되지 않은 시간」이 48 ~ 67%, 넣은 뒤 2.8 ~ 4.1%. `AbstractJacksonHttpMessageConverter.writeInternal` 은 목록에 넣어도 구간 0 — 에이전트가 `org.springframework` 내부를 계측하지 않는 것으로 본다(BCrypt 는 잡혔다 — 원인은 확인하지 않았다) |
| 행마다 불리는 함수 | — | **목록에서 뺀다** — 추적 하나에 100번 넘게 불린 것. 그 비용은 프로파일러로 본다 | #378 로컬 실측 — 기동 따라잡기 배치 한 번이 구간 약 26만 개, 지도 마커의 거리 계산이 요청 하나에 498 ~ 1,003번. 실데이터 클라이언트의 항목 해석 함수는 로컬에서 돌지 않아 소스를 보고 뺐다(정적 판단) |
| 요청 밖 구간 | 버린다 | 남긴다(배치 · 스케줄 · 외부 호출). `/actuator`는 그대로 버린다 | 배치 동시 시나리오의 시간을 본다. 시험 중 배치는 대개 꺼 둔다 |
| 사본 | 없다 | 부하 생성기의 수신기(OTel Collector, `chaos-harness/measure/node/trace-receiver.sh`)로 두 번째 내보내기(`OTEL_MEASURE_RECEIVER_ENDPOINT`) | Tempo는 보존 14일(2.3)이고 읽으려면 토큰이 든다. 파일 내보내기(`otlp_file/development`)는 2.31.1에서 `file://`을 무시하고 표준 출력으로 내보낸다(#378 로컬 실측) — 앱 로그와 섞여 Loki로 간다 |

**대가** — 구간 수와 내보내기 하나가 는다. 같은 요청 · 같은 시간으로 평시와 비교한 로컬 실측은 #378 「로컬 실측」 코멘트에 있다 — 슬롯 메모리 최대 627 → 644 MiB(상한 680), 응답 시간은 회차가 1번씩이라 흔들림과 구분되지 않았다. 노드 값은 시험 직전 반영 때 잰다.

**Grafana Cloud 예산(2.3)** — 측정 모드도 첫 내보내기(Grafana)를 그대로 두므로 늘어난 구간이 추적 예산(월 50GB)에 들어간다. 로컬에서 수신기 파일이 요청 하나에 약 17 KB(압축 전 JSON)였다 — 평시 추적 하나 1.7 KB(압축 전, 위 로컬 실측)의 약 10배다. 압축 비율이 평시(약 8 : 1)와 같다고 보면 요청 하나에 약 2 KB, 100 RPS · 10분 회차가 약 120 MB다. **추정이다** — 반영 뒤 Grafana Cloud 사용량 화면으로 확인한다. 배치가 켜진 채 측정 모드를 켜면 이 계산이 무너진다(기동 배치 한 번 약 26만 구간) — `measure-mode.sh`가 배치 넷이 꺼져 있을 때만 켠다.

## 7. 스냅샷 점검

상시로 두면 종류가 많아 한도를 넘거나, 상시로 볼 까닭이 없는 것이다. **손으로 뜨고 기록한다** — 자동화는 하지 않는다(구현 묶음 밖).

| 항목 | 언제 | 어떻게 |
|---|---|---|
| CPU 크레딧 · 초과 사용(O15) | 노드를 오래 켠 작업 뒤 | `aws cloudwatch get-metric-statistics` — `CPUCreditBalance` · `CPUSurplusCreditsCharged` |
| 질의 통계 전체(S2) | 성능 조사 · 시험 전후 | 운영 절차서 2장 「질의 통계」 — 구간을 재려면 시작 전 초기화 |
| 통계 행 수 vs 실제(S4) · 컬럼 통계(S5) · 추정 vs 실제(S6) | 대량 적재 · 배치 구조 변경 뒤, 질의가 갑자기 느려졌을 때 | `pg_class.reltuples` · `pg_stats` · `EXPLAIN (ANALYZE, BUFFERS)` — 대표 질의는 지도 범위 · 구별 집계 · 목록 |

## 8. 하지 않는 것

| 항목 | 이유 |
|---|---|
| 자원 압박(PSI) | 네 노드 커널에서 꺼져 있다(`/proc/pressure` 없음). 켜려면 부팅 옵션 `psi=1`과 재부팅이 든다. O2 · O8로 대신한다 |
| 질의별 계획 수립 시간(`pg_stat_statements.track_planning`) | PG 문서: 「같은 구조의 문장을 많은 동시 연결이 실행해 적은 수의 항목을 다투면 눈에 띄는 성능 저하가 있을 수 있다」([PG 17](https://www.postgresql.org/docs/17/pgstatstatements.html)) — 지도 조회가 그 모양이다. 계획 시간은 따로 보지 않는다(추적의 JDBC 구간은 계획 + 실행을 합친 시간이다) |
| `auto_explain` · 느린 질의 로그 — **상시로는** | **DB 노드에는 로그 전송기(Vector)가 없어** 기록이 노드 밖으로 나가지 않는다. 느린 SQL은 S1과 추적(6장)이 찾는다. (`auto_explain`은 `session_preload_libraries`로 넣으면 DB 재시작 없이 새 세션부터 적용된다 — [PG 17](https://www.postgresql.org/docs/17/auto-explain.html). 재시작이 이유가 아니다.) **부하 시험 동안에는 켠다** — DB 단위 설정으로 켜고, 회차 구간의 기록을 컨테이너 로그에서 가져온다(`chaos-harness/measure/node/auto-explain.sh` · `collect.sh`, #378). 운영에서 실제로 그 계획으로 도는지가 결과 보고서의 칸이다 |
