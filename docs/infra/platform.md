# 전월세 부동산 금융 플랫폼 — 서버 운영 기반 설계서

> Rocky Linux 이전 후의 서버 · 네트워크 · 저장소 · 계정 · 정기 작업
> 네트워크 격리 · 파일시스템 · NAS(NFS) · 계정 관리 · 스케줄링 · OS 보안 · 이전 절차
> ※ 기능이 왜 필요한지는 `docs/features/infra.md`(INF-07 ~ 09)를, 노드 배치와 포트는 `docs/infra/system.md`를, 손으로 밟는 순서는 `docs/infra/runbook.md` 9장을 따른다.
> 작성 기준일 : 2026년 9월

## 1. 문서 목적

1차 배포(EC2 · Amazon Linux 2023)를 **Rocky Linux 9**로 옮긴 뒤, 웹 서비스를 안정적으로 운영하기 위해 **현재 구성(이중화 · 무중단 배포 · 복제 · 백업) 외에 더하는 서버 운영 기반**을 정한다(2026-09-19 사용자 결정).

| 다루는 것 | 다루지 않는 것 |
|---|---|
| 네트워크 격리(VPC · 서브넷 · NAT · 접근 통제) · 네트워크 이중화 | 모니터링 · 알림 — **하지 않는다**(INF-05 차기) |
| 파일시스템 구성(EBS · XFS) | 애플리케이션 · DB 설계 — 지금 설계 그대로(INF-01 ~ 04) |
| NAS(NFS) — 백업 저장소 | 부하 · 장애 시험(INF-06 차기) |
| 계정 관리(AWS · OS) | 도메인 · TLS(공인 IP + HTTP 유지) |
| 정기 작업 스케줄링 · OS 보안 기준 · 이전 절차 | |

**각 결정은 조사한 근거를 함께 적는다.** 근거 없이 그럴듯한 값을 적지 않고, 정할 수 없는 값은 「미확정」과 확정 시점을 적는다.

## 3. 네트워크 격리 (INF-07)

### 3.1 구성

```
                    인터넷
                      │
              ┌───────┴────────┐  Internet Gateway
              │                │
   ┌──────────┴── 공개 서브넷 (AZ-a) ─────────┐
   │  APP-01  (Elastic IP · 80 공개 · 22 운영자) │
   │  NAT-01  (사설 서브넷의 인터넷 출구)          │
   └──────────┬───────────────────────────────┘
              │ 사설 경로만
   ┌──────────┴── 사설 서브넷 (AZ-a) ──┐   ┌── 사설 서브넷 (AZ-c) ──┐
   │  DB-01 (Primary)  NAS-01 (NFS)     │   │  DB-02 (Standby)        │
   └────────────────────────────────────┘   └─────────────────────────┘
              │
        S3 게이트웨이 엔드포인트 — WAL · 백업 사본은 인터넷을 거치지 않는다
```

노드 배치 · 포트별 허용 범위는 시스템 구성서 4장이 갖는다. 여기에는 **그렇게 나눈 이유**만 둔다.

- **DB · NAS를 사설 서브넷에 두는 이유:** 공인 주소가 없으면 인터넷에서 직접 닿을 경로 자체가 없다. 보안 그룹을 실수로 열어도 도달할 수 없어 방어가 두 겹이 된다. 사용자 메모의 「외부 침입이 어렵도록 NAT 구조」를 VPC로 옮긴 것이다.
- **VPC · 서브넷 CIDR은 미확정**이다. VPC 생성 작업에서 정해 시스템 구성서 4장에 적는다(예: `/16` VPC 안에 서브넷별 `/24`).

### 3.2 인터넷 출구 — NAT 인스턴스를 쓴다

사설 서브넷의 DB · NAS도 OS 보안 갱신(`dnf`)과 컨테이너 이미지 수신에 인터넷 출구가 필요하다.

| 방식 | 비용(개략) | 가용성 | 판단 |
|---|---|---|---|
| NAT Gateway(관리형) | 시간당 과금 + 처리 GB당 과금. us-east-1 기준 시간당 $0.045(월 약 $33) + GB당 $0.045이고 리전에 따라 더 높다. **서울 단가는 AWS VPC 요금 페이지로 확인한다 — 미확정** | AWS가 AZ 안에서 이중화 | 배제 — 쓰지 않아도 매달 붙는 고정비로, 이 규모의 평시 합계(시스템 구성서 6장)에서 큰 몫이다. 인프라 기술 스택 1.1 「관리형 서비스에 의존하지 않는다 · 비용 상한 우선」 |
| **NAT 인스턴스(NAT-01)** | 최소 사양 인스턴스 1대(월 수 달러 수준) | 단일 인스턴스 — 죽으면 사설 서브넷의 **밖으로 나가는 길만** 끊긴다 | **채택** |

- **NAT-01이 죽어도 서비스는 멈추지 않는다.** 사용자 요청은 APP-01로 들어오고, APP-01 ↔ DB는 VPC 내부 경로다. 끊기는 것은 DB · NAS의 패키지 갱신과 이미지 수신뿐이라 복구를 기다릴 수 있다.
- NAT 인스턴스는 **소스/대상 확인(source/destination check)을 꺼야** 자기 주소가 아닌 패킷을 전달한다(AWS VPC 문서). 커널 IP 포워딩 + firewalld 마스커레이드로 구성한다.
- NAT-01의 OS도 Rocky Linux 9로 통일한다 — 관리 도구 · 절차가 하나로 끝난다.
- **S3 게이트웨이 엔드포인트를 둔다.** 추가 요금이 없고(AWS VPC 문서) WAL 아카이브 · 백업 사본이 NAT를 거치지 않아 NAT-01 장애와 무관해진다.

### 3.3 접근 통제 — 세 겹

| 겹 | 수단 | 역할 |
|---|---|---|
| 1 | **보안 그룹**(상태 기반, 인스턴스 단위) | 1차 방어. 노드별 허용 표는 시스템 구성서 4장 |
| 2 | **firewalld**(호스트) | 보안 그룹이 잘못 열려도 호스트가 한 번 더 막는다. Rocky 기본 활성 |
| 3 | **Docker 포트 루프백 바인딩** | Docker가 게시한 포트는 firewalld를 **우회한다** — Docker가 iptables/nftables에 DNAT 규칙을 직접 넣어 호스트 입력 규칙보다 먼저 목적지를 바꾸기 때문이다(firewalld 프로젝트 「Strict filtering of Docker containers」). 그래서 앱 슬롯 · web은 이미 `127.0.0.1:포트`로만 게시한다(`infra/docker-compose.yml`). 새 컨테이너 포트도 이 규칙을 따른다 |

**예외 — DB 노드의 5432.** PostgreSQL은 APP-01 · DB-02가 다른 노드에서 붙어야 하므로 루프백에만 게시할 수 없고, 게시된 포트라 firewalld도 거치지 않는다. **이 포트를 지키는 것은 보안 그룹과 사설 서브넷 두 겹이다.** 게시 주소를 노드의 사설 IP 하나로 좁히고(`0.0.0.0` 금지), 보안 그룹의 출발지를 APP-01 · 상대 DB 노드로 한정한다. Docker의 `DOCKER-USER` 체인으로 호스트 규칙을 한 겹 더 두는 방법은 구축 때 검토한다 — 미확정.

### 3.4 운영자 접속

| 방식 | 판단 |
|---|---|
| **APP-01을 경유하는 SSH(ProxyJump)** | **채택.** 보안 그룹이 22를 운영자 IP에만 연다. 사설 노드는 APP-01의 사설 주소에서 오는 22만 받는다. 별도 배스천 인스턴스를 두지 않는다 |
| 전용 배스천 인스턴스 | 배제 — 인스턴스 비용과 관리 대상이 하나 는다 |
| AWS Systems Manager Session Manager | 대안으로 기록 — 22를 아예 닫고 IAM으로 접속을 통제할 수 있어 보안상 더 낫다는 평가가 많다. 다만 에이전트 · IAM 역할 · (NAT 없이 쓰려면) 인터페이스 엔드포인트가 필요하고 AWS 전용이다. 인프라 기술 스택 1.1 이식성 원칙에 따라 기본은 SSH로 두고, 22 노출이 문제가 되면 옮긴다 |

- SSH는 **공개키 인증만** 허용한다(`PasswordAuthentication no`, `PermitRootLogin no`) — 시스템 구성서 4장의 기존 방침.

### 3.5 네트워크 이중화 — NIC 티밍 대신

사용자 메모의 「네트워크 이중화(NIC 티밍)」는 온프레미스에서 NIC 두 개를 하나로 묶어 한쪽 회선 · 포트 장애를 견디는 구성이다. **EC2에서는 같은 목적을 다른 수단으로 달성한다.**

| 온프레미스 수단 | EC2에서 | 근거 |
|---|---|---|
| NIC 티밍 · 본딩(대역폭 합산 · 링크 장애 대비) | **쓰지 않는다** | AWS 문서 — 네트워크 인터페이스를 추가로 붙여(예: NIC 티밍 구성) 대역폭을 늘리거나 두 배로 만들 수 없다. 같은 서브넷의 ENI를 여러 개 붙이면 비대칭 라우팅 문제가 생길 수 있다. 물리 링크는 AWS가 관리하므로 인스턴스 쪽에서 링크 이중화를 구성할 대상이 없다 |
| 스위치 · 회선 이중화 | **가용 영역 분산** — DB-01(AZ-a) · DB-02(AZ-c) | 한 AZ 장애에도 standby가 다른 AZ에 남는다. 승격 절차는 운영 절차서 6장(기존) |
| 공인 IP 이중화 · 전환 | **Elastic IP 재지정** | APP-01을 교체할 때 같은 공인 주소를 새 인스턴스로 옮긴다. 이전 절차(9장)의 전환 수단이다 |
| 서버 이중화 | 앱 2슬롯(INF-01) · DB 복제(INF-03) — 기존 | 변경 없음 |

- **APP-01은 여전히 단일 AZ · 단일 노드다.** 노드 자체의 장애는 두 슬롯으로도 막지 못한다 — 시스템 구성서 3장의 기존 한계. 확장 지점(두 번째 앱 노드 + 로드 밸런서)은 그대로 기록만 둔다.

### 3.6 사설 구간의 암호화

- 인스턴스 간 트래픽을 하드웨어에서 자동 암호화하는 것은 **지원 인스턴스 유형에 한정**된다. `t3` · `t4g`는 대상이 아니다(AWS 문서 · 사용 사례).
- 그래서 사설 서브넷 안의 PostgreSQL 복제 · NFS는 **평문**이다. 사설 서브넷 + 보안 그룹으로 경로를 좁혀 받아들인다. 인스턴스 유형이 정해지면 이 판단을 다시 본다 — **미확정**.

## 4. 파일시스템 (INF-09)

### 4.1 볼륨 분리

| 노드 | 루트 볼륨 | 데이터 볼륨(별도 EBS) | 분리 이유 |
|---|---|---|---|
| APP-01 | OS | `/var/lib/docker` — 이미지 · 컨테이너 · 로그 | 이미지 3세대 보존과 컨테이너 로그가 늘어도 OS가 멈추지 않게 |
| DB-01 · DB-02 | OS | `/srv/pgdata` — PostgreSQL 데이터 디렉터리 | DB 파일이 루트를 채우면 SSH 로그인조차 실패한다. 볼륨 단위 스냅샷 · 확장이 가능해진다 |
| NAS-01 | OS | `/srv/nfs` — 백업 저장소 | 5장 |
| NAT-01 | OS만 | — | 데이터가 없다 |

### 4.2 파일시스템 · 마운트 규칙

| 규칙 | 근거 |
|---|---|
| **XFS** | Rocky(RHEL 계열) 기본 파일시스템. AWS EBS 문서의 예시도 XFS다 |
| `/etc/fstab`은 **UUID**로 적는다 | 장치 이름(`/dev/nvme1n1` 등)은 재부팅 · 재부착에서 바뀔 수 있다 |
| 데이터 볼륨에는 **`nofail`** | AWS 문서 권고 — 볼륨이 붙지 않은 채 부팅돼도 인스턴스가 부팅에 실패하지 않게 한다 |
| **LVM을 쓰지 않는다** | EBS는 붙은 채로 크기를 늘릴 수 있고(Elastic Volumes), 전체 디스크를 쓰는 XFS는 `xfs_growfs <마운트 지점>`으로 늘린다(AWS 문서). 볼륨을 합치거나 LVM 스냅샷을 쓸 요구가 없어 계층을 하나 줄인다 |
| 볼륨 유형 · 크기 **미확정** | 시스템 구성서 6장의 60 GB 개략치를 기준으로 인스턴스 생성 때 정한다 |

- 예(형식만): `UUID=<blkid 값>  /srv/pgdata  xfs  defaults,nofail  0 2`

## 5. NAS — 백업 저장소 (INF-08)

### 5.1 역할

사용자 메모 「DB 파일 백업 경로를 NAS로 잡아 NAS를 구성」을 따른다. **NAS-01은 백업을 한곳에 모으는 NFS 서버다.**

| 들어오는 것 | 누가 | 주기 |
|---|---|---|
| 논리 백업(`pg_dump -Fc`) — **DB-01에서 암호화한 뒤** 보낸다 | DB-01 | 일 1회 — 7장 |
| 운영 설정 사본(`infra/` · 암호화한 `.env`) | APP-01 | 변경 시 · 주 1회 |

- **기존 물리 백업(`pg_basebackup` 주 1회 + WAL 연속 아카이빙 → S3)은 그대로 둔다**(INF-04). NAS는 여기에 **논리 백업의 자리**를 더한다. 논리 백업은 테이블 단위 복원 · 다른 버전으로의 이전에 쓰고, 물리 백업 + WAL은 시점 복구(PITR)에 쓴다 — 둘은 대체가 아니라 보완이다(PostgreSQL 문서 25장 · 다수 운영 가이드의 권장 조합).
- **백업은 NAS에 닿기 전에 암호화한다.** 인프라 기술 스택 3장 「백업 파일은 전송 전 암호화하고 복호화 키를 분리 보관한다」(USER 자격 정보) — 사설 구간의 NFS가 평문이고(3.6) NAS 디스크의 파일도 평문이면 이 원칙이 깨진다. 암호화 도구는 **미확정**(Rocky 기본 패키지 중에서 구축 때 정한다), 복호화 키는 NAS에 두지 않는다.
- **NAS 자체가 단일 장애점이다.** NAS의 내용은 주 1회 S3로 사본을 보낸다(암호화, 7장) — 백업의 백업.

### 5.2 자체 NFS 서버를 쓴다

| 방식 | 판단 |
|---|---|
| **EC2 + EBS + NFS(`nfs-utils`)** | **채택.** EBS 요금만 든다. Rocky 표준 패키지로 구성해 온프레미스로 그대로 옮길 수 있다(기술 스택 1.1 이식성). 사용자 메모의 학습 목표와 맞는다 |
| Amazon EFS(관리형 NFS) | 배제 — GB당 요금이 EBS보다 높고(공개 요금 비교 자료), 관리형 의존이다. 여러 AZ 이중화가 필요해지면 다시 본다 |

### 5.3 구성 규칙

| 규칙 | 근거 |
|---|---|
| **NFSv4만** — 포트 2049/TCP 하나 | 서버는 기본으로 v3도 함께 제공한다. `/etc/nfs.conf`의 `[nfsd]`에 `vers3=n`을 두어 v4 전용으로 만들고, 그러면 `rpcbind`를 네트워크에 열 필요가 없다(RHEL 9 문서 「Configuring an NFSv4-only server」) |
| 공유는 **사설 주소 단위로** 허용 — `*` 금지 | 공유 대상을 DB-01 · DB-02 · APP-01의 사설 IP로 한정한다 |
| **`root_squash` 유지** — `no_root_squash` 금지 | 클라이언트의 root가 공유 파일에 root 권한을 갖지 못하게 한다. 기본값이다 |
| `sync` | 백업 파일이 서버 디스크에 기록된 뒤 응답한다 |
| 클라이언트 fstab에 `_netdev,nofail` | 네트워크가 올라온 뒤 마운트하고, NAS가 없어도 부팅은 진행한다 |
| **정기 작업에 실행 시간 상한** | 기본 hard 마운트에서는 NAS가 멈추면 그 경로를 건드리는 작업이 끝나지 않고 멈춘 채 남아 저널에 실패도 남지 않는다. 그래서 NAS를 쓰는 timer 서비스에 `TimeoutStartSec`를 둬 멈추면 실패로 끝나고 기록되게 한다. 값은 미확정 |
| 백업 계정 **UID · GID를 모든 노드에서 같게** | NFS는 이름이 아니라 숫자 ID로 권한을 본다 — 6장 |
| SELinux | Rocky는 SELinux가 enforcing이다. NFS 공유의 쓰기 · 컨테이너가 NFS 경로를 쓰는 경우 필요한 boolean · 파일 컨텍스트는 **구축 때 거부 로그(`ausearch` · `audit2why`)로 확인해 정한다 — 미확정.** SELinux를 끄는 것으로 해결하지 않는다 |

- 공유 경로 예(형식만): `/srv/nfs/backup  <DB-01 사설IP>(rw,sync,root_squash)  <DB-02 사설IP>(rw,sync,root_squash)  <APP-01 사설IP>(rw,sync,root_squash)`

### 5.4 보존

| 대상 | 보존 | 비고 |
|---|---|---|
| 논리 백업 | **미확정** | 첫 백업 크기 · NAS 볼륨 크기를 보고 정한다 |
| 설정 사본 | **미확정** | 같다 |
| S3 사본 | 물리 백업과 같게 | 인프라 기술 스택 3장 `pg_basebackup` 행의 4주 보존 |

## 6. 계정 관리 (INF-09)

### 6.1 AWS 계정

| 규칙 | 이유 |
|---|---|
| 루트 계정은 MFA를 켜고 일상 작업에 쓰지 않는다 | 루트는 모든 권한을 갖고 제한할 수 없다 |
| 작업용 IAM 사용자 · 액세스 키는 **필요한 서비스(EC2 · VPC · S3)로 좁힌다** | 키가 새도 피해 범위를 줄인다 |
| 액세스 키는 운영자 PC의 AWS CLI 설정에만 둔다 — 저장소 · 서버에 두지 않는다 | 서버가 S3를 쓰는 권한은 **인스턴스 역할(IAM Role)**로 준다. 서버에 키 파일이 없어진다 |

### 6.2 OS 계정

| 계정 | 로그인 | 권한 | 용도 |
|---|---|---|---|
| 운영자 개인 계정 | SSH 공개키 | `wheel`(sudo) | 사람이 쓰는 유일한 로그인. 누가 무엇을 했는지 남는다 |
| `rocky`(AMI 기본) | 초기 설정 후 **SSH로 들어올 수 없게** | — | 공용 계정은 행위자를 구분하지 못한다. **`passwd -l` · `usermod -L`로는 막히지 않는다** — Rocky의 sshd는 `UsePAM yes`라 잠긴 계정을 「비밀번호가 없는 것」으로만 보고 공개키 로그인을 허용한다. `authorized_keys`를 지우고 계정을 만료시키며(`usermod --expiredate`) 셸을 `nologin`으로 바꾼다. 확인: `rocky`로 SSH 시도가 거부된다 |
| `deploy` | SSH 공개키 | `docker` 그룹 | 배포 스크립트 실행. **`docker` 그룹은 root와 같은 권한이다**(Docker 공식 문서) — sudo는 주지 않지만 사실상 관리자 권한임을 알고 키를 관리한다 |
| `backup` | **로그인 불가**(`nologin`) | 백업 디렉터리 소유 | 정기 작업이 이 계정으로 돈다. **UID · GID를 모든 노드에서 같은 값으로 고정**(NFS — 5.3). 값은 **미확정**, 서버 준비 때 정한다 |
| `root` | SSH 금지 | — | `PermitRootLogin no` |

| 규칙 | 이유 |
|---|---|
| 비밀번호 로그인 금지 — 공개키만 | 대입 공격이 성립하지 않는다(시스템 구성서 4장 기존 방침) |
| sudo는 `wheel` 그룹에만 | 권한을 계정이 아니라 그룹으로 관리한다 |
| 계정 추가 · 삭제는 운영 절차서 9장 순서로, 전 노드에 같게 | 노드마다 계정이 달라지면 NFS 권한과 감사 기록이 어긋난다 |
| 컨테이너 안 프로세스는 호스트 계정과 별개 | 앱 이미지는 이미 비루트 사용자로 돈다(`backend/Dockerfile`) |

## 7. 정기 작업 스케줄링 (INF-09)

### 7.1 수단 — systemd timer를 쓴다

사용자 메모의 「crontab으로 스케줄링」과 같은 목적이다. Rocky 9는 cron(`cronie`)과 systemd timer를 모두 쓸 수 있다.

| 비교 | cron | **systemd timer(채택)** |
|---|---|---|
| 서버가 꺼져 있던 시각의 작업 | 건너뛴다 | `Persistent=true`면 다음 부팅 때 실행한다 |
| 실행 기록 | 메일 · 직접 남긴 로그 | `journalctl -u <작업>`에 성공 · 실패 · 출력이 남는다 — **모니터링 없이 결과를 확인할 수단**이 된다 |
| 동시 실행 방지 · 의존 | 직접 구현 | 서비스 단위로 한 번에 하나, 네트워크 · 마운트 이후 실행을 선언할 수 있다 |
| Rocky의 보안 갱신 | — | `dnf-automatic`이 이미 systemd timer다 |

- cron을 금지하지는 않는다. 다만 이 문서의 정기 작업은 모두 timer로 둔다 — 확인 수단이 하나가 된다.

### 7.2 작업 목록

| 작업 | 노드 | 시각(서울) | 내용 |
|---|---|---|---|
| 논리 백업 | DB-01 | 매일 02:00 | `pg_dump -Fc` → 암호화 → NAS `/srv/nfs/backup` → 보존 기간 지난 것 삭제 |
| NAS → S3 사본 | NAS-01 | 매주 일 04:00 | 암호화 후 S3로(키는 백업 복호화 키와 분리 보관 — 기술 스택 3장) |
| 설정 사본 | APP-01 | 매주 일 01:00 | `infra/` · 암호화한 `.env` → NAS |
| 이미지 정리 | APP-01 | 매주 | 배포 스크립트가 남긴 3세대 밖의 이미지 · 중지된 컨테이너 정리 |
| 보안 갱신 | 전 노드 | 매일(분산) | `dnf-automatic` — **보안 갱신만 설치, 자동 재부팅 안 함.** 커널 갱신은 월 1회 계획 재부팅(운영 절차서 2장) |

- **승격 뒤에는 새 primary가 논리 백업을 이어받는다.** timer는 DB-01 · DB-02 양쪽에 두고, 작업이 시작할 때 자기가 primary인지(`pg_is_in_recovery()`가 거짓) 확인해 standby면 아무것도 하지 않고 끝낸다 — 페일오버 절차에 timer 전환 단계를 넣지 않아도 된다.
- **03:00은 비운다.** 등기 재조회 배치(RISK-08)가 03:00에 돈다(`application.yml`). 백업 · 사본이 그 시각과 겹치지 않게 앞뒤로 둔다.
- **서버 시간대는 `Asia/Seoul`**로 둔다 — 작업 시각 · 로그를 운영자가 바로 읽는다. 앱은 코드에서 서울 시간대를 명시하므로 영향이 없다.
- 시각 · 보존은 **잠정** — 운영 1개월 뒤 실행 시간 · 용량으로 조정한다.

| 항목 | 기준 | 근거 |
|---|---|---|

| 저널 | `journald` 영구 저장 + 용량 상한 | 정기 작업 결과 확인의 자리다(7.1) |

## 9. Amazon Linux 2023 → Rocky Linux 9 이전

**옮길 대상은 OS 준비와 데이터다.** 이미지 · Compose · 배포 스크립트는 그대로 쓴다(시스템 구성서 2.1).

| 단계 | 내용 | 되돌리는 길 |
|---|---|---|
| 1 | Rocky 노드를 **새로 만든다**(기존 인스턴스를 제자리에서 바꾸지 않는다). 3 ~ 8장 기준으로 준비 | 기존 노드가 그대로 서비스 중 |
| 2 | 데이터 이전 — DB는 논리 백업 복원 또는 새 노드를 standby로 붙여 복제로 따라잡게 한다 | 기존 DB가 그대로 primary |
| 3 | 새 노드에서 운영 절차서 3장 배포와 확인(분산 · 한쪽 정지 · SSE) | 같다 |
| 4 | **점검 모드로 쓰기를 막고**(운영 절차서 4.2) 마지막 차분을 맞춘 뒤 **Elastic IP를 새 APP-01로 옮긴다** | Elastic IP를 옛 APP-01로 되돌린다 |
| 5 | 일정 기간 옛 노드를 정지 상태로 보존한 뒤 삭제 | 정지된 옛 노드를 다시 켠다 |

- 세부 명령 순서는 운영 절차서 9장. 실제로 밟으며 기록해 그 절을 채운다(운영 절차서 1장 원칙).
