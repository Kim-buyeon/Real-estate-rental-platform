> 부하 시험 · 장애 주입 · 용량 산정

> ※ 가용성 설계는 `docs/features/infra.md`를, 지표 정의는 `docs/infra/observability.md`를 따른다.
> 작성 기준일 : 2026년 8월

## 1. 문서 목적 및 원칙

설계는 문서에 적었다고 성립하지 않는다. 본 문서는 `docs/features/infra.md`가 정의한 인프라 기능이 실제로 동작하는지 확인하는 방법을 정의한다.

두 종류의 시험을 다룬다.

| 구분 | 목적 | 산출물 |
|---|---|---|
| 부하 시험 | 현 사양의 한계를 수치로 확정하고 병목을 특정한다 | 용량 산정 리포트 |
| 장애 주입 시험 | 인프라 구성 요소가 정지했을 때 설계대로 동작하는지 확인한다 | 시나리오별 결과서 9종 |

### 원칙

- **부하는 분석 대상이 아니라 실험 변수다.** 합성 트래픽을 분석해 증설을 권고하는 것은 스스로 넣은 값을 스스로 꺼내는 순환논리다. 부하를 계단식으로 올려 한계를 측정하는 것만이 실사용 트래픽이 없는 환경에서 성립하는 방법이다.
- **시험의 목적은 통과가 아니라 차이의 발견이다.** 기대 동작대로 되지 않았다면 그것이 성과다. 완화해서 기록하지 않는다.
- **측정하지 못한 값은 미측정으로 남긴다.** 그럴듯한 숫자로 채우지 않는다.
- **시험 중 발견한 문제를 그 자리에서 고치지 않는다.** 코드를 고치면 이후 결과가 앞선 결과와 비교 불가능해진다.

## 2. 부하 시험과 용량 산정

### 2.1 사용하는 프로파일

부하 패턴 자체는 `docs/infra/traffic.md`가 정의한다. 본 장은 그 프로파일을 인가한 결과를 **어떻게 판정할 것인가**만 다룬다.

| 목적 | 프로파일 | 비고 |
|---|---|---|
| 포화점 실측 | **T2 계단식** | 10 → 200 RPS, 각 단계 5분 |
| 기준선 확보 | T1 기준선 | 회귀 비교의 기준값 |
| 캐시 기여 측정 | T5 캐시 콜드 ↔ T3 대조 | 두 결과의 차이가 캐시의 기여분 |
| 누수 확인 | T4 지속 | 2시간. 힙·스레드·커넥션 모두 확인 |

### 2.2 측정 항목

단계마다 다음을 함께 기록한다. 응답 시간만 기록하면 **무엇이 먼저 포화되었는지** 알 수 없어 증설 방향을 판단할 수 없다.

- 응답: p95 · p99 · 5xx 비율 · 실제 처리량
- 자원: CPU · 메모리 · GC 일시정지
- 병목 후보: Tomcat 스레드 busy/max, HikariCP active/pending, PostgreSQL 커넥션 수·슬로우 쿼리, Redis 적중률·축출
- 누수 후보: `jvm_threads_live` (T4 지속 시험)
- 외부: 연동별 응답 시간, 서킷 상태

### 2.3 포화점 판정

다음 중 먼저 도달하는 지점을 포화점으로 한다.

| 판정 조건 |
|---|
| 대상 엔드포인트의 p95가 500ms를 초과 |
| 5xx 비율이 1%를 초과 |
| 처리량이 목표 RPS를 따라가지 못하고 정체 |

포화점은 구간이 아니라 값으로 특정한다. "100 RPS 근처"가 아니라 "88 RPS에서 p95 512ms"처럼 기록한다.

**개선 후에는 동일 조건으로 재측정한다.** 병목을 인덱스나 캐시로 해소한 뒤 같은 프로파일을 반복해 한계가 어디까지 올라갔는지 대조한다. 이 전후 비교가 성능 개선의 유일한 증거다. 조건이 달라졌다면(데이터 규모 변경, 캐시 상태 차이) 비교가 성립하지 않으므로 그 사실을 명시한다.

### 2.4 용량 산정 리포트

시험 결과를 다음 형식으로 정리한다. 이것이 `docs/infra/runbook.md` 2장 월 1회 점검 항목인 "용량 추이 대비 증설 시점 판단"의 판단 근거가 된다.

| 항목 | 내용 |
|---|---|
| 실측 한계 RPS | p95 500ms를 유지하는 최대 처리량 |
| 포화 지점 | 가장 먼저 한계에 도달한 구성 요소와 그 시점의 수치 |
| 현재 헤드룸 | 예상 피크(8 RPS) 대비 배수 |
| 증설 불필요 구간 | 한계 RPS를 DAU로 환산한 값 |
| 증설 권고 방향 | 포화 원인에 따른 우선 조치 |
| 축소 가능성 | 사양을 낮춰도 목표를 유지하는지 |
| 알림 임계 조정 | `docs/infra/observability.md` 5장의 미검증 임계값을 실측 기준으로 갱신 |

결론은 다음과 같은 형태로 서술한다.

> 현 사양(2 vCPU / 4 GB, 앱 2 프로세스)에서 p95 500ms를 유지하는 한계는 약 XX RPS이며, 포화 원인은 CPU가 아니라 DB 커넥션 풀이었다. 예상 피크 8 RPS 대비 헤드룸은 약 N배이므로 DAU 약 X,000까지 증설이 불필요하다. 그 이상에서는 vCPU 증설보다 앱 노드 추가가 유효하다.

**증설 방향은 포화 원인에 따라 달라진다.** 자원을 늘리는 것이 항상 답은 아니다.

| 먼저 포화된 자원 | 권고 방향 |
|---|---|
| CPU | vCPU 증설 또는 앱 노드 추가. 둘 다 유효 |
| Tomcat 스레드 | 커넥션 풀이 여유 있는데 스레드가 마르면 **외부 API 대기**다. 사양 증설로 해결되지 않는다 |
| 커넥션 풀 · DB 커넥션 | **노드 추가는 오히려 악화된다.** 풀 크기, 애플리케이션의 트랜잭션 경계, DB 사양을 먼저 검토 |
| 메모리 · GC 일시정지 | 힙 설정 조정 후 재측정. 그 뒤에도 부족하면 메모리 증설 |
| 외부 API 대기 | **사양과 무관하다.** 캐시 적중률, 타임아웃, 병렬 호출 구조를 조정 |
| 디스크 I/O | 스토리지 유형 변경. vCPU 증설은 효과 없음 |

## 3. 장애 주입 시험

관측과 이중화가 실제로 동작하는지는 장애를 만들어 확인해야 알 수 있다. 아래 시나리오를 순서대로 시험하고 결과를 기록한다.

대상은 인프라 구성 요소의 정지와 자원 고갈이다.

| # | 시나리오 | 주입 방법 | 기대 동작 | 검증 지표 |
|---|---|---|---|---|
| 1 | 앱 인스턴스 1대 다운 | `docker stop app-1` | 30초 내 upstream 제외, 조회 요청 손실 0건 | `probe_success`, 5xx 비율, upstream 상태 |
| 2-a | 앱 전체 다운 (노드 생존) | 두 슬롯 정지 | 점검 페이지, **내부** critical 알림 1분 내 발송 | `probe_success`·`probe_http_status_code`, 알림 수신 시각 |
| 2-b | 노드 전체 정지 | 클라우드 콘솔에서 인스턴스 정지 | **외부 경로 감시 알림 도착. 내부 알림 없음** | 외부 알림 수신 시각, 내부 알림 부재 확인 |
| 3 | DB primary 다운 | `docker stop postgres-primary` | `docs/infra/runbook.md` 6.1절로 **30분 내** 복구(1등급 RTO), 이어서 6.2절 페일백 완료 | 단계별 실측 소요, 승격 직후 처리량 |
| 4 | Redis 다운 | `docker stop redis` | 조회 기능 유지, 재로그인 유도 | 조회 p95, 5xx 비율 |
| 5 | 배포 중 요청 유실 | 부하 중 슬롯 순차 교체 배포 | 조회 요청 실패 0건 | k6 실패 건수 |
| 6 | 디스크 임계 | 여유 공간에서 5 GB만 남기고 채워 90% 도달 | warning·critical 알림, 정리 절차 동작 | 알림 수신, 정리 후 사용률 |
| 7 | 논리적 손상 | 임의 UPDATE 후 PITR | 지정 시점으로 정확히 복구 | 목표 시점 대비 오차 |
| 8 | 복제 슬롯 적체 | `docker stop postgres-standby` 후 방치 | 슬롯 무효화 + 알림. primary 디스크 정상 | primary 디스크 사용률, 슬롯 상태 |

시나리오 8은 흔히 누락되지만 실제 운영에서 서비스를 정지시키는 대표적 경로다. **이중화를 위해 만든 복제 슬롯이 오히려 primary를 정지시키는 경우이며, 이중화 구성 자체가 새로운 장애 원인이 될 수 있다는 점을 시험 대상에 포함한다.**

### 3.1 주입 수단

시나리오별 주입과 복구 명령을 고정한다. 아래에 없는 파괴적 명령을 임의로 사용하지 않는다.

| # | 시나리오 | 주입 | 복구 |
|---|---|---|---|
| 1 | 앱 인스턴스 1대 다운 | `docker stop app-1` | `docker start app-1` |
| 2-a | 앱 전체 다운 | 두 슬롯 모두 stop | 두 슬롯 start |
| 2-b | 노드 전체 정지 | 클라우드 콘솔에서 인스턴스 Stop | 콘솔에서 Start |
| 3 | DB primary 다운 | `docker stop postgres-primary` | `docs/infra/runbook.md` 6.1절 페일오버 → 6.2절 페일백 |
| 4 | Redis 다운 | `docker stop redis` | `docker start redis` |
| 5 | 배포 중 요청 유실 | 부하 중 `deploy.sh` 실행 | 불필요 |
| 6 | 디스크 임계 | 여유 공간에서 5 GB만 남기고 채운다 (아래) | `rm /var/lib/dummy` |
| 7 | 논리적 손상 | 임의 UPDATE 후 PITR | PITR 완료로 복구 |
| 8 | 복제 슬롯 적체 | `docker stop postgres-standby` 후 방치 | standby 재기동 및 재구축 |

**시나리오 2-b의 전제** — 인스턴스를 정지했다 켜면 공인 IP가 바뀔 수 있다. 고정 IP가 할당되어 있는지 먼저 확인한다. 아니면 DNS를 다시 잡는 동안 서비스가 계속 정지 상태로 남는다.

**시나리오 2-b는 두 가지를 모두 판정한다.** 외부 알림이 왔는가, 그리고 **내부 알림이 오지 않았는가.** 후자를 확인하지 않으면 외부 경로 감시가 유일한 수단이었음을 보인 것이 아니다.

**시나리오 6의 주입 명령** — 고정 크기로 채우면 디스크 여유에 따라 임계에 도달하지 못한다. 남은 용량을 계산해 채운다.

```bash
AVAIL=$(df --output=avail -BG /var | tail -1 | tr -dc '0-9')
fallocate -l $(( AVAIL - 5 ))G /var/lib/dummy   # 여유 5 GB만 남긴다
```

### 3.2 실행 절차

시나리오별 배경 부하 프로파일은 `docs/infra/traffic.md` 5.2절이 정한다. 대부분 T3(25 RPS 고정)이며, 일부는 다른 프로파일을 쓴다.

주입 시점이 매번 달라지면 결과를 비교할 수 없다. 아래 타이밍을 고정한다.

```
1. 사전 확인   대상 환경, 현재 상태 정상 여부, 관측 스택 가동
2. 부하 기동   해당 시나리오의 배경 프로파일을 백그라운드 실행
3. 워밍업      120초. 이 구간이 비교 기준선이 된다
4. 주입        시각 기록. 실행한 명령을 그대로 기록
5. 관찰        180초. 이 구간에서 기대 동작을 확인
6. 복구        시각 기록. 복구 소요 측정
7. 안정화      120초. 지표가 기준선으로 돌아오는지 확인
8. 수집        구간별 지표 질의
9. 결과서      기대 동작과 실제 동작 대조
```

시나리오 3(페일오버)은 예외다. `docs/infra/runbook.md` 6.1절 절차의 **단계별 소요를 각각 측정**해야 하므로 자동 실행하지 않고 단계마다 시각을 기록하며 진행한다. 승격 전 점검 모드 전환을 건너뛰지 않는다. 스플릿 브레인이 발생한다.

시나리오 2-b도 예외다. 콘솔 조작이라 하네스로 자동화하지 않고, 정지·기동 시각을 손으로 기록한다.

**계획된 시험 전에 외부 경로 감시를 일시정지한다.** 시나리오 2-b와 3은 서비스가 수십 분 정지하므로, 그대로 두면 계획된 작업이 장애 알림으로 발송된다. 무료 플랜에는 유지보수 윈도우가 없으므로 HetrixTools 콘솔에서 모니터를 수동으로 정지하고, 시험 종료 후 반드시 다시 켠다. 재개 확인을 결과서 체크 항목에 포함한다.

**시나리오 3은 페일백까지 수행해야 완료된다.** 페일오버만 확인하고 끝내면 사양이 낮은 노드가 primary인 상태로 남는다. 승격 직후 상태에서 T2를 다시 인가해 그 구성의 처리 한계를 측정하고, 평시 한계와 대조한 뒤 6.2절 절차로 원복한다. 이 측정값이 "페일백을 계획 작업으로 둘 수 있는가, 즉시 조치로 올려야 하는가"의 판단 근거가 된다.

### 3.3 판정 기준

| 판정 | 조건 |
|---|---|
| PASS | 3장 표의 기대 동작과 실제가 일치 |
| PARTIAL | 기대 동작은 달성했으나 부수 문제 발생 (복구는 되었으나 목표 시간 초과 등) |
| FAIL | 기대 동작 불일치 |

**판정을 관대하게 하지 않는다.** 시나리오 1의 기대 동작은 요청 손실 0건인데 5xx가 3건 발생했다면 PASS가 아니라 PARTIAL이며, 그 3건의 원인(POST 비멱등 요청의 재시도 미적용 등)을 함께 기록한다.

## 4. 시험 하네스

부하 생성과 장애 주입을 손으로 실행하면 주입 시점이 매번 달라지고, 결과서를 손으로 작성하는 비용도 크다. 실행과 수집을 스크립트로 고정한다.

### 4.1 구성

```
chaos-harness/
├── harness.sh              # 오케스트레이터
├── load/
│   ├── steps.js            # 계단식 부하 (포화점 실측용)
│   ├── steady.js           # 정상 부하 (장애 주입용, 25 RPS 고정)
│   └── tokens.json         # 사전 발급 토큰 풀
├── scenarios/
│   ├── 01-app-down.sh      # inject / recover 두 인자를 받는다
│   └── ... (9개)
└── report/
    └── collect.sh          # Prometheus 질의 → 마크다운 표
```

### 4.2 오케스트레이터

```bash
#!/usr/bin/env bash
# usage: ./harness.sh 04-registry-fault
set -euo pipefail
S=$1; T0=$(date +%s)

k6 run load/steady.js --out json=report/$S-load.json &
K6=$!
sleep 120                                   # 워밍업 + 기준선 확보

INJECT_AT=$(date +%s)
bash scenarios/$S.sh inject

sleep 180                                   # 장애 지속 구간
bash scenarios/$S.sh recover
RECOVER_AT=$(date +%s)

sleep 120                                   # 안정화 확인
kill $K6 || true

bash report/collect.sh "$S" "$T0" "$INJECT_AT" "$RECOVER_AT" > report/$S.md
```

`collect.sh`는 Prometheus `/api/v1/query_range`로 주입 전·중·후 구간의 p95, 5xx 비율, 서킷 상태, upstream 수를 질의해 **구간별 비교표**를 생성한다. 이것이 결과서의 지표 절이 된다.

### 4.3 제작 순서

**시나리오 3개를 손으로 먼저 실행하고, 반복이 비효율적이라고 판단되는 지점에서 자동화한다.**

하네스를 먼저 완성하려다 정작 시험을 소수만 수행하는 것이 흔한 실패다. 손으로 실행해 봐야 어떤 지표를 수집해야 하는지도 정확해진다. 그것을 모르는 상태에서 수집기를 작성하면 필요 없는 값을 모으게 된다.

예상 비용은 하네스 본체 반나절, 시나리오 9개 각 30분 내외, 수집기 반나절이다.

## 5. 시험 실행 자동화

시험은 절차가 명확하고 반복되므로 실행과 수집을 자동화한다. 다만 **판정은 자동화하지 않는다.**

### 5.1 자동화하는 범위와 하지 않는 범위

| 단계 | 수행 주체 |
|---|---|
| 부하 인가, 장애 주입, 복구 명령 실행 | 스크립트 |
| 구간별 지표 질의 및 표 생성 | 스크립트 |
| 기대 동작과 실제 동작의 대조 | **본인** |
| PASS / PARTIAL / FAIL 판정 | **본인** |
| 원인 분석과 조치 결정 | **본인** |

판정을 자동화하지 않는 이유는 두 가지다. 첫째, 기대 동작과의 대조는 설계 의도를 아는 사람만 할 수 있다. 둘째, **장애 대응 역량은 판정과 원인 분석에 있으므로 그 부분을 넘기면 시험을 수행한 의미가 없다.**

### 5.2 실행 트리거

시험은 GitHub Actions `workflow_dispatch`로 실행한다. 애플리케이션에 실행 엔드포인트를 두지 않는다.

| 워크플로 | 실행 위치 | 대상 |
|---|---|---|
| load-test | APP-02 | 부하 프로파일 T1 ~ T7 |
| chaos-test | APP-02 | 장애 시나리오 1 ~ 9 |

**부하 시험 입력**

| 파라미터 | 값 |
|---|---|
| profile | T1 · T2 · T3 · T4 · T5 · T6 · T7 |
| duration | 프로파일 기본값을 덮어쓸 때만 지정 |
| sse | SSE 동시 연결 병행 여부 |

**장애 시험 입력**

| 파라미터 | 값 |
|---|---|
| scenario | 1 ~ 9 |
| background | T1 · T3 · T6 · none |

**부하 생성기를 APP-01에 두지 않는다.** 측정 대상과 자원을 공유하면 두 가지가 깨진다. 첫째, k6가 쓰는 CPU만큼 앱이 쓸 자원이 줄어 포화점이 과소 측정된다. 둘째, 포화 구간에서 k6도 CPU를 받지 못해 목표 RPS를 인가하지 못하고, 그 결과 **부하를 올리는 구간에서 부하가 스스로 줄어들어** 포화점이 드러나지 않는다.

애플리케이션에 실행 엔드포인트를 두지 않는 이유도 같다. 요청을 받아 부하를 생성하는 순간 측정 대상이 부하 생성에 관여한다. 실행 이력은 Actions 로그에 남고, 결과서는 시험 이슈에 첨부한다.

### 5.3 AI 코딩 에이전트 사용 규약

본 프로젝트는 AI 코딩 에이전트로 개발하므로, 시험 실행 절차를 `.claude/agents/` 아래 규약으로 고정해 실행 조건과 금지 사항을 명시한다. 에이전트는 위 표의 스크립트 영역만 담당한다.

규약에 포함하는 금지 사항은 다음과 같다.

- 수치 없이 결론을 쓰지 않는다. 개선되었다는 서술은 전후 값이 함께 있을 때만 허용한다
- 측정하지 못한 값은 미측정으로 남기고 그럴듯한 숫자로 채우지 않는다
- 발견한 문제를 임의로 수정하지 않는다. 시험 중 코드를 고치면 이후 결과가 앞선 결과와 비교 불가능해진다
- 대상이 운영 환경으로 판별되면 즉시 중단한다
- 복구 단계를 반드시 실행하며, 복구 실패 시 현재 상태를 보고한다
- 3.1절 표에 없는 파괴적 명령을 생성하지 않는다

`docker stop`, `fallocate` 등 파괴적 명령을 다루므로 주입 단계는 자동 승인 대상에서 제외하고 실행마다 확인을 받는다.

## 7. 결과서 양식

### 7.1 용량 산정 리포트

`report/capacity-YYYYMMDD.md`

```markdown
# 용량 산정 리포트 (YYYY-MM-DD)

## 시험 조건
대상 사양 / 데이터 규모 / 부하 생성기 위치 / 애플리케이션 커밋 해시

## 단계별 결과
| 목표 RPS | 실제 RPS | p95 | p99 | 5xx | CPU | 풀 pending | 캐시 적중률 |

## 포화점
실측 한계 / 포화 원인 / 판정 근거 수치

## 용량 판단
헤드룸 / 증설 불필요 구간 / 증설 권고 방향 / 축소 가능성

## 개선 전후 비교

## 한계
이 측정이 담보하지 못하는 것
```

**마지막 절을 비워두지 않는다.** 합성 부하는 실사용 패턴과 다르고 단일 세션 시험은 장기 누적 효과를 보지 못한다. 무엇을 측정하지 못했는지 기록하는 것이 리포트의 신뢰를 만든다.

## 8. 배포 방식이 회피하는 실패 사례

스크립트 기반 배포에서 반복적으로 보고되는 실패 유형과, 본 설계가 각각을 어떻게 차단하는지 정리한다.

| 실패 유형 | 증상 | 본 설계의 차단 방식 |
|---|---|---|
| upstream에 죽은 서버 상주 | 요청의 절반이 실패. 사용자에 따라 성공·실패가 갈린다 | 두 슬롯을 실제로 상시 기동한다. 교체 중인 슬롯은 `down`으로 명시 |
| 순서 역전 | 컨테이너를 먼저 정지한 뒤 upstream을 수정 | 제외 → drain → 교체 → 확인 → 복귀 순서를 스크립트로 고정 |
| reload 누락·실패 | 설정은 바뀌었으나 반영되지 않음 | `nginx -t && nginx -s reload`를 단일 함수로 강제 |
| restart 사용 | 배포마다 전체 연결 단절 | reload만 사용. restart 금지를 규칙으로 명시 |
| `fail_timeout` 경과 후 재전송 | 제외했던 서버로 주기적으로 다시 전달되어 간헐적 실패 | 죽은 서버를 목록에 남기지 않고 `down`으로 완전 제외 |
| Docker DNS 캐싱 | 컨테이너 재생성 후 옛 IP로 전달 | 루프백 IP + 고정 포트 사용 |
| old worker 누적 | 배포 반복 시 메모리 사용량 증가 | `worker_shutdown_timeout 30s` |
| 상태 불일치 | 배포 실패 후 설정과 컨테이너가 어긋남 | `down` 토글 방식으로 멱등성 확보 |
