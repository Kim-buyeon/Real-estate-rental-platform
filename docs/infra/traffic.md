# 전월세 부동산 금융 플랫폼 — 트래픽 정의서

> 트래픽 프로파일 및 상황별 적용 기준
> T1 ~ T7 · 요청 조합 · 적용 매핑
> ※ 판정 기준과 시험 절차는 `docs/infra/test-plan.md`를, 대상 시스템 구성은 `docs/infra/system.md`를 따른다.
> 작성 기준일 : 2026년 8월

## 1. 문서 목적

본 문서는 시스템에 인가할 트래픽을 프로파일로 정의하고, **어떤 상황에 어떤 프로파일을 적용할지**를 확정한다.

### 1.1 왜 상황마다 다른 트래픽이 필요한가

하나의 부하 패턴으로 모든 것을 확인할 수 없다. 병목은 트래픽의 성격에 따라 다른 곳에서 드러난다.

| 확인하려는 것 | 필요한 트래픽 성격 | 단일 패턴으로는 안 되는 이유 |
|---|---|---|
| 처리 한계 | 점진적으로 증가 | 고정 부하로는 한계가 어디인지 알 수 없다 |
| 캐시 의존도 | 캐시가 비워진 상태에서 시작 | 캐시가 데워진 상태의 수치는 실제 최악을 보여주지 않는다 |
| 자원 누수 | 낮은 부하를 장시간 유지 | 5분 시험으로는 메모리·연결 누적이 드러나지 않는다 |
| 순간 급증 대응 | 짧은 시간에 급격히 상승 | 완만한 증가는 큐 적체와 타임아웃을 재현하지 못한다 |
| 락 경합 | 쓰기 비율 상승 | 조회 위주 부하에서는 락이 거의 잡히지 않는다 |
| 장애 시 동작 | 일정한 배경 부하 | 부하가 변하면 장애 영향과 부하 영향을 구분할 수 없다 |

특히 마지막 항목이 중요하다. **장애 주입 시험에서 배경 부하가 흔들리면 지표 변화가 장애 때문인지 부하 때문인지 판정할 수 없다.** 그래서 장애 시험용 프로파일은 고정 부하여야 한다.

### 1.2 원칙

- **부하는 분석 대상이 아니라 실험 변수다.** 합성 트래픽을 분석해 결론을 내는 것이 아니라, 부하를 통제된 조건으로 인가해 시스템의 반응을 측정한다.
- **프로파일을 먼저 정의하고 시험은 그것을 인용한다.** 시험할 때마다 부하를 새로 짜면 결과를 비교할 수 없다.
- **한 번에 하나만 바꾼다.** 프로파일과 시스템 설정을 동시에 바꾸면 원인을 특정할 수 없다.

## 2. 트래픽 산출 근거

실측치가 없으므로 가정값을 명시한다. 부하 시험 이후 실측으로 갱신한다.

| 항목 | 가정값 | 산출 근거 |
|---|---|---|
| 일 활성 사용자 | 1,000명 | 서울 25개 자치구 대상 초기 서비스 |
| 피크 시간대 집중률 | 20% | 평일 20~22시 |
| 세션당 요청 수 | 12건 | 지도 탐색 3~4회 + 상세 진입 2~3회 + 위험도·대출 조회 |
| 평균 세션 길이 | 5분 | — |
| **피크 RPS** | **약 8 RPS** | (1,000 × 0.2 × 12) ÷ 300초 |
| **설계 목표 RPS** | **25 RPS** | 피크의 3배 여유 |

설계 목표를 피크의 3배로 두는 이유는 두 가지다. 첫째, 가정값 자체의 오차를 흡수한다. 둘째, 배포 중 한 슬롯이 빠져도 남은 슬롯이 처리할 수 있어야 한다.

## 3. 요청 조합

### 3.1 사용자 여정 기반 가중치

무작위 엔드포인트 호출은 실제 부하를 재현하지 못한다. 지도 탐색 → 상세 → 위험도로 이어지는 실제 경로를 따른다.

| 엔드포인트 | 서비스 기능 | 비중 | 성격 |
|---|---|---|---|
| `GET /api/properties` (좌표 조건) | PROP-02 | 30% | **가장 무거운 조회.** 부하 시험의 주 대상 |
| `GET /api/properties/district-counts` | PROP-08 | 22% | 캐시 대상. 첫 화면 |
| `GET /api/properties/{id}` | PROP-03 | 13% | 상세 진입 |
| `GET /api/properties/{id}/risk` | RISK-01 | 10% | 판정 결과 조회 |
| `GET /api/properties` (목록) | PROP-01 | 7% | 커서 페이지네이션 |
| `GET /api/me/wishlist` | PROP-05 | 6% | 인증 사용자별 조회. 조회 경로가 공개 매물 조회와 다르다 |
| `GET /api/notifications` | NOTI-05 | 4% | **SSE 유실 시의 폴백 경로.** 앱 정지 시 이 경로로 몰린다 |
| `POST · DELETE /api/me/wishlist` | PROP-05 | 3% | 쓰기 |
| `POST /api/auth/refresh` | USER-02 | 2% | **Redis를 치는 유일한 상시 요청.** 토큰 회전 포함 |
| `GET /api/loans/limit` | LOAN-01 | 2% | 계산 |
| `POST /api/properties/{id}/risk/reanalyze` | RISK-08 | 1% | **분산 락 경합과 외부 API 호출을 유발하는 유일한 경로** |

**여정 규칙** — 지도 마커 조회 결과에서 실제 `propertyId`를 뽑아 상세·위험도를 호출한다. 존재하지 않는 ID로 404를 유발하면 부하가 실제보다 가벼워진다.

상세 진입률은 30%로 둔다. 지도에서 마커를 본 사용자 전원이 상세로 들어가지 않는다.

**토큰 갱신을 조합에 넣는 이유** — 3.3절에서 로그인을 사전 발급 토큰으로 대체한 것은 해싱 비용의 오염을 막기 위해서다. 그러나 그 결과 Redis를 치는 요청이 배경 부하에서 사라지면 Redis 정지 시나리오의 영향이 과소평가된다. 갱신 요청은 해싱을 수반하지 않으므로 오염 없이 Redis 경로를 유지한다. T4는 2시간이므로 액세스 토큰 만료가 실제로 발생한다.

**재분석 요청의 비중을 1%로 두는 이유** — 외부 API를 실제로 호출하는 쓰기 경로이므로 비중을 올리면 측정 대상이 조회 성능에서 외부 연동 지연으로 옮겨간다. 분산 락 경합을 관측할 최소량만 인가한다.

### 3.2 지도 탐색 단계 분포

PROP-02는 3단계 드릴다운이며 단계마다 쿼리 비용이 다르다. 단일 비중으로 묶으면 주 측정 대상의 내부 분포가 사라진다.

| 단계 | 조회 내용 | PROP-02 내 비중 | 비용 특성 |
|---|---|---|---|
| 1단계 (시 전체) | 자치구 단위 집계 | 30% | 집계 결과. 캐시 적중 대상 |
| 2단계 (자치구) | 동 단위 클러스터 | 40% | 바운딩 박스 + 그룹핑 |
| 3단계 (동) | 개별 마커 | 30% | **바운딩 박스 + 거리 계산.** 가장 무겁다 |

3단계만 인가하면 실제보다 무겁고, 1단계만 인가하면 실제보다 가볍다.

### 3.3 지역 분포

자치구를 균등하게 무작위 선택하면 캐시 적중률이 실제보다 낮게 나온다. 실사용자는 특정 지역에 몰린다.

| 구분 | 비중 |
|---|---|
| 상위 3개 자치구 | 60% |
| 나머지 22개 자치구 | 40% |

### 3.4 공통 파라미터

| 항목 | 값 | 이유 |
|---|---|---|
| think time | 3~10초 무작위 | 연타하면 커넥션 풀이 실제보다 빨리 포화된다 |
| 인증 | 사전 발급 토큰 풀 100개 | 매 요청 로그인하면 bcrypt 해싱이 측정 대상을 오염시킨다 |
| 워밍업 제외 | 각 단계 첫 60초 | JIT 컴파일과 커넥션 풀 예열 구간 |
| 응답 검증 | 본문의 배열 길이 확인 | 200을 반환하며 빈 배열을 주는 상태를 성공으로 세지 않는다 |

### 3.5 SSE 동시 연결

NOTI-03은 장시간 유지되는 연결이므로 RPS로 표현할 수 없다. 요청 조합과 별개로 **동시 연결 수**를 축으로 잡는다.

| 항목 | 값 | 이유 |
|---|---|---|
| 동시 연결 | 인가 RPS × 10 (T3 기준 250) | think time 3~10초 구간에도 연결은 유지된다 |
| 연결 유지 시간 | 시험 전 구간 | 중간에 끊으면 스레드 점유가 실제보다 짧게 측정된다 |
| 분산 | 두 인스턴스에 고르게 | 한쪽에 몰리면 팬아웃이 검증되지 않는다 |
| 수신 검증 | 이벤트 도달 여부와 지연 | 연결만 유지되고 이벤트가 오지 않는 상태를 성공으로 세지 않는다 |

**동시 연결을 별도 축으로 두는 이유** — SSE 연결은 응답이 끝나지 않으므로 요청 하나가 처리 스레드를 계속 점유한다. 이 부하가 없으면 세 가지가 재현되지 않는다.

| 재현되지 않는 것 | 관련 |
|---|---|
| Tomcat 스레드 점유 | `docs/infra/observability.md`의 스레드 지표가 움직이지 않는다 |
| 다중 인스턴스 팬아웃 | app-1의 연결에 app-2가 발행한 이벤트가 도달하는지 확인 불가 |
| 앱 1대 정지 시 연결 단절·재연결 | 시나리오 1에서 SSE 영향이 관측되지 않는다 |

## 4. 트래픽 프로파일

| ID | 이름 | 패턴 | 지속 | 목적 |
|---|---|---|---|---|
| **T1** | 기준선 | 10 RPS 고정 | 10분 | 정상 상태 확인. 회귀 비교의 기준값 |
| **T2** | 계단식 | 10 → 25 → 50 → 100 → 200 RPS, 각 5분 유지 · 2분 휴지 | 약 40분 | **포화점 실측.** 처리 한계와 병목 특정 |
| **T3** | 정상 부하 | 25 RPS 고정 | 시험 길이에 맞춤 | **장애 주입 시 배경 부하.** 변동이 없어야 한다 |
| **T4** | 지속 | 15 RPS 고정 | 2시간 | 메모리·커넥션 누수 확인 |
| **T5** | 캐시 콜드 | 캐시 전체 비운 뒤 25 RPS | 10분 | 공유 저장소 의존도 측정. 최악 조건의 응답 시간 |
| **T6** | 배포 중 | T3 유지 상태에서 배포 실행 | 배포 소요 + 5분 | 무중단 배포 검증 |
| **T7** | 배치 동시 | T3 유지 상태에서 재분석 배치 실행 | 배치 소요 + 5분 | **배치가 도는 동안의 조회 성능.** 커넥션 풀 경합 확인 |

요청 조합은 전 프로파일이 3.1절 표준을 사용하고, SSE 동시 연결은 3.5절 기준을 함께 인가한다. 프로파일이 다른 것은 인가량과 지속 시간뿐이다.

**T2와 T3의 관계** — T2는 한계를 찾고, T3는 그 한계보다 충분히 낮은 지점에서 고정한다. 25 RPS는 T2로 확인한 한계의 절반 이하여야 한다. 배경 부하가 이미 포화 근처면 장애를 넣지 않아도 지표가 흔들린다.

**T5의 실행 방법** — `FLUSHALL` 이후 즉시 인가한다. T3와 같은 조건에서 캐시 상태만 다르므로 두 결과의 차이가 곧 공유 저장소의 기여분이다.

**T7이 필요한 이유** — RISK-08 배치는 관심 매물 전량을 일 1회 재분석하며 외부 API 호출과 쓰기를 동반한다. 이 시간대에 조회 응답이 어떻게 되는지가 실제 운영에서 확인해야 할 값이다. T3와 T7의 p95 차이가 배치의 사용자 영향이며, 차이가 크면 배치 실행 시각을 저부하 시간대로 옮기거나 처리 속도를 제한한다.

## 5. 상황별 적용

### 5.1 일정상의 적용

| 시점 | 상황 | 프로파일 | 목적 |
|---|---|---|---|
| 1주차 | 조회 경로 예비 측정 | T1, T2(50 RPS까지) | 인덱스 설계 검증, 더미 데이터 규모 확정 |
| 5주차 | 포화점 실측 | **T2 전체** | 용량 산정 리포트 작성 |
| 5주차 | 병목 개선 후 재측정 | T2 (동일 조건) | 전후 비교 |
| 5주차 | 캐시 기여 측정 | T5 ↔ T3 대조 | 공유 저장소 의존도 정량화 |
| 6주차 | 배포 검증 | **T6** | 무중단 배포 확인 |
| 7주차 | 장애 주입 9종 | 5.2절 매핑 | 인프라 정지 시 동작 검증 |
| 5주차 | 배치 영향 측정 | **T7 ↔ T3 대조** | 재분석 배치의 사용자 영향 정량화 |
| 5주차 (야간) | 안정성 | **T4** | 누수 확인 |

1주차 시점에는 매물 도메인만 존재하므로 위험도·알림을 포함한 전체 조합을 인가할 수 없다. 조회 경로만으로 축소한 조합을 사용하고, 그 사실을 결과에 명시한다.

### 5.2 장애 시나리오별 배경 부하

`docs/infra/test-plan.md` 3장의 시나리오에 각각 어떤 프로파일을 배경으로 깔지 정한다.

| # | 시나리오 | 배경 프로파일 | 이유 |
|---|---|---|---|
| 1 | 앱 인스턴스 1대 다운 | T3 + SSE | 요청 손실 0건 판정에 일정한 부하가 필요. SSE 연결 단절과 재연결도 함께 확인한다 |
| 2-a | 앱 전체 다운 | T3 + SSE | 알림 발생 시각 측정. 전 연결의 단절을 함께 확인한다 |
| 2-b | 노드 전체 정지 | 부하 없음 | 외부 감시가 도달 여부만 보므로 배경 부하가 불필요하다 |
| 3 | DB primary 다운 | T3 | 페일오버 단계별 소요 측정 중 사용자 영향 확인 |
| 4 | Redis 다운 | **T5 직후 T3** | 캐시가 비워진 상태와 유사한 조건에서 조회 유지 확인. 조합에 포함된 토큰 갱신이 인증 경로의 영향을 드러낸다 |
| 5 | 배포 중 요청 유실 | **T6** | 정의상 배포 프로파일 |
| 6 | 디스크 임계 | T1 | 부하가 낮아도 알림은 발생해야 한다 |
| 7 | 논리적 손상 후 PITR | 부하 없음 | 복구 정확성 시험이며 처리량과 무관 |
| 8 | 복제 슬롯 적체 | T3 | WAL 생성이 있어야 슬롯이 적체된다 |

**시나리오 8에 부하가 필요한 이유** — standby를 멈춰도 WAL이 생성되지 않으면 슬롯이 적체되지 않는다. 쓰기가 포함된 배경 부하가 있어야 `max_slot_wal_keep_size` 초과를 확인할 수 있다.

## 6. 데이터 전제

트래픽을 인가하기 전에 아래가 충족되어야 한다. 하나라도 미충족이면 시험 결과가 무의미하다.

|---|---|---|

| 관측 스택 | Prometheus 스크레이프 중 | 지표 없이 인가한 부하는 결과가 없는 것과 같다 |

## 7. 측정 오염 요인

아래에 해당하면 그 결과는 시스템의 성능이 아니다. 시험 전에 확인하고, 발견되면 그 사실을 리포트에 명시한다.

| 요인 | 확인 방법 | 조치 |
|---|---|---|
| **부하 생성기 병목** | `dropped_iterations` > 0, 또는 `http_req_connecting` · `http_req_sending`이 단계마다 증가 | `maxVUs` 상향 후 재측정. 그래도 남으면 생성기를 별도 노드로 분리. 서버 포화점을 측정한 것이 아님 |
| 동일 노드 실행 | 생성기와 애플리케이션이 같은 노드 | CPU를 나눠 쓴다. APP-02에서 실행 |
| 워밍업 미제외 | 첫 구간의 p95가 유독 높음 | 첫 60초 집계 제외 |
| 캐시 상태 불일치 | 같은 프로파일인데 결과가 크게 다름 | T6로 콜드 상태를 명시적으로 만들거나, 워밍업으로 상태를 맞춘다 |
| 네트워크 경유 | 로컬 PC에서 인터넷을 통해 인가 | 25 RPS까지는 무방. 100 RPS 이상은 같은 리전에서 실행 |
| 데이터 편중 | 항상 같은 매물만 조회 | 캐시 적중률이 100%가 되어 DB 부하가 사라진다 |

## 8. 스크립트 대응

프로파일과 k6 스크립트를 1:1로 대응시킨다. 스크립트에서 프로파일을 즉석으로 변형하지 않는다.

| 프로파일 | 파일 | executor |
|---|---|---|
| T1 | `load/baseline.js` | `constant-arrival-rate` |
| T2 | `load/steps.js` | `ramping-arrival-rate` |
| T3 | `load/steady.js` | `constant-arrival-rate` |
| T4 | `load/soak.js` | `constant-arrival-rate` |
| T5 | `load/steady.js` + `redis-cli FLUSHALL` 선행 | `constant-arrival-rate` |
| T6 | `load/steady.js` + `deploy.sh` | `constant-arrival-rate` |
| T7 | `load/steady.js` + 배치 수동 기동 | `constant-arrival-rate` |
| SSE 동시 연결 | `load/sse.js` (전 프로파일과 병행 실행) | `constant-vus` |

**executor는 반드시 arrival-rate 계열을 사용한다.** VU 기반 executor는 응답이 느려질수록 실제 인가 RPS가 함께 떨어져 포화점을 찾지 못한다. 목표 처리량을 직접 지정해야 시스템이 그것을 따라오지 못하는 지점이 드러난다.

**`maxVUs`는 포화 구간을 기준으로 잡는다.** arrival-rate는 목표 RPS를 맞추기 위해 VU를 늘리는데, 응답이 느려질수록 더 많은 VU가 필요하다. 정상 응답 시간을 기준으로 잡으면 정작 한계를 재는 구간에서 상한에 걸린다.

**상한에 걸리면 k6가 요청을 버리고 `dropped_iterations`로 집계한다.** 이 값이 0이 아닌 구간은 결과에서 제외한다. 응답 시간이 나빠진 것이 서버가 못 버텨서인지 k6가 요청을 못 보내서인지 구분되지 않기 때문이다.

**SSE만 `constant-vus`를 사용한다.** 다른 스크립트가 arrival-rate인 것은 초당 요청 수를 고정하기 위해서인데, SSE는 요청을 반복해서 보내는 것이 아니라 연결을 붙잡고 있는 것이 부하다. 목표량이 초당 요청 수가 아니라 동시 연결 수이므로 VU 수를 직접 고정한다. SSE 스크립트는 별도 프로세스로 먼저 기동해 연결을 확립한 뒤 본 프로파일을 인가한다.

요청 조합(3.1절), 지도 탐색 단계 분포(3.2절), 공통 파라미터(3.4절)는 모든 스크립트가 공유하는 모듈로 분리해, 조합을 바꿀 때 한 곳만 수정한다.
