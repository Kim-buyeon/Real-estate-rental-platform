# add-judgement

**산식은 문서가, 임계값은 기준 테이블이 갖고, 코드는 둘을 읽어 계산만 한다.** 산식의 정본은 `docs/business-logic.md`, 기준 테이블은 `docs/architecture/database.md`, 응답 필드는 영역 API 명세, 계층 규칙은 `backend/CLAUDE.md` Service 절이다. 여기서는 순서와 표의 형식만 정한다.

## 1. 순서

```
1. 산식 출처표          입력마다 문서 위치. 빈 칸이면 멈춘다
        │
2. 기대값 표            경계값 포함. 구현 전에
        │
3. 승인                 두 표가 계획에 첨부되어 승인된다
        │
4. 구현                 순수 함수 클래스. 기준값은 인자로 받는다
        │
5. 케이스 테스트         표 1행 = 테스트 1건. 같은 변경 단위
        │
6. 실패 확인            등호를 잠시 뒤집어 빨개지는지 (test-engineer)
```

**4번을 1 · 2 · 3보다 먼저 하지 않는다.** 기대값 표는 구현 전에 쓴다 — `docs/architecture/testing.md` 1.1 단위 테스트 행. 구현을 보고 기대값을 역산하면 테스트가 구현을 베끼는 것이 되어 아무것도 검증하지 못한다 — `test-engineer` 2단계.

## 2. 산식 출처표

산식의 **입력 · 임계값 · 등호 방향 · 정밀도 · 출력** 하나하나를 적는다.

| 열 | 내용 |
| --- | --- |
| 항목 | 예: 전세가율, 담보인정비율, 안전기준비율, LTV 한도 |
| 산식 위치 | `docs/business-logic.md`의 절 |
| 값의 출처 | 기준 테이블 컬럼(`GUARANTEE_CRITERIA` · `LOAN_REGULATION` 등) 또는 입력 엔티티 컬럼 |
| 등호 | `≤` `<` `≥` `>`를 문서 그대로. 「이상」 「초과」를 바꿔 쓰지 않는다 |
| 단위 · 정밀도 | 원(정수) · %(소수 자릿수) · 반올림 모드 |
| 출력 | API 명세의 응답 필드와 열거값 — 구조까지(예: 기관별 배열 안의 위배 조건 목록) |

| 빈 칸이 생기는 곳 | 처리 |
| --- | --- |
| 산식에는 있는데 기준 테이블에 컬럼이 없다 | **멈춘다.** 상수로 넣지 않는다. 어느 테이블에 둘지 제안한다 |
| 문서가 값을 둘 이상 적었다 — 예: 깡통전세 안전기준비율은 4장 주석에 70%와 60%가 함께 있다 | 멈춘다. 어느 값을 어느 조건에 쓰는지 정해 문서에 남긴 뒤 진행 |
| 함수 이름만 있고 산식이 없다 — 예: 6장 의사코드의 `역산(maxAnnualPayment, loan.interest_rate)` | 멈춘다. 산식을 문서에 먼저 적는다. 6-1의 상환방식별 식이 그 자리인지 확인 |
| 응답 열거값이 명세에 예시로만 있다 — `gradeReason` · `providers[].failedConditions` | 전체 목록을 명세에 추가하는 제안. 코드에서 임의로 늘리지 않는다 |
| 반올림 모드가 없다 | 산식마다 정해 표에 적고 승인받는다. `persistence.md` 1.2는 「명시한다」까지만 정한다 |

## 3. 기대값 표

| 열 | 내용 |
| --- | --- |
| 케이스 ID | 기능 ID + 순번 |
| 입력 | 산식의 입력값 전부. **기준값도 입력이다** — 기준 테이블에서 읽어 넘기는 값 |
| 기대 출력 | 등급 · 금액 · 불리언 · 열거값. 명세의 필드명으로 |
| 경계 | 경계값 자체 · 경계 ± 최소 단위 · 해당 없음 |
| 근거 | 산식 출처표의 행 |

| 반드시 넣는 케이스 | 근거 |
| --- | --- |
| 등호 양쪽 — 경계값과 경계 ± 최소 단위 | `business-logic.md` 3장 등급 기준의 등호 |
| 우선순위가 갈리는 조합 — 둘 이상의 조건이 동시에 참 | 3장 의사코드의 분기 순서 |
| 기관별로 결과가 다른 경우 | 2장 종합 판정 |
| 여러 한도 중 최솟값 — 셋이 다 다를 때, 둘이 같을 때 | 6장 |
| 0과 null — 선순위채권 없음, 자격 정보 미입력 | `docs/api/loan.md` 1.1 `missingFields` |
| **기준값을 바꾼 케이스** — 같은 입력에 기준값만 바꿔 결과가 따라온다 | 구현 안에 숫자가 박혔는지 잡는다 |

표는 계획에 첨부한다. `test-engineer`가 2단계에서 이 표를 찾는다 — 없으면 멈춘다.

## 4. 구현

| 규칙 | 근거 |
| --- | --- |
| 별도 클래스, 순수 함수, 이름 형태, 빈 여부 | `backend/CLAUDE.md` Service 「계산 · 판정 규칙이 복잡하면 별도 클래스」 |
| **기준값은 인자다.** 서비스가 기준 테이블(JPA 엔티티)에서 읽어 넘긴다. 계산기 안에 숫자가 없다 | `testing.md` 1.2 · `docs/conventions.md` 「매직 넘버」 |
| 금액 · 비율은 `BigDecimal`, 나눗셈은 반올림 모드와 자릿수를 명시 | `persistence.md` 1.2 |
| 분기 누락이 치명적인 결과는 봉인 인터페이스 + `switch` 패턴 매칭 | `backend/CLAUDE.md` Enum · `docs/tech-stack.md` 2장 Java |
| 결과와 함께 근거(위배 조건 · 적용 규제 · 사용 시세)를 돌려준다 | `docs/api/risk.md` 1.1 · `docs/api/loan.md` 1.1 |
| 계산기는 저장하지 않는다. 이력 적재 · 최신 표시 · 이전 등급 보존은 CommandService | `database.md` RISK_ANALYSIS |
| 판정을 관점으로 옮기지 않는다 | `docs/architecture/spring-aop.md` 1.2 |

## 5. 케이스 테스트

| 규칙 | 내용 |
| --- | --- |
| 도구 · 대상 | `testing.md` 1.1 단위 테스트 행. DB 없음 — 순수 함수 |
| 표 1행 = 1건 | 파라미터화 테스트로 표를 그대로 옮긴다. 케이스 ID를 표시 이름에 넣는다 |
| 기준값은 테스트의 입력 데이터 | 테스트가 기준 객체를 만들어 넘긴다 — `testing.md` 1.2. 이것은 「임계값을 상수로 박는 것」이 아니다 — 구현에 숫자가 없고, 기준값이 바뀌면 결과가 따라오는 케이스가 그것을 증명한다 |
| 실패 확인 | 등호를 잠시 뒤집거나 우선순위를 바꿔 빨개지는지 본다. 되돌린 뒤 `git diff`로 확인 |
| 통과시키려 고치지 않는다 | 실패하면 표가 틀렸는지 구현이 틀렸는지 밝힌다 |

## 6. 함께 커밋한다

짝은 `docs/git/commit.md`의 「함께 커밋해야 하는 것」 두 표가 갖고 `git-check`가 본다. 「판정 로직 + 케이스 테스트」가 거기 있다.

## 7. 하지 않는다

- **산식을 코드에서 고치지 않는다.** 문서가 틀렸으면 근거를 붙여 문서 수정을 먼저 제안한다 — 루트 `CLAUDE.md` 「문서를 고칠 때」.
- **임계값을 구현에 박지 않는다.**
- **구현을 보고 기대값을 만들지 않는다.**
- **커밋하지 않는다.** 커밋은 별도 단계이며 `git-check`를 거친다.
