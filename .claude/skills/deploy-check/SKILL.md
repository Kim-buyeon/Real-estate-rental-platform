# deploy-check

**시작하기 전에 `docs/infra/runbook.md` 3장을 읽는다.** 절차·실행 규칙·스크립트가 거기 있다.

## 1. 배포 가능한 상태인가

| 확인 | 통과 조건 | 근거 |
| --- | --- | --- |
| 이미지가 커밋 해시 태그로 올라와 있다 | `ghcr.io/<계정>/<저장소>:<해시>` | `docs/infra/runbook.md` 3.2 |
| Trivy CRITICAL이 없다 | 스캔 결과. HIGH는 기록만 | 3.1 |
| 마이그레이션이 하위 호환이다 | 컬럼 삭제 · 이름 변경 · NOT NULL 추가가 없다. **있으면 세 단계 분리의 마지막 단계인지 확인한다** — 앞 두 단계가 적용됐는지 Flyway 이력 테이블로 보고, 이 배포는 롤백해도 되돌아가지 않으므로 승인을 받는다 | 3.1 · 3.4 |
| 서버에 `.env`가 있고 권한이 소유자 전용이다 | | 3.2 |
| 이전 이미지 태그가 3개 남아 있다 | 롤백 경로 | 3.4 |
| Prometheus가 앱을 스크레이프하고 있다 | `up{job="app"}` | 3.3 |

**하나라도 아니면 배포하지 않는다.** 마지막 항목은 관찰 판정 자체를 성립시키는 조건이다.

## 2. 어떤 배포인가

| 종류 | 배경 부하 | 관찰 | 추가로 세는 것 |
| --- | --- | --- | --- |
| 일상 배포 | 없음 | 스크립트의 첫 슬롯 관찰 | — |
| 배포 검증 (INF-02 · 시나리오 5) | **T6** | 같음 | 조회 요청 실패 0건 |
| 롤백 | 없음 | **건너뛴다** | — |

- 부하 없이 배포하면 무중단 여부를 셀 수 없다 — `docs/architecture/testing.md` 1.1
- 롤백이 관찰을 건너뛰는 것은 되돌아갈 대상이 이미 검증된 버전이기 때문이다 — `docs/infra/runbook.md` 3.4
- 프로파일과 시나리오 실행 방식은 `docs/infra/test-plan.md` 5.2를 따른다

## 3. 실행한다

`bash deploy.sh`.

**중간에 개입하지 않는다.** 첫 슬롯이 복귀한 뒤 멈춘 것처럼 보이는 구간이 있는데 관찰 대기다. 스크립트가 멈추면 5장으로 간다.

## 4. 끝난 뒤 확인한다

**스크립트는 첫 슬롯만 관찰한다.** 두 번째 슬롯은 readiness만 통과하고 지표는 확인되지 않은 채 배포가 끝난다.

| 확인 | 방법 |
| --- | --- |
| 두 슬롯이 모두 upstream에 있다 | `upstream.conf`에 `down`이 남아 있지 않다 |
| 두 슬롯 모두 readiness가 UP이다 | 8081 · 8082의 `/actuator/health/readiness` |
| 지표가 기준 안이다 | `bash observe.sh`를 한 번 더 실행한다 |
| 구 버전이 남아 있지 않다 | 실행 중인 두 컨테이너의 이미지 태그가 배포 대상과 같다 |
| 배포 마커를 기록했다 | 스크립트는 문구만 출력한다. 실제 기록은 여기서 한다 |

**마커 기록 방법은 미확정이다.** `docs/infra/observability.md` 4장은 대시보드가 마커를 지원한다고만 정한다. 방식을 정하면 그 문서에 반영한다. 월간 운영 보고의 변경 절이 이 마커를 근거로 쓴다.

배포 검증이었다면 k6의 실패 건수를 결과서에 남긴다. **쓰기 요청의 실패는 손실이 아니다** — 비멱등 요청은 재시도되지 않으므로 「요청 손실 0건」은 조회 요청에 대한 서술이다. 구분해서 적는다 (`docs/infra/runbook.md` 4.2).

## 5. 멈췄으면

| 어디서 | 지금 상태 | 다음 |
| --- | --- | --- |
| `nginx -t` 실패 | `upstream.conf`는 고쳐졌고 **실행 중 설정은 그대로다** | 치환 결과를 보고 파일을 바로잡은 뒤 reload한다 |
| readiness 30회 실패 | 그 슬롯이 `down`, 나머지 슬롯이 전량 처리 | 컨테이너 로그로 기동 실패 원인을 잡는다. 롤백은 불필요하다 |
| `observe.sh` 판정 실패 | 첫 슬롯을 `down`으로 되돌린 상태, 구 버전이 전량 처리 | 지표를 보고 원인을 잡는다. 고치기 전에 다시 배포하지 않는다 |
| 관찰 구간을 지난 뒤 결함 발견 | 두 슬롯 모두 신 버전 | 롤백한다 |

**롤백은 이전 태그를 지정해 같은 스크립트를 다시 실행하는 것이다.** 별도 절차가 없다. 스키마 마이그레이션이 포함된 배포는 롤백해도 스키마가 되돌아가지 않는다. **세 단계 분리의 마지막 단계(제거)를 배포한 뒤에는 이전 태그가 신 스키마에서 검증된 버전이 아니다** — 그때의 롤백은 관찰을 건너뛰지 않고, 되돌릴지 자체를 먼저 판단한다.

**어느 경우든 남은 슬롯이 서비스하고 있다.** 급하게 손대지 말고 상태를 먼저 확정한다.

## 6. 알린다

| 항목 | 내용 |
| --- | --- |
| 배포 종류 | 일상 · 검증 · 롤백 |
| 이미지 태그 | 커밋 해시 |
| 결과 | 완료 · 중단(어느 슬롯, 어느 단계) |
| 관찰 지표 | 요청 수 · 5xx · p95 |
| 남은 조치 | 없으면 없다고 적는다 |

**표본이 없는 것과 판정에 실패한 것을 구분해서 적는다.** 요청 100건 미만이면 판정을 생략하고 진행한 것이지 통과한 것이 아니다.
