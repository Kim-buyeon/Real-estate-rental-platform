# deploy-check

**시작하기 전에 `docs/infra/runbook.md` 3장을 읽는다.** 절차·실행 규칙·스크립트가 거기 있다.

## 1. 배포 가능한 상태인가

| 확인 | 통과 조건 | 근거 |
| --- | --- | --- |
| 이미지가 커밋 해시 태그로 올라와 있다 | GHCR의 `backend:<해시>` · `frontend:<해시>` 둘 다 | `docs/infra/runbook.md` 3.2 |
| Trivy CRITICAL이 없다 | 그 커밋의 `Image` 워크플로가 성공했다(CRITICAL이면 이미지가 올라가지 않는다). HIGH는 산출물로 기록만 | 3.1 |
| 마이그레이션이 하위 호환이다 | 컬럼 삭제 · 이름 변경 · NOT NULL 추가가 없다. **있으면 세 단계 분리의 마지막 단계인지 확인한다** — 앞 두 단계가 적용됐는지 Flyway 이력 테이블로 보고, 이 배포는 롤백해도 되돌아가지 않으므로 승인을 받는다 | 3.1 · 3.4 |
| 서버에 `infra/.env`가 있고 권한이 소유자 전용이다 | | 3.2 |
| 이전 이미지 태그가 3개 남아 있다 | 롤백 경로 | 3.4 |
| 점검 모드가 꺼져 있다 | `bash maintenance.sh status` → 꺼짐 | 4.2 |

**하나라도 아니면 배포하지 않는다.**

## 2. 어떤 배포인가

| 종류 | 배경 부하 | 관찰 | 추가로 세는 것 |
| --- | --- | --- | --- |
| 일상 배포 | 없음 | 첫 슬롯 복귀 전 `smoke.sh` | — |
| 배포 검증 (INF-02) | 조회 요청을 반복하는 루프 하나 | 같음 | 조회 요청 실패 0건 |
| 롤백 | 없음 | **건너뛴다** | — |

- 부하 없이 배포하면 무중단 여부를 셀 수 없다 — `docs/architecture/testing.md` 1.1
- 롤백이 관찰을 건너뛰는 것은 되돌아갈 대상이 이미 검증된 버전이기 때문이다 — `docs/infra/runbook.md` 3.4
- k6 프로파일(T6)을 쓰는 배포 검증은 부하 시험(INF-06)이 차기 범위라 쓰지 않는다. 배포 중 Nginx 경유로 조회 요청을 계속 보내고 상태 코드를 센다

## 3. 실행한다

`infra/`에서 `bash deploy.sh <커밋 해시>` (롤백은 `--rollback`).

**중간에 개입하지 않는다.** 첫 슬롯 교체 뒤 멈춘 것처럼 보이는 구간이 있는데 워밍업 대기(60초)다. 스크립트가 멈추면 5장으로 간다.

## 4. 끝난 뒤 확인한다

**스크립트는 첫 슬롯만 관찰한다.** 나머지 슬롯은 readiness만 통과한 채 배포가 끝난다. 슬롯은 APP-01 둘 · APP-02 둘, 넷이다 — 목록은 `upstream.conf`.

| 확인 | 방법 |
| --- | --- |
| 모든 슬롯이 upstream에 있다 | `upstream.conf`에 `down`이 남아 있지 않다 |
| 모든 슬롯의 readiness가 UP이다 | 슬롯마다 `http://<주소>:<포트>/actuator/health/readiness` — APP-01에서 루프백 둘과 APP-02 사설 IP 둘 |
| 관찰하지 않은 슬롯도 기준 안이다 | 슬롯마다 `bash smoke.sh <주소> <포트>`를 한 번 실행한다 |
| 구 버전이 남아 있지 않다 | 두 노드의 `docker compose ps` 에서 app-1 · app-2(APP-01은 web도) 이미지 태그가 배포 대상과 같고, 두 노드 `.env`의 `APP_IMAGE`(APP-01은 `WEB_IMAGE`도)도 같다 |
| 배포를 기록했다 | 스크립트 출력(시각 · 태그 · 단계)을 남긴다. 월간 운영 보고의 변경 절이 이것을 근거로 쓴다 |

배포 검증이었다면 조회 요청의 상태 코드별 건수를 남긴다. **쓰기 요청의 실패는 손실이 아니다** — 비멱등 요청은 재시도되지 않으므로 「요청 손실 0건」은 조회 요청에 대한 서술이다. 구분해서 적는다 (`docs/infra/runbook.md` 4.2).

## 5. 멈췄으면

| 어디서 | 지금 상태 | 다음 |
| --- | --- | --- |
| `nginx -t` 실패 | `upstream.conf`는 고쳐졌고 **실행 중 설정은 그대로다** | 치환 결과를 보고 파일을 바로잡은 뒤 reload한다 |
| readiness 120초(60회 × 2초) 실패 | 그 슬롯이 `down`, 나머지 슬롯이 전량 처리 | 컨테이너 로그로 기동 실패 원인을 잡는다. 롤백은 불필요하다 |
| `smoke.sh` 판정 실패 | 첫 슬롯이 `down`(upstream에 넣기 전이다), 구 버전이 전량 처리 | 그 슬롯의 로그와 판정 출력(실패 건수 · p95)으로 원인을 잡는다. 고치기 전에 다시 배포하지 않는다 |
| 관찰 구간을 지난 뒤 결함 발견 | 모든 슬롯이 신 버전 | 롤백한다 |

**롤백은 이전 태그를 지정해 같은 스크립트를 다시 실행하는 것이다.** 별도 절차가 없다. 스키마 마이그레이션이 포함된 배포는 롤백해도 스키마가 되돌아가지 않는다. **세 단계 분리의 마지막 단계(제거)를 배포한 뒤에는 이전 태그가 신 스키마에서 검증된 버전이 아니다** — 그때의 롤백은 관찰을 건너뛰지 않고, 되돌릴지 자체를 먼저 판단한다.

**어느 경우든 남은 슬롯이 서비스하고 있다.** 급하게 손대지 말고 상태를 먼저 확정한다.

## 6. 알린다

| 항목 | 내용 |
| --- | --- |
| 배포 종류 | 일상 · 검증 · 롤백 |
| 이미지 태그 | 커밋 해시 |
| 결과 | 완료 · 중단(어느 슬롯, 어느 단계) |
| 관찰 결과 | `smoke.sh` 출력 — 요청 수 · 실패 · p95 |
| 남은 조치 | 없으면 없다고 적는다 |

**롤백에서 관찰을 건너뛴 것과 통과한 것을 구분해서 적는다.**
