# backend-dev

`backend/` 하위 코드를 작성한다. **계층별 작성 규칙은 `backend/CLAUDE.md`를 따른다.** 본 문서는 순서와 경계만 정한다.

## 작업 순서

엔드포인트 하나를 구현할 때의 순서다. 단계마다 무엇을 확인하는지는 `add-endpoint`, 조회 작성은 `add-mapper`를 따른다. **아래에서 위로 거슬러 올라가지 않는다.**

1. **명세 확인** — 대상 엔드포인트의 경로·메서드·요청·응답 예시를 확인한다. **명세에 없는 경로나 필드를 만들지 않는다.**
2. **DTO** — Request와 Response를 작성한다. 필드명은 명세 예시와 일치시킨다.
3. **영속성** — 조회면 Mapper와 XML을, 변경이면 Repository를 작성한다. 매퍼를 추가했다면 테스트를 같은 변경 단위에 포함한다.
4. **Service** — 조회는 QueryService, 변경은 CommandService.
5. **Controller** — 요청 검증과 서비스 호출만 한다.
6. **검증** — 컴파일, 테스트, 마이그레이션 정합을 순서대로 실행한다.

### 순서가 달라지는 경우

- **엔티티나 스키마 변경이 필요하면** 1번과 2번 사이에서 마이그레이션을 먼저 추가한다. 마이그레이션과 엔티티는 같은 커밋에 넣는다. 한쪽만 반영되면 `ddl-auto validate`에서 기동이 실패한다.
- **판정·계산 로직이 포함되면** 구현 전에 기대값 표를 작성한다. 임계값은 기준 테이블에서 읽고 테스트에 상수로 박지 않는다. `add-judgement`를 따른다.
- **외부 연동이 필요하면** 인터페이스와 Mock 구현을 먼저 둔다. Real은 API 승인 이후에 붙이고, Fault는 서킷 검증용으로 함께 만든다. `add-external-client`를 따른다.

## 무상태 전제

애플리케이션이 **두 프로세스로 구동된다.** 다음을 프로세스 메모리에 두지 않는다.

- 세션·토큰 → Redis
- 캐시 → Redis
- 배치 실행 여부 → Redis 분산 락
- SSE 연결 → 이벤트는 Redis Pub/Sub으로 전 인스턴스에 브로드캐스트하고, 각 인스턴스가 해당 사용자의 연결 보유 여부를 확인해 전달한다

단일 인스턴스에서는 이 셋이 모두 통과하므로, **테스트로만 드러난다.** 상세는 횡단 관심사·알림 전달 문서를 따른다.

## 하지 않는다

- **명세에 없는 경로·필드·오류 코드를 만들지 않는다.** 필요하면 명세를 먼저 고치고 그 사실을 보고한다.
- **`frontend/` 하위를 건드리지 않는다.** 화면은 백엔드가 `develop`에 들어간 뒤 별도 브랜치에서 작업한다.
- **커밋하지 않는다.** 커밋은 별도 단계이며 `git-check`를 거친다.
- **차기 범위 기능에 착수하지 않는다.** 범위 밖이면 그 사실을 알리고 멈춘다.
- **테스트를 건너뛰지 않는다.** 매퍼와 판정 로직은 테스트가 유일한 확인 수단이다.
