# chaos-runner

**주입하고, 복구하고, 지표를 모아 표를 채운다.** 기대 동작과 실제가 일치하는지, PASS·PARTIAL·FAIL 중 무엇인지, 원인이 무엇인지는 본인이 판단한다. 시험 계획서가 수행 주체를 그렇게 나눴고, 그 부분을 넘기면 시험을 한 의미가 없다.

시나리오·기대 동작·주입 수단·실행 절차·결과서 양식·워크플로 입력은 시험 계획서가, 시나리오별 배경 부하는 트래픽 정의서가, 페일오버·페일백·PITR 절차는 운영 절차서가 갖는다. **본 문서는 순서와 경계만 정한다.**

## 순서

```
1. 사전 확인         대상 환경 · 현재 상태 정상 · 관측 스택 · 시나리오별 전제
        │
        ├── 미충족 ──→ 멈추고 알린다
        │
2. 감시 정지         시험 계획서가 지목한 시나리오만. 본인이 콘솔에서
        │
3. 배경 부하         트래픽 정의서의 시나리오별 프로파일. SSE가 붙으면 SSE를 먼저 기동
        │
4. 워밍업            기준선 구간
        │
5. 주입              ★ 승인. 시험 계획서 주입 수단 표의 명령만. 시각 기록
        │
6. 관찰 → 복구       시각 기록
        │
        ├── 복구 실패 ──→ 현재 상태를 그대로 보고하고 멈춘다
        │
7. 안정화            기준선으로 돌아오는지
        │
8. 수집              구간별 지표 표
        │
9. 결과서 초안       실행 기록 · 지표를 채운다. 판정 · 차이 · 조치는 「본인 기입」
        │
10. 감시 재개 확인   2단계에서 멈춘 것
```

각 구간의 길이는 시험 계획서의 실행 절차가 고정한다. **길이를 바꾸면 시나리오 간 비교가 깨진다.**

## 실행 경로

| 상황 | 경로 | 승인 지점 |
| --- | --- | --- |
| 워크플로가 있다 | `gh workflow run chaos-test -f scenario=<스크립트명> -f background=<T…> [-f sse=true]` → `gh run watch` | **워크플로 기동 전** |
| 하네스가 있다 | `harness.sh <스크립트명>` — 3~8단계를 스크립트가 고정 타이밍으로 실행한다 | **하네스 기동 전** |
| 하네스 구축 전 | 3~8단계를 손으로 밟고 시각을 기록한다 | **주입 명령 실행 전** |

**하네스와 워크플로는 기동이 곧 주입이다.** 중간에 멈춰 물어볼 수 없으므로 기동 전에 확인을 받는다. 한 번 기동은 주입 한 번이고, 다음 시나리오는 다시 확인을 받는다.

워크플로 이름과 입력은 시험 계획서의 실행 트리거 절을 따른다.

## 1. 사전 확인

- **대상이 운영 환경이면 즉시 멈춘다.**
- 주입 전에 현재 상태가 정상인지 본다. 기준선이 흔들리면 장애의 영향을 분리할 수 없다.
- Prometheus가 앱을 스크레이프하고 있는지 본다. 없으면 수집이 성립하지 않는다.
- **시나리오별 전제를 확인한다.** 시험 계획서가 적은 것(노드 정지 전 고정 IP)과, 복구 절차가 요구하는 것(PITR이면 운영 절차서의 복구 단계가 쓰는 기저 백업과 WAL 아카이브). 없으면 시작하지 않는다.

## 2. 감시 정지

시험 계획서가 지목한 시나리오는 외부 경로 감시를 **본인이 콘솔에서** 멈춘 뒤 시작한다. 그대로 두면 계획된 시험이 장애 알림으로 나간다. 재개 확인은 10단계이고 결과서 체크 항목이다.

**외부 알림 도착이 기대 동작인 시나리오는 멈추지 않는다.** 멈추면 검증할 것이 없어진다.

## 3. 배경 부하

트래픽 정의서의 시나리오별 배경 부하 표를 따른다. **SSE 동시 연결이 붙는 시나리오는 SSE 스크립트를 별도 프로세스로 먼저 기동해 연결을 확립한 뒤 본 프로파일을 인가한다.** SSE 없이 돌리면 연결 단절·재연결이 관측되지 않는다.

배경 부하가 「없음」인 시나리오에는 인가하지 않는다.

## 5. 주입

- **주입·복구 명령은 시험 계획서 주입 수단 표의 것만 쓴다.** 표에 없는 파괴적 명령을 만들지 않는다.
- **주입은 자동 승인 대상이 아니다.** 승인 지점은 위 실행 경로 표를 따른다.
- 실행한 명령을 그대로 기록한다. 요약하지 않는다.

## 예외 시나리오

| 시나리오 | 다른 점 |
| --- | --- |
| 노드 전체 정지 | 클라우드 콘솔 조작이라 **본인이 직접 수행한다.** 정지·기동 시각을 손으로 기록한다. 하네스 대상이 아니다 |
| DB primary 다운 | **하네스 대상이 아니다.** 운영 절차서의 페일오버·페일백을 **단계마다 확인을 받고 시각을 기록하며** 밟는다. 승격 전 점검 모드 전환을 건너뛰지 않는다. **승격 직후 상태에서 T2를 다시 인가해 처리 한계를 측정**하고, 페일백까지 마쳐야 완료다 |
| 논리적 손상 후 PITR | 배경 부하 없음. 기저 백업과 WAL 아카이브 존재를 먼저 확인한다 |

## 8·9. 수집과 결과서

`collect.sh`가 구간별 비교표를 만든다. 없으면 같은 구간을 Prometheus `query_range`로 잘라 직접 질의한다.

시험 계획서의 장애 시험 결과서 양식을 그대로 쓴다. **절마다 누가 채우는지가 다르다.**

| 절 | 채우는 쪽 |
| --- | --- |
| 기대 동작 | 에이전트. 시험 계획서 표를 인용한다 |
| 실행 기록 · 구간별 지표 | 에이전트 |
| 판정 · 관찰된 차이 · 조치 사항 | **본인.** `「본인 기입」`으로 남긴다 |

지표 표에는 **시나리오별 검증 지표**를 반드시 넣는다. p95와 5xx만으로는 기대 동작을 대조할 수 없는 시나리오가 있다.

전 시나리오가 끝나면 요약 파일을 만든다. 판정 요약표와 발견 사항 모두 본인이 채운 결과서에서 옮긴다. 새로 쓰지 않는다.

## 하지 않는다

- **판정하지 않는다.** 기대 동작과 다르게 보여도 「FAIL」이라 쓰지 않고, 같아 보여도 「PASS」라 쓰지 않는다. 수치를 놓고 본인이 본다.
- **관찰하지 못한 항목을 추정으로 채우지 않는다.** 수집에 실패했으면 그렇게 쓴다.
- **복구를 확인하지 않고 다음 시나리오로 가지 않는다.**
- **시험 중 발견한 문제를 고치지 않는다.** 코드를 고치면 이후 결과가 앞과 비교되지 않는다.
- **실패한 실행을 성공할 때까지 반복하지 않는다.** 실패가 기록 대상이다.
- **커밋하지 않는다.** 결과서 커밋과 PR은 별도 단계이며 시험 이슈를 닫는 수단이다.
