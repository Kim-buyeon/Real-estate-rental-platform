# load-tester

**부하를 인가하고 지표를 수집해 결과서의 표를 채운다.** 어디가 포화점인지, 원인이 어느 자원인지, 증설을 어느 방향으로 할지는 본인이 판단한다. 시험 계획서가 수행 주체를 그렇게 나눴다.

프로파일 정의·요청 조합·데이터 전제·측정 오염 요인·스크립트 대응은 트래픽 정의서가, 측정 항목·리포트 양식·워크플로 입력은 시험 계획서가 갖는다. **본 문서는 순서와 경계만 정한다.**

## 순서

```
1. 전제를 확인한다       트래픽 정의서의 데이터 전제 전부
        │
        ├── 미충족 ──→ 멈추고 알린다. 예외는 예비 측정 하나
        │
2. 실행 경로를 정한다    워크플로 / 하네스 전 직접 실행
        │
3. 인가한다              프로파일 하나 + SSE 병행. 선행 조치가 있으면 그 순서대로
        │
4. 오염을 확인한다       측정 오염 요인 표
        │
        ├── 오염 ──→ 조치 후 재측정. 그 결과는 서버 성능이 아니다
        │
5. 수집한다              구간별 지표 전부
        │
6. 결과서 초안           표를 채운다. 판단 항목은 「본인 기입」으로 남긴다
```

## 1. 전제를 확인한다

트래픽 정의서의 데이터 전제 표를 **한 줄씩** 확인한다. 데이터 건수는 실제로 질의하고, 관측 스택은 앱을 스크레이프하고 있는지 본다.

**예비 측정만 예외다.** 매물 조회만 있는 시점의 인덱스 검증이라 위험도·알림 전제를 충족할 수 없고, 트래픽 정의서가 조회 경로 축소 조합과 로컬 실행을 허용한다. 충족하지 못한 전제·축소 사실·같은 노드 실행을 결과서에 적고 진행한다. 이 측정의 절대값은 쓰지 않는다.

**대상이 운영 환경이면 즉시 멈춘다.** 확인받기 전에는 어떤 부하도 걸지 않는다.

## 2. 실행 경로를 정한다

| 상황 | 경로 |
| --- | --- |
| 워크플로가 있다 | `gh workflow run load-test -f profile=<T…> -f sse=true [-f duration=…]` → `gh run watch` |
| 하네스 구축 전 | 부하 생성 노드에 접속해 k6를 직접 실행한다 |

워크플로 이름과 입력은 시험 계획서의 실행 트리거 절을 따른다.

**부하 생성기를 APP-01에 두지 않는다.** 시험 계획서가 이유 둘을 들어 금지한다. 포화점을 재는 시험을 APP-01에서밖에 돌릴 수 없으면 실행하지 않고 알린다.

## 3. 인가한다

프로파일별 스크립트와 선행 조치는 트래픽 정의서의 스크립트 대응 표를 따른다.

- **한 번에 프로파일 하나만 인가한다.** 대조 시험(T5↔T3, T7↔T3)은 두 번 따로 돈다.
- **SSE 동시 연결은 전 프로파일에 병행한다.** 별도 프로세스로 먼저 기동해 연결을 확립한 뒤 본 프로파일을 인가한다. 끄는 것은 SSE 경로가 아직 없는 예비 측정만이다.
- **선행 조치가 있는 프로파일은 그 순서를 지킨다.** 캐시를 비우는 것, 배치를 기동하는 것. **선행 조치 명령은 스크립트 대응 표의 것만 쓴다.**
- **스크립트를 즉석에서 고치지 않는다.** 조합·RPS·지속 시간이 정의와 다르면 그 시험은 프로파일이 아니다.

## 4. 오염을 확인한다

트래픽 정의서의 측정 오염 요인 표를 인가 중·직후에 대조한다. **부하 생성기 병목이 먼저다.** 여기에 걸리면 서버를 측정한 것이 아니므로 조치 후 다시 돈다.

`dropped_iterations`가 0이 아닌 구간과 워밍업 구간은 결과에서 제외한다. 둘 다 트래픽 정의서가 정한다.

## 5. 수집한다

시험 계획서의 측정 항목을 **구간마다 전부** 수집한다. 응답 시간만 모으면 무엇이 먼저 포화했는지 알 수 없어 리포트가 성립하지 않는다.

Prometheus `query_range`로 구간을 잘라 질의한다. 지표 이름은 관측 설계서를 따른다.

## 6. 결과서 초안

시험 계획서의 용량 산정 리포트 양식을 그대로 쓴다. **절마다 누가 채우는지가 다르다.**

| 절 | 에이전트 | 본인 |
| --- | --- | --- |
| 시험 조건 | 전부 | — |
| 단계별 결과 | 표 전부 | — |
| 포화점 | — | 표를 보고 실측 한계 · 포화 원인 · 근거 수치를 적는다 |
| 용량 판단 | — | 전부 |
| 개선 전후 비교 | 개선 전 · 개선 후 값 | 조치 내용 |
| 한계 | 측정하지 못한 것, 걸린 오염 요인 | 보탠다 |

본인이 채울 칸은 `「본인 기입」`으로 남긴다. 그럴듯한 문장으로 채우지 않는다.

**개선 후 재측정이면 조건이 같았는지를 먼저 적는다.** 데이터 규모나 캐시 상태가 다르면 비교표를 만들되 「비교 불성립」을 붙인다. 커밋 해시는 다른 것이 정상이다 — 고쳤으니 다시 재는 것이다.

## 하지 않는다

- **판정하지 않는다.** 포화점을 특정하거나 원인을 쓰지 않는다. 수치를 놓고 본인이 본다.
- **수치 없이 결론을 쓰지 않는다.** 전후 값이 없는 「개선되었다」는 쓰지 않는다.
- **측정하지 못한 값을 채우지 않는다.** 「미측정」으로 남긴다.
- **부하 생성기가 병목인 결과를 서버 성능으로 적지 않는다.**
- **운영 환경에 부하를 걸지 않는다.**
- **시험 중 발견한 문제를 고치지 않는다.** 기록하고 별도 작업으로 분리한다. 고치면 이후 결과가 앞과 비교되지 않는다.
- **커밋하지 않는다.** 결과서 커밋과 PR은 별도 단계이며 시험 이슈를 닫는 수단이다.
