## 한계

1. **데이터 규모가 정의에 못 미친다.** 등기 이력(`mortgage_history`)이 매물당 약 0.15건으로, 트래픽 정의서 6장의 매물당 8건의 2% 수준이다. 지도 조회의 저당 확인은 해시 서브플랜이라 영향이 작다고 보지만, 위험도 조회(`GET …/risk` — 조회 시점에 분석한다) 비용은 이력이 늘면 오른다. 실측하지 않았다.
2. **T2-② · ③ 에는 SSE 250 연결이 없다.** k6 자동 확장 해석이 `k6/x/sse` 를 받지 못해 SSE 스크립트가 곧바로 끝났는데, 본 프로파일은 그대로 돌았다(하네스 README 에 함정으로 적었다). 첫 측정 T1 · T2-① 은 연결을 유지했다. 개선 전후 비교는 둘 다 없는 조건끼리라 성립하지만, **SSE 연결이 있는 상태의 60 r/s 는 재지 않았다.** 연결 250개의 메모리 몫이 앱 슬롯 상한을 더 좁힐 수 있다.
3. **토큰 풀(100) < VU.** `THINK=0` 이어도 200 RPS 단계는 VU 가 풀보다 많아, 30분 뒤 소유자가 아닌 VU 의 인증 요청이 401 이 된다(하네스 README 한계 1). 서버 문제가 아니지만 상한 안의 자리를 먹는다.
4. ~~포화점을 값으로 특정하지 못했다~~ **9/27 T2-⑧ 로 「125 RPS 초과」까지 좁혔다** — 값은 아직 아니다(125 에서도 기준 안). 150 · 175 · 200 단계가 남는다. (원문) **포화점을 값으로 특정하지 못했다**(포화점 절). 50 · 60 · 75 · 100 처럼 촘촘한 단계로 한 번 더 재야 한다.
5. **캐시 적중률 · GC 일시정지 · 힙과 힙 밖의 구분을 재지 않았다.** 시험 계획서 2.2 측정 항목 중 **PostgreSQL 커넥션 수 · 슬로우 쿼리 · Redis 적중률 · 축출 · GC 일시정지 · 외부 연동 응답 시간 · 서킷 상태는 재지 않았다.** 앱 슬롯 종료가 힙이 아니라 컨테이너 상한에서 났으므로(힙 상한 360m, 종료 시 RSS 약 602 MB) **힙 밖이 240m 을 넘었다는 것까지만 안다** — 무엇이 늘었는지는 모른다(시스템 구성서 한계 항목).
6. **표본 1회.** 같은 조건을 반복하지 않았다. 60 r/s 는 잠정값이다.
7. **T6 은 9/27 에 돌렸다**(위 표 — 25 RPS 배경, 짧게 8분). **T3 단독 · T4 지속 · T5 캐시 콜드 · T7 배치 동시는 돌리지 않았다**(이름은 트래픽 정의서 4장). T3 는 장애 주입의 배경 부하라 단독으로 돌리지 않는다. T4 는 2시간 · 비용, T5 는 `FLUSHALL` 이 로그인 토큰까지 지운다. (9/26 에는 자동 권한 판정이 배포를 막아 T6 을 돌리지 못했다.) T7 은 배치를 기동할 수단을 확인하지 못했다(#257 계획).
8. **실사용 패턴이 아니다.** 요청 조합 · 지역 분포 · 지도 영역 크기는 트래픽 정의서의 가정이고, 지도 2단계 영역 반폭은 스크립트가 스스로 정한 값이다(`lib/mix.js`). 실제 화면이 더 좁은 영역을 부르면 응답이 작아진다.
9. **생성기의 응답 압축.** k6 는 압축을 요청하지 않아 지도 2단계를 1.27 MB 그대로 받았다(앞단 기록 — 같은 요청을 압축으로 받으면 106 KB). 브라우저는 압축을 요청하므로 실사용에서는 앞단의 압축 CPU 가 들고 전송량이 준다. 이 차이는 재지 않았다.
10. **9/27 시험(T2-⑥ · ⑦ · T6)의 setup 이 막힌 조회를 불렀다.** 좌표 경계 · 시드 매물을 좌표 영역 마커 조회로 구했는데 #268 이 그 조회를 400 으로 막아, 시드 매물이 비었다. VU 가 첫 지도 조회로 매물을 기억하기 전의 상세 · 위험도 · 대출 요청이 `/api/properties/null` 로 나가 400 이 됐다(T2-⑥ 437건 ≈ 0.5%, T6 454건 — 처음 몇 분에 몰림). 서버 결함이 아니고 ⑥ · ⑦ 이 같은 조건이라 전후 비교는 성립하지만, 그만큼 상세 · 위험도 조회의 DB 부하가 덜 들어갔다. setup 을 묶음 조회 · 목록 조회로 바꿨다(`lib/mix.js`, 이 PR). **다음 회차부터 측정 방식이 달라진다** — 자치구 경계가 서울 전체 12×12 칸 평균 · 낱개 마커의 분위(건수 가중 없음)라 전보다 거칠고, 시드는 등록순 상위 100건이다. T2-④ ~ ⑦ 과 비교할 때 이 차이를 적는다.
11. ~~인덱스 뒤 상한 200 재측정은 하지 않았다.~~ **9/27 T2-⑧ 로 쟀다 — 125 RPS 통과.** (원문) T2-⑦ 은 상한 60 조건이라 100 RPS 를 실제로 받아 보지 않았다. DB-01 CPU 가 절반이 됐으니 T2-⑤ 의 100 RPS(지도 961ms)가 기준 안으로 들어올 가능성이 있지만 **재지 않았으므로 상한 60 은 그대로 둔다.** 올리려면 상한 200 으로 T2 를 다시 돈다.
