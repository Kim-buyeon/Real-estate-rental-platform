# 성능 원인 정밀 조사 (2026-09-29)

이슈 #292. 성능 카드(`perf-cards-20260928.md`, #290)에서 **추론으로 적었던 원인을 운영 노드에서 직접 확인**했다. 앱 · DB 는 고치지 않았다 — 측정용 임시 설정은 모두 되돌렸다(맨 아래 「되돌린 것」).

**근거 표시** — 문장 끝의 괄호가 그 문장의 근거다.
**측정**: 부하를 주고 잰 값(k6 · DB 질의 통계 · DB 대기 샘플 · Grafana · CPU 프로파일) / **실제 계획**: 운영에서 돈 질의의 실행 계획 로그(auto_explain) / **계획 비교**: 같은 질의를 조건만 바꿔 `EXPLAIN ANALYZE` 한 결과 / **코드**: 파일 · 줄.
확인하지 못한 것은 「미확인」 절에 따로 모았다 — 본문에 추측으로 채우지 않았다.

**지도 화면의 세 단계** — 1단계: 서울 전체에서 구마다 매물 수 숫자. **2단계**: 구를 확대하면 가까운 매물을 묶은 **숫자 동그라미**(`GET /api/properties/map-clusters`). **3단계**: 더 확대하면 반경 안 매물이 **핀 하나하나**(`GET /api/properties?lat&lng&radiusKm`).

**틀렸던 것(성능 카드 9/28 · 29)** — 「준비문 일반 계획이 원인」은 **틀렸다**. 값을 넣어 계획해도 똑같이 느린 방식이 나오고(계획 비교), 일반 계획을 금지해도 2단계 591 → 594 ms · 섞은 부하 24.9 → 24.9 ms 로 **그대로**였다(측정). 「`effective_cache_size` 4GB 불일치」는 **누가 설정한 값이 아니라 PostgreSQL 기본값**이고, 512MB · `random_page_cost` 1.1 로 바꿔도 **계획이 같았다**(34.0 → 32.9 ms, 계획 비교). 성능 카드 결과서의 해당 절을 이 문서에 맞게 고쳤다.

## 1. 지도 질의 — 좌표 타입 불일치

### 무엇이 문제인가

지도 2 · 3단계는 화면에 보이는 영역(위도 · 경도 범위)으로 매물을 고른다. 앱은 이 범위를 `double` 로 들고 있고(`BoundingBox.java:4` — `record BoundingBox(double minLat, double maxLat, double minLng, double maxLng)`)(코드), JDBC 는 이것을 `float8` 로 보낸다. DB 의 `property.latitude · longitude` 는 `NUMERIC` 이다(엔티티 `Property.java:103 · 106` `BigDecimal`)(코드). 타입이 다르면 PostgreSQL 은 **열 쪽을 바꿔서** 비교한다 — 계획에 `(latitude)::double precision >= …` 로 찍힌다(계획 비교 · 실제 계획).

그 결과 세 가지가 연달아 일어난다(모두 계획 비교 — 강남구 한 화면, 결과 3,126행).

| | 지금(좌표 `float8`) | 좌표를 `numeric` 으로 맞추면 |
|---|---|---|
| 좌표 인덱스 `(district, latitude, longitude)` | **못 쓴다** — 구 인덱스로 4,973행을 읽고 1,847행을 버린다 | 쓴다 — 처음부터 3,126행만 |
| DB 의 결과 수 예상 | **1행**(실제 3,126) | 654행 |
| 고르는 방식 | 한 건씩 처리(중첩 루프) — 코드 표를 **3,126번 × 2**, 위험 분석을 3,126번 따로 읽는다 | 한꺼번에 처리(해시 조인) — 코드 표 1번 |
| 읽은 메모리 블록 · 실행 시간 | **15,051** · 34.0 ms | **711** · 26.3 ms |

지도 3단계(핀)도 같은 원인이다 — 8.9 ms → 3.2 ms(계획 비교).

### 운영에서 실제로 이렇게 도는가

- 부하 중 기록한 실제 계획 중 **지도 2단계 268건 전부**가 한 건씩 처리 · 좌표 변환 비교였다(섞은 부하 23 · 몰린 구 111 · 고른 구 134)(실제 계획).
- 섞은 부하에서 2단계 질의 한 번이 읽은 블록 평균 **11,225**, 몰린 구에서 **20,042**(측정) — 위 표의 「지금」과 같은 규모다.

### 얼마나 부하를 주는가

| 부하 | 결과 |
|---|---|
| **실사용 비율로 섞은 부하** 25 RPS · 5분(트래픽 정의서 비율) | 앱 질의 DB 시간 32.6초 중 **2단계 78.4 % · 3단계 14.7 % — 합 93 %**. 나머지 50여 종 질의가 7 %(측정). DB 가 일한 시간의 **100 %가 CPU**(디스크 · 락 대기 0)(측정) |
| 2단계 — **매물 수 1위 구 하나**에 몰림 | 10 RPS p95 68 ms → 25 RPS p95 175 ms → **50 RPS 타임아웃 92 %**. DB CPU 100 %, DB 안 동시 실행 평균 9.4 · 최대 32, 질의 평균 591 ms(단독 34 ms)(측정) |
| 2단계 — 25개 구에 고르게 | 50 RPS 까지 p95 74 ms, DB CPU 57 %(측정) |

**뜻** — 지금 DB 병목의 거의 전부가 이 두 질의다. 몰린 구에서는 CPU 2개에 질의가 9개씩 몰려 한 번에 걸리는 시간이 17배가 된다(측정).

### 고칠 때 알아야 할 것

- 타입만 맞추고 **일반 계획(값을 보지 않고 미리 짜 둔 계획)** 이 쓰이면 다시 한 건씩 처리로 돌아간다 — 17,603 블록(계획 비교). 그래서 이 두 질의는 타입 수정과 함께 「값을 넣은 계획」이 쓰이는지 확인해야 한다.
- 고친 뒤 **같은 회차(섞은 부하 · 2단계 몰림 · 3단계 몰림)로 전후를 잰다** — 부하 상황의 효과는 그때 확정한다.

## 2. 로그인 — 비밀번호 확인 동안 커넥션 점유

- `UserCommandService.login` 은 `@Transactional` 안에서 `passwordEncoder.matches`(BCrypt — `SecurityConfig.java:109` 에서 인자 없는 기본 생성자로 만든다)를 부른다(코드). 트랜잭션이 열리면 커넥션을 빌려 두므로, 비밀번호를 확인하는 동안 커넥션을 쥐고 있다.

| 로그인 부하 | p95 | 앱 CPU(APP-01 · APP-02) | DB CPU | 커넥션 한 번 사용 시간 | 커넥션 대기(네 슬롯 합) |
|---|---|---|---|---|---|
| 10 RPS | 126 ms | — | — | — | — |
| 25 RPS | 150 ms | — | — | — | — |
| **50 RPS** | **10초(타임아웃) · 5xx 14 %** | **100 % · 100 %** | 8 % | **801 ms**(평소 28 ms) | **164** |

(모두 측정. 앱 CPU · 커넥션 값은 회차 구간 최대)

- 50 RPS 프로파일(APP-02 슬롯, 30초 · 표본 2,880개): 요청 스레드 CPU 의 **97 %가 BCrypt**(측정). 같은 때 스레드 덤프 — BCrypt 계산 중 스레드가 커넥션 풀 크기(8)만큼, 나머지는 커넥션 대기(성능 카드 9/29 측정).
- **뜻** — 로그인 처리량의 한계는 BCrypt 가 먹는 CPU 다. 문제는 그동안 커넥션까지 쥐어서 **로그인이 몰리면 커넥션을 쓰는 다른 모든 화면이 함께 멈춘다**는 것이다. 해싱을 트랜잭션 밖으로 빼면 이 전파가 끊긴다. 로그인은 트래픽 정의서 3.1 에 없는 요청이다 — 평소가 아니라 모두가 다시 로그인하는 순간(토큰 일괄 만료 · 대입 공격)에 닿는다.

## 4. 커넥션 누수 감지 설정

- `application.yml:38` `leak-detection-threshold: 30000`(코드). 이 값이 0 보다 크면 Hikari 는 커넥션을 빌릴 때마다 「누가 빌렸는지」 스택을 남기려고 예외 객체를 하나 만든다 — 프로파일에서 `HikariPool.getConnection → ProxyLeakTask.<init> → Exception.<init> → fillInStackTrace` 로 보였다(측정).
- 대출 한도 50 RPS 프로파일에서 요청 처리 표본 349개 중 37개(**10.6 %**), 위험 판정에서 380개 중 11개(2.9 %)(측정).
- **측정 조건** — 이 두 프로파일은 슬롯 재시작 직후라 전체 표본의 41 · 63 %가 JIT 컴파일이었다(측정). 요청 스레드 안의 비율은 쓸 수 있지만, 예열이 끝난 JVM 에서의 크기는 다시 재야 확정된다.

## 6. 앱 CPU 프로파일 — 확인된 것과 못 한 것

| 회차(50 RPS, APP-02 슬롯 30초) | 표본 | JIT 컴파일 | 요청 스레드 안 결론 |

| 무엇 | 왜 못 했나 | 확인하려면 |
