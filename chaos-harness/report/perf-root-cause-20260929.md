# 성능 원인 정밀 조사 (2026-09-29)

이슈 #292. 성능 카드(`perf-cards-20260928.md`, #290)에서 **추론으로 적었던 원인을 운영 노드에서 직접 확인**했다. 앱 · DB 는 고치지 않았다 — 측정용 임시 설정은 모두 되돌렸다(맨 아래 「되돌린 것」).

**근거 표시** — 문장 끝 괄호가 그 문장의 근거다. **측정**: 부하를 주고 잰 값(k6 · DB 질의 통계 · DB 대기 샘플 · 컨테이너 메모리 샘플 · Grafana · CPU 프로파일 · 스레드 덤프) / **실제 계획**: 운영에서 돈 질의의 실행 계획 로그(auto_explain) / **계획 비교**: 같은 질의를 조건만 바꿔 `EXPLAIN ANALYZE` 한 결과 / **코드**: 파일 · 줄 / **문서**: 설계 문서. 근거 표시가 없는 「기대」는 고친 뒤 재야 확인되는 것이다. 확인하지 못한 것은 「미확인」 절에 모았다.

**지도 화면의 세 단계** — 1단계: 서울 전체에서 구마다 매물 수 숫자. **2단계**: 구를 확대하면 가까운 매물을 묶은 **숫자 동그라미**(`GET /api/properties/map-clusters`). **3단계**: 더 확대하면 반경 안 매물이 **핀 하나하나**(`GET /api/properties?lat&lng&radiusKm`). 「몰린 구」는 부하를 매물 수 1위 구 하나(**강서구**)에만 준 회차, 「고른 구」는 25개 구에 고르게 준 회차다(측정 — k6 로그의 요청 주소 · 「상위 자치구」).

## 1. 지도 질의 — 좌표 타입 불일치

### 무엇이 문제인가

지도 요청의 좌표 범위는 `Double` 로 들어와(`PropertyMapClustersRequest.java:25-28` · `PropertySearchRequest.java:34-37`) 매퍼가 바인딩하는 조건 객체도 `Double` 이다(`PropertySearchCondition.java:36-39`)(코드). DB 의 `property.latitude · longitude` 는 `NUMERIC` 이다(엔티티 `Property.java:103 · 106` `BigDecimal`)(코드). 타입이 다르면 PostgreSQL 은 **열 쪽을 바꿔서** 비교한다 — 계획에 `(latitude)::double precision >= …` 로 찍힌다(계획 비교 · 실제 계획).

그 결과(계획 비교 — 강남구 한 화면, 결과 3,126행, `sql/map-clusters.sql` · `map-clusters-numeric.sql`):

| | 지금(좌표 `float8`) | 좌표를 `numeric` 으로 맞추면(값을 넣은 계획) |
|---|---|---|
| 좌표 인덱스 `(district, latitude, longitude)` | **못 쓴다** — 구 인덱스로 4,973행을 읽고 1,847행을 버린다 | 쓴다 — 처음부터 3,126행만 |
| DB 의 결과 수 예상 | **1행**(실제 3,126) | 654행 |
| 고르는 방식 | 한 건씩 처리(중첩 루프) — 코드 표를 3,126번 × 2, 위험 분석을 3,126번 따로 읽는다 | 한꺼번에 처리(해시 조인) — 코드 표 1번 |
| 읽은 메모리 블록 · 실행 시간 | **15,051** · 34.0 ms | **711** · 26.3 ms |

지도 3단계도 같은 원인이다 — 3,887 블록 · 8.9 ms → 2,814 블록 · 3.2 ms(계획 비교, `map-markers-radius*.sql`).

### 운영에서 실제로 이렇게 도는가

- 부하 중 기록한 2단계 실제 계획 **374건 전부**가 중첩 루프 · 좌표 변환 비교였다(실제 계획 — A: 섞은 부하 23 · 몰린 구 111 · 고른 구 134, B: 섞은 부하 19 · 몰린 구 87).
- 섞은 부하에서 2단계 질의 한 번이 읽은 블록 평균 **11,227**, 몰린 구 **20,042**(측정).

### 얼마나 부하를 주는가

| 부하 | 결과(측정) |
|---|---|
| **실사용 비율로 섞은 부하** 25 RPS · 5분(트래픽 정의서 비율) | 앱 질의 DB 시간 32.6초 중 **2단계 78.4 % · 3단계 14.7 % — 합 93 %**, 나머지 53종이 6.9 %. DB 대기 샘플(325초 중 활동 21건)은 모두 CPU — 디스크 · 락 대기 0 |
| 2단계 — 몰린 구(강서구) | 10 RPS p95 67 ~ 68 ms. **25 RPS p95 는 회차마다 크게 달랐다 — 175 ms(A) · 803 ms(B) · 1,922 ms(9/29 성능 카드)**. **50 RPS 는 세 회차 모두 실패 89 ~ 94 %**. 회차 구간 DB CPU 최대 100 %(Grafana), DB 안 동시 실행 평균 9.4 · 최대 32, 질의 평균 591 ms |
| 2단계 — 고른 구 | 50 RPS 까지 p95 74 ms, DB CPU 57 %, 질의 평균 19.9 ms |

**뜻** — 지금 DB 병목의 거의 전부가 이 두 질의다(측정). 몰린 구의 한계는 25 ~ 50 RPS 사이에 있고, 25 RPS 에서 이미 회차에 따라 p95 가 기준(500 ms)을 넘는다(측정). 강서구 영역 한 번의 단독 실행 시간은 이번에 재지 않았다.

### 고칠 때 알아야 할 것(계획 비교)

- 타입만 맞추고 **일반 계획(값을 보지 않고 미리 짜 둔 계획)** 이 쓰이면 다시 한 건씩 처리가 된다 — 2단계 17,603 블록 · 31.6 ms, 3단계 4,178 블록.
- 타입을 맞춘 뒤에는 플래너 값도 계획을 바꾼다 — `effective_cache_size = 512MB` · `random_page_cost = 1.1` 이면 2단계가 해시 조인(711 블록 · 26.3 ms)에서 중첩 루프 + Memoize(8,792 블록 · 23.1 ms)로 바뀐다. 3단계 2,814 → 3,146 블록.
- 그래서 고친 뒤에는 **같은 회차(섞은 부하 · 2단계 몰린 구 · 3단계 몰린 구)로 전후를 재고, 실제 계획을 auto_explain 으로 확인**한다.

## 2. 로그인 — 비밀번호 확인 동안 커넥션 점유

- `UserCommandService.login`(76 ~ 84행)은 `@Transactional` 안에서 `passwordEncoder.matches`(BCrypt — `SecurityConfig.java:109` 에서 인자 없는 기본 생성자로 만든다)를 부른다(코드).

| 로그인 부하 | p95 | 5xx |
|---|---|---|
| 10 RPS | 126 ms | 0 |
| 25 RPS | 150 ms | 0 |
| **50 RPS** | **10초(타임아웃)** | **14 %** |

(측정) 회차 구간에서 앱 CPU 두 노드 최대 100 % · DB CPU 최대 8 %, 커넥션 한 번 사용 시간 최대 **801 ms**(평소 회차 28 ms), 커넥션 대기 최대 **164**(네 슬롯 합)(측정 — Grafana, 회차 구간 최대).

- **뜻** — 로그인 처리량의 한계는 BCrypt 가 먹는 CPU 다(측정). 그동안 커넥션까지 쥐어 슬롯의 커넥션 8개가 모두 로그인에 묶였다(측정). 로그인은 트래픽 정의서 3.1 에 없는 요청이다(문서).

## 4. 커넥션 누수 감지 설정

- `application.yml:38` `leak-detection-threshold: 30000`(코드). 이 설정이 켜진 상태에서 프로파일에 `HikariPool.getConnection → ProxyLeakTask.<init> → Exception.<init> → fillInStackTrace` 가 보였다 — 커넥션을 빌릴 때마다 호출 위치를 담은 예외 객체를 만든다(측정 · 코드).

| 프로파일(50 RPS) | 요청 표본 | 그중 `ProxyLeakTask` 가 있는 표본 |
|---|---|---|
| 지도 2단계 | 135 | 18 (**13.3 %**) |
